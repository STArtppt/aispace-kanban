PDF 转换引擎阶梯

把 PDF / PPTX 的默认转换从 MinerU 在线 API 换成本地的 anydoc，MinerU 退成扫描件与抽图的兜底。 目的不是提速，是让日常入库不再依赖网络，顺带修掉现有兜底静默损坏中文的问题。

引入@firecrawl/anydoc 0.2.3
保留MinerU · 扫描件 / 抽图
淘汰markitdown · 仅留 .msg
不引pdf-inspector · 已内嵌

为什么要改

网络是单点

MinerU 是整条入库链路里唯一外发资料的环节，也是唯一会因为网络失败的环节。 轮询 5 秒一次、上限 900 秒，赶上服务抖动就是等一刻钟拿一个失败。

它还有 200 页 / 200 MB / 每天 1000 页的硬限制 —— 稍厚一点的规程、标准、教材根本进不来。

没配 key 时的兜底会静默损坏中文

实测 markitdown 转中文 PDF，会把常用汉字写成康熙部首区的同形字。 产物肉眼看着没问题，但 grep 水库 一条都搜不到。

水
U+6C34
源文档
⽔
U+2F54
markitdown 产物

「门」同理：U+95E8 → U+2ED4。 看板搜索和后面所有 AI 分析都建立在这份产物上 —— 这比转失败更糟，转失败至少台账上是红的。

实测对照 · macOS arm64 / Node 22 / anydoc 0.2.3

场景 markitdown（现兜底） anydoc
中文 PDF 码位 ✗康熙部首，搜不到「水库」 ✓全对
标题层级 ✗全丢 ✓# / ## 还原
369 页中文 PDF（8.4 MB） — ✓1.3 秒 · 24.6 万字 · 560 行表格
MinerU 超 200 页会被直接拒
真实中文 PPTX — ✓0.7 秒 · 91 个标题 · 137 行表格
扫描件 ✗静默产出空文件 ✓明确报错，带类型和页数

anydoc 是 MIT 的 Rust 单二进制，无运行时依赖：npm 包装 10 KB + 平台二进制 6.7 MB，按平台只装一个。 不要单独再引 pdf-inspector —— anydoc 的 PDF 后端就是它，而且它的 npm 包没有 darwin-x64 预编译，Intel Mac 上装不上。

anydoc 做不到的三件事 —— 这就是 MinerU 必须留着的理由

PDF 里的图一张都拿不到
不是 CLI 的问题：Python 绑定调 to_document() 对 PDF 直接抛 UnsupportedError: PDF converts directly to Markdown。 现在 write_mineru_result() 是会把图落进 input/assets/ 的，这条能力只有 MinerU 有。
不做 OCR
npm CLI 连 --ocr 选项都没有 —— OCR 是 Rust 的 build-time feature， 还要外挂 PDFium 与 ONNX Runtime。
版式启发式基于字号
封面、目录、多栏这类页会翻车：369 页那份出了 897 个标题，版权页被当成表格。 MinerU 的版面模型在这类页上明显更好。

PPTX 的图：CLI 出的 markdown 不带图，但 Python 绑定的 to_document() 能拿到原始图片字节（实测那份 pptx 有 76 张）。 本条不走 Python 绑定 —— ingest.py 的「零 Python 依赖」是硬约束，为抽图破例不值当。

改成一条阶梯

①
anydoc默认 · 本地 · 不联网

绝大多数 PDF 走到这里就结束了。

②
MinerU --ocranydoc 报 Scanned / ImageBased 时自动升级

不需要额外的探测工具：anydoc 的报错串里自带类型和页数，正则抓一下就能路由。 没配 key 就记一条 ⚠ 扫描件需 OCR，不算失败。

③
--pdf-engine mineru用户显式指定

要抽图、要公式、版式复杂时手动走这条。

PPTX
默认引擎维持 MinerU（要抽图）；没配 key 时的兜底从 markitdown 改成 anydoc。
.msg
继续 markitdown —— 这是留着它的唯一理由。

四个坑 · 都是「本地绿了、发出去坏了」那一类

01
组包脚本会漏掉这个依赖

build-npm-package.mjs(L100–133) 靠正则扫裸 import 字面量决定发布包的 dependencies。 createRequire(...).resolve('@firecrawl/anydoc/cli.js') 匹配不上 —— createRequire( 里是大写 R，参数也不是字符串字面量。 结果是本地跑得好好的、发出去的包里没这个依赖，装包的人一转 PDF 就悄悄退回兜底。

02
新的日志分支必须排在 mineru 那条前面

summarizeIngestLog() 里那条判断吃的是整段日志而不是某一行： 只要日志里任何地方出现过 mineru 和「缺 / 失败」，它就先命中， 用户看到的就变成「检查 token 是否正确」这种驴唇不对马嘴的话。

03
subprocess.run 必须显式给 encoding="utf-8"

只写 text=True 的话，Windows 上默认跟系统 locale 走，中文正文当场炸。 和 ingest.py 顶上那段 reconfigure 是同一个坑。

04
扫描件不算 failures

它不是失败，是缺配置。算进去会让整批退出码变 1，看板整条飘红。 另外升级进 deferred 的文件必须让 mineru.parse_batch(is_ocr=True) —— 不能沿用命令行 --ocr 的默认 False，它们本来就是扫描件。

验收 · typecheck 绿不算做完

  • buildpnpm typecheck + pnpm build 绿。

  • cli一份中文 PDF → 产物里能 grep 到正文中的中文词，frontmatter 的 converted_by 是 anydoc。

  • cli一份扫描版 PDF，没配 MINERU_API_KEY → 台账是 ⚠ 扫描件需 OCR，脚本退出码仍是 0。

  • cli同一份扫描件，配了 key → 自动走 MinerU OCR 出正文。

  • 回归--pdf-engine mineru --force 重转一份带图的 PDF → 图仍落进 input/assets/，链接点得开。别把抽图能力弄丢了。

  • 浏览器重启 pnpm serve，点一次「转换」；再把 ANYDOC_BIN 指到一个不存在的路径点一次 —— 提示要是人话，不是一段 traceback。

  • 装包pnpm build:npm && node scripts/smoke-package.mjs：干净目录装包后能转 PDF。这一步专门验坑 1，跳过等于没验。
