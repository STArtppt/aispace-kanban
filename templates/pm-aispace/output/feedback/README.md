# output/feedback/ — 看板反馈单

这里放交给看板维护者的单子，分两种：

- **缺陷单**（`kind: bug`，缺省）：看板显示不对、而且改工作空间里的写法绕不开时写。
- **贡献单**（`kind: contribution`）：在这个工作空间里沉淀出**换一个项目也成立**的改进
  （去 AI 味规则、技能文案的通用补充、模板脚本的缺陷修复），交回模板源。

看板的 ⌘K 工作台「反馈单」页读这个目录。它**不进**产出列表、搜索、溯源反链和完整度。

一份一个文件：`F<四位编号>.md`，例如 `F0007.md`。两种单子共用一套编号。

## 编号

- 四位数字，从 `F0001` 起，只增不复用。删了一份也不把号让出来。
- 编号以**文件名**为准。front-matter 里的 `id` 要和文件名一致。
- 看板不新建反馈单。建文件是工作空间智能体的事。

## 谁写哪一块

人和智能体各写各的，不用锁。

| 区域 | 字段 | 谁写 |
| --- | --- | --- |
| AI 写区 | `id` `title` `kind` `created` `status` `receipt`，以及正文的内容节 | 工作空间智能体 |
| 人写区 | `sent_at`，以及「## 发送记录」下的 `###` 子节 | 看板，只在用户点「我已发出」之后 |

看板若收到 `status` / `receipt` / `title` / `id` / `created`，整份不落盘。
智能体回写回执时**只改 `status` 和 `receipt`**，不要动 `sent_at`，也不要改「## 发送记录」。

## 类型 `kind`

| 值 | 含义 |
| --- | --- |
| `bug` | 缺陷单。不写 `kind` 也按缺陷单处理，旧单不用改 |
| `contribution` | 贡献单 |

写成别的值，看板归到「未识别」组并显示原文。

## 状态与分组

`status` 只有三个值：

| 值 | 含义 |
| --- | --- |
| `pending` | 还没处理完 |
| `fixed` | 看板那边已修复（贡献单：已收进模板） |
| `wontfix` | 不修，理由写在 `receipt`（贡献单：不收） |

看板上的分组不写进文件，由这两个字段推出来：

| 条件 | 分组 |
| --- | --- |
| `pending` 且 `sent_at` 为空 | 待发送 |
| `pending` 且 `sent_at` 有值 | 已发送 |
| `fixed` | 已修复 |
| `wontfix` | 不修 |
| 其它写法、`kind` 写歪，或文件解析失败 | 未识别（界面显示原文） |

## 缺陷单的形状

```markdown
---
id: F0001
title: 一句话说清问题
status: pending
created: 2026-09-29
receipt:
sent_at:
---

## 现象

看板哪个视图、哪一块、显示成了什么样。

## 期望

应该显示成什么样。

## 最小复现

合成的最小片段。自己编名称和内容，能单独复现问题。

## 疑似源码位置

GitHub 链接，尽量带行号。

## 建议改法

文字说明，或一段 diff 文本。只写在这里，不落到看板仓库。

## 临时绕法

工作空间里改了哪些文件、怎么改的；看板修好后要撤掉哪些。

## 发送记录
```

## 贡献单的形状

```markdown
---
id: F0005
title: 去 AI 味规则：一句话说清这条改进
kind: contribution
status: pending
created: 2026-09-30
receipt:
sent_at:
---

## 贡献了什么

一句话，再标类型：技能文案 / 去味规则 / 脚本修复 / 目录说明。

## 为什么能推广

换一个项目这条还成立的理由。只对本项目成立的，不是贡献（见下文）。

## 合成示例

反例、正例或复现片段，全部自己编。

## 涉及的模板文件

模板里的相对路径（看板仓库 `templates/pm-aispace/` 下），如 `.claude/skills/pm-deai-writing/rules/rules.md`。

## 改动内容

diff，或新增部分的全文。已脱敏。

## 实例里的对应

本地编号和版本，方便回执对上，如「本地规则 R012（规则库 v2）」。

## 发送记录
```

一个示例（全部是合成内容）：

```markdown
## 贡献了什么

去味规则：「首先……其次……最后……」三段式开头，改成直接说事。类型：去味规则。

## 为什么能推广

这是生成式写作的通病，和行业、客户无关；三个不同项目的交付稿批注里都出现过。

## 合成示例

- 反例：首先，系统需要支持数据接入；其次，需要支持告警；最后，需要支持报表。
- 正例：系统要接数据、报告警、出报表。

## 涉及的模板文件

.claude/skills/pm-deai-writing/rules/rules.md

## 改动内容

（按规则库格式写的整条规则，含短名、判据、反例、正例）

## 实例里的对应

本地规则 R012（规则库 v2）
```

### 什么算可推广

判据只有一条：**换一个项目，这条还成立吗？**

- 算：去 AI 味规则的新增或修改；技能里补一条对谁都适用的说明；模板脚本的缺陷修复。
- 不算：本项目的原型工程在哪、客户的术语表、某个现场系统的特殊字段。
  这些写进工作空间根的 `AGENTS.local.md` 或实例自己的文件，不写贡献单。

### 回执回来以后

用户转来看板那边的回执时，照样**只改 `status` 和 `receipt`**：收下写 `fixed`，`receipt` 记模板里的位置和提交号；不收写 `wontfix` 和理由。
规则类的贡献被收下后，另外在本地那条规则里补一行 `上游：模板 R<编号>`，按 `pm-deai-writing` 的「规则库怎么改」升一个版本
（CHANGELOG 来源写这份贡献单的编号）。本地规则的编号和判据不改。

## 两种单子都要有的

各自的内容节和「## 发送记录」都要在。缺了「## 发送记录」，看板认不出结构，用户点「我已发出」会得到 409，不会替你把这一节补上。

`sent_at` 和发送记录里的时间是看板服务所在机器的本地时间，形如 `2026-09-29 14:30`。
每发一次追加一条，旧的留下：

```markdown
### 2026-09-29 14:30 已发送至 aispace_kanban@163.com
```

## 最小复现、合成示例、改动内容必须是合成的或已脱敏

不贴工作空间里的真实资料、客户名称、截图、本机路径。
规则类贡献的反例如果来自真实批注，改写成合成句子，搜不到原句里的专有名词。
这份单子会从看板预览进邮件，也可能被带进公开仓库。发之前再看一遍。

## 旧目录

早先反馈单放在工作空间根的 `.kanban-feedback/`。看板只数那里有几份 `.md`，不读内容，也不移动。
迁法写在工作空间 `AGENTS.md` 的「看板显示不对时」。
