## Why

不做的话,批注这件事有两个断点。

**第一个断点:批注读不到。** 归档后的批注批次现在写在 `~/.pmwork/dashboard/note-history/` ——
看板自己的缓存目录(`src/server/note-history.mjs` 的注释写得很直接:「不碰工作空间」)。
当时这是正确的取舍(不用动只读红线),代价是**工作空间里的 AI 读不到批注**,
批注也不跟着工作空间走:换台机器、重装、换人接手就全丢,git 同步不经过它。

**第二个断点:批注没有闭环。** 批注的本来目的是「让 AI 去改正文」,
但现行 `preview-annotation` 的两条要求合起来是「文档一变就整批清掉」:

> MUST 把这一批归档,MUST 清掉页面上的标记点与高亮,**不论这次改动是否覆盖了全部批注**

> 系统 MUST NOT 尝试把旧批注重新贴回被改写后的文档

于是发 10 条给 AI、它改了 6 条,文档一变 10 条一起归档清空 —— **剩下 4 条没人知道**。
现在只有「改动即视为处理完」,没有逐条的状态返回。

## What Changes

- **批注历史搬进工作空间。** 落点改成 `output/records/notes/I<编号>.md`,
  挂在 `output-item-record` 的记录上,按产出物聚成一份(不按批次拆文件,否则文件数成倍膨胀)。
  搬完之后工作空间的 AI 读得到批注,批注跟着 git 和机器走。
- **每条批注带状态**:`pending`(待处理)/ `adopted`(已采纳)/ `rejected`(未采纳,带原因)/
  `unclear`(待确认)。发给 AI 执行后由 **agent 回写**状态,而不是靠文档改动推断。
- **归档不再是整批一刀切。** 文档被改动时,未回写状态的批注 MUST 保留为 `pending` 并说明,
  不再「不论是否覆盖全部批注」一律清空。
- **提示词里带回写指令。** 复制给 agent 的提示词要包含批注文件路径与回写格式,
  否则 agent 不知道自己该在哪里交代结果。
- **存量批注迁移**:按记录的 `target` 反查搬运,没命中的一条不删,缓存目录作只读回退源。

**依赖 `output-item-record`**:批注挂在它的记录上、用它的编号、沿用它的人写区/AI 写区分区。
它没落地之前本 change 无处挂载。

## Capabilities

### New Capabilities

- `annotation-status-loop`: 批注的逐条状态机、agent 回写的契约与格式、
  提示词里要带什么才能让 agent 交代结果、未回写批注的保留规则。

### Modified Capabilities

- `preview-annotation`: 成套修改。
  「当前批注在浏览器本地,历史落看板缓存目录」—— 落点改成工作空间(有记录时),
  Scenario「归档不写工作空间」不再成立,非环回监听时归档要 403
  (原先写缓存目录不受 `allowMutations` 约束)。
  「文档被改动后当前批注归档并清掉标记」—— 不再整批一刀切,
  未回写状态的批注保留;流水文件缺失(404)时不清标记也不清批注。
  「把一个批注批次组装成可直接粘贴的提示词」—— 提示词要加批注文件路径与回写格式。
  「用户 MUST 能清空该文档的历史」这一句要收窄:
  **已经写进工作空间的批次不能从看板清空** —— 流水只追加,
  删除由用户自己在文件系统里做(与 `capture` 那条例外第 ⑤ 条同一口径)。

## Impact

| 平面 | 影响 |
| --- | --- |
| 服务端 `src/server/**` | `note-history.mjs` 的落点迁移与双源回退读取;批注状态的写入与校验 |
| 前端 `src/app/**` | 批注面板显示逐条状态;`hooks/useNoteHistory.ts` 换数据源;提示词组装加回写指令 |
| 契约 `src/app/lib/api.ts` | **动**。`NoteHistoryBatch` 形状随落点与状态字段调整 |
| CLI `bin/cli.mjs` | 不动 |
| `templates/` | **动**。批注文件格式进 `output/records/README.md`;技能要会读批注、按格式回写状态;迁移脚本 |

**依赖**:不引入新依赖。

### 放宽只读红线(已拍板 2026-09-22:同意)

批注批次搬进工作空间是**服务端直写**,与 `output-item-record` 的状态写入同形,
但它的特征不同:**体量大**(一批十几条,每条带选中原文)、**频率低**(一次评审攒一批)。
按 `writeQuestion` 那条例外的立项理由(高频小写入、起进程会让交互变钝),
它本该走 `spawn` 脚本。

**它能搭同一条例外的唯一理由是:它现在已经是服务端直写**
(`note-history.mjs` 写看板缓存目录),搬进工作空间等于同一个动作换落点,
不是新增一条写入通道。

**已拍板**:同意批注批次搭第六条窄例外(与状态写入同一条),不拆成 `spawn` 脚本。
但它是这条例外里**体量最大**的一笔,spec 要把「只追加、不改写、不删除」写死,
不要让它成为将来往工作空间写别的东西的先例。

另外 agent 回写批注状态这件事**不需要**看板的任何权限:那是用户自己在终端里跑的 agent,
本来就不归看板管。看板只负责把回写格式写进提示词。
