# output/ — 阶段三：产出

所有分析结论和交付文档都落在这里。`input/` 是别人给你的，`output/` 是你交出去的。

## 三个子目录

### `analysis/` — 想清楚的过程

给自己和 AI 看的中间产物，不对外发。典型内容：

- `现状基线.md` — 接手时项目到底是什么状态（`pm-project-handover` 产出）
- `需求拆解.md` — 按模块拆开的需求条目、优先级、验收标准（`pm-requirement-analysis` 产出）
- `questions/` — **澄清问题清单，接手阶段最有价值的产物之一**。一问一文件，见下
- `干系人.md` — 谁能拍板、谁提需求、谁验收

建议加日期前缀便于排序：`2026-07-30-计费模块需求拆解.md`。

`questions/` 值得单独说：接手项目时资料一定不全，
把「资料里查不到、需要向对方确认」的问题攒成一份清单，比硬猜着填满文档有用得多。
它直接就是你跟对方团队第一次对齐会议的议程。

**为什么是一问一文件，不是一张表。** 早先这里是单份 `open-questions.md` 的 markdown 表格。
九个技能往里追加，没有一个负责取出，两个月就长成「两百多条、一半标『高』、
平均 200 字挤在一个单元格里」，最后整份被放弃。改成一问一文件之后：
条目长度由 front-matter 的扁平结构管住、排序轴从自我评估的优先级换成客观的
「阻塞哪个在途交付物」、每条都有「被回答」之外的消解出路。

字段契约在 [`analysis/questions/README.md`](analysis/questions/README.md)，
落问题和取问题都走 `pm-open-questions` 技能。旧工作空间要迁移跑
`python3 scripts/migrate_questions.py`（默认预演，不落盘）。

### `docs/` — 交付给别人的文档

PRD、需求规格说明书、评审材料、验收标准。用 `pm-prd-writing` 生成，格式规范、能直接发出去。

一份文档一个文件，文件名就是文档名，不要 `v2_final_最终版` 这种后缀——版本交给 git。

### `decisions/` — 决策记录

一个决策一个文件，`0001-短标题.md` 顺序编号，**只追加不改历史**。

```markdown
# 0001-计费口径按自然月而非 30 天

- 日期：2026-07-30
- 状态：已确认 | 待确认 | 已推翻（被 0007 取代）
- 决策：计费周期按自然月对齐，跨月订单按自然月切分。
- 背景：原系统按 30 天滚动，与财务对账口径不一致（来源：input/converted/财务对账说明.md）。
- 代价：历史订单需要迁移，影响约 2 万条数据。
- 谁拍的：王××（财务）+ 李××（技术负责人），2026-07-30 对齐会。
```

为什么值得单独建目录：接手项目三个月后，一定会有人问「这里为什么这么设计」。
没有决策记录时答案只在某个人脑子里，而那个人可能已经不在项目上了。
被推翻的决策不要删，把 `状态` 改成已推翻并指向新决策——推翻的过程本身是重要信息。
