# 两份清单的交叉比对与核对件

PM 接手项目时反复会遇到同一件事：**甲方给一份清单，我方有一份清单，两份对不上。**
测点表、接口清单、指标字典、需求条目、字段说明——形态不同，但要回答的问题都一样：

- 他们列了、我们没有的，是什么？我们做不做？
- 我们有的、他们没列的，是什么？会不会被当成「范围外」跳过？
- 两边都有但描述不一致的，以谁为准？

这个技能把这套动作固化成：**对齐 → 分类归因 → 旁证裁决 → 可回填核对件**。

最终产物是**能直接发出去的**——不是一个内部结论，而是一份对方可以逐条回填的表。
差异清单如果只停在我们这边，对方永远不会主动来解释，缺口就一直挂着。

手写 Markdown 的写法（front-matter 形态、标题层级、文档间链接、哪些语法现在先别用）见工作空间 `AGENTS.md` 的「Markdown 写法」一节，这里不复述。

## 零、先验一件事：这份「新版」真的是新的吗

对方发来「更新后的」文件时，**先确认内容真的变了**，再花时间比对。

```bash
# 转换产物已入库的情况：直接看 git 有没有实质 diff
git diff --stat input/converted/<产物路径>
git diff input/converted/<产物路径>          # 逐行看
```

这一步经常有惊喜：文件指纹变了、`converted_at` 变了，但**内容一个字没改**——
对方只是重新另存了一遍。这时最该做的不是比对，而是回去问「您改的是不是另一份文件」。

把结论写在报告最前面。如果对方以为自己回应了你上次提的缺口、而实际没落到文件里，
这件事比任何差异统计都重要。

## 一、定对齐键：用编码，不要用名称

**名称一定会有字形差异。** 真实案例：甲方表写「芦**蓭**滩」，我方表写「芦**庵**滩」，
按名称匹配会凭空多出一整个站的差异。同类问题还有全角半角括号、`#1` 与 `１＃`、
「一级」与「1级」、有无空格。

所以：**找一个双方都有的稳定编码列**（测点点号、接口编号、需求 ID、字段 code）作为对齐键，
名称只用来给人看。

如果两边编码体系不同，先建映射表再比对，映射表本身也是要向对方确认的产物——
**别在脑子里做模糊匹配然后当成事实**。映射不确定的条目单独列一类，标 `[推断]`。

## 二、解析：先自检列位，别信表头行

甲方的 Excel 极少规整。**在写解析逻辑之前，先让数据告诉你编码在第几列**：

```python
from collections import Counter
import csv, re
rows = list(csv.reader(open(path, encoding="utf-8-sig")))
pos = Counter()
for r in rows:
    hit = [i for i, c in enumerate(r) if re.fullmatch(r"\d{6,}", c.strip())]
    if hit: pos[tuple(hit)] += 1
    else:   print("无编码行:", r[:5])      # 表头、分段标题、小计行
print(pos)   # {(4,): 53} → 编码稳定在第 5 列，不是你以为的第 4 列
```

这条自检值得每次都做。踩过的坑和处理办法见
[`references/解析陷阱.md`](references/解析陷阱.md)——列位偏移、分段标题占用首列、
合并单元格 forward-fill 污染归属列、同一编码在多个 sheet 重复出现。

**解析完先对一次总数**：分 sheet 统计去重编码数，加起来对不对得上全表。
对不上就是解析漏了，别往下走——比对结论全建立在这个数上。

## 三、归一成两份标准清单

把各自解析结果写成**同一套列名**的 CSV，交给脚本。这是「半自动」的分界线：
**不规则解析靠你判断，机械的集合运算和出表交给脚本。**

| 列名 | 必填 | 说明 |
| --- | --- | --- |
| `键` | ✅ | 对齐键（编码）。唯一，重复会被脚本报出来 |
| `名称` | ✅ | 给人看的名称 |
| `分组` | | 电站 / 模块 / 系统 / 责任方，用来做缺失度归因 |
| `类别` | | 测点类型 / 需求类型，用来看缺口集中在哪一类 |
| `属性` | | 要比对的口径，多值用分隔符（如 `实时/小时/日/旬/月`） |
| `属性原文` | | 原始单元格文本，原样带进核对件，便于对方认领 |
| `来源` | | 来自哪个 sheet / 文件 / 章节，方便对方定位 |
| `可比` | | 填 `否` 表示这条两边属性不在同一坐标系上，脚本排除出冲突判定并单独计数 |

`可比` 是给**结构不同的分区**准备的。真实案例：甲方表有个 sheet 记的是计算公式和数据库表，
根本没有采集频次列；拿它跟我方的「实时/小时/日/旬/月」硬比，会凭空造出两条不存在的冲突。
标成不可比，脚本会在统计里单独报「口径不可比 N 条（已排除）」——**排除了要说出来，别静默丢掉。**

**空白和「明确不提供」要分开。** `属性` 存解析出的多值集合，`属性原文` 存原始文本；
对方留空（该补填）和对方写了 `/`（说不提供、但我方说有）是两类完全不同的问题，
脚本靠 `属性原文` 把它们分成两种冲突类型。

`分组` 和 `类别` 是**归因的抓手**，值得花点力气填对。差异报告里
「缺 505 个点」没人会当回事，「缺的 505 个点里 229 个是闸门开度、88 个是机组状态，
这两类是防汛泄洪判断的直接输入」才会有人接。

分组名尽量取自**权威字典**（标准化表的 `sta_name` 之类），其次按名称前缀投票，
最后才用原表的分组列——原表那一列常被合并单元格填错（见解析陷阱）。

## 四、旁证：让现场数据来裁决

两份清单打架时，**第三方证据比任何一方的自述都有力**。

如果项目里已经有现场实测数据（`pm-field-data` 建的库），把「实际有数的键」导出来当旁证：

```bash
sqlite3 -csv input/converted/现场数据/SplittingObject/<数据集>/实测数据.sqlite \
  "SELECT 测点ID AS 键, '有' AS 旁证, '实时库' AS 旁证明细 FROM 测点;" > /tmp/旁证.csv
```

多个数据集就各查一遍再合并（同一个键在哪几个库里有数，合并成 `实时库/日/月` 这样）。

旁证能把定性讨论变成定量结论。真实案例里最有说服力的两句都来自旁证：

- 「甲方列了、我方没接入的 505 个点，现场实测数据里**一条都没有**」——
  说明这不是接口没配通，是采集侧就没有。
- 「甲方标『不提供』的 55 个点，现场**确实在出数**」——
  说明甲方那份口径表过期了。

**旁证要写清楚口径边界**：导出窗口内出现过，不等于长期稳定采集，更不等于数据质量合格。
这句话必须写进核对件，否则对方会拿它当验收依据。

## 五、跑脚本出产物

```bash
python3 skills/pm-list-diff/scripts/listdiff.py \
  --a 归一后的甲方清单.csv --a-name "甲方《数据来源》表" \
  --b 归一后的我方清单.csv --b-name "我方接入点表" \
  --evidence 旁证.csv --evidence-name "现场实测" \
  --attr-sep "/" \
  --title "水调系统《数据来源》表 · 测点核对件" \
  --project "XX 项目｜2026-08-25" \
  --notes 核对说明补充.md \
  --out-xlsx  output/docs/<日期>-<主题>核对件.xlsx \
  --out-csv   output/analysis/<日期>-<主题>差异明细.csv
```

脚本负责：三集合运算、按分组算缺失度、按属性算冲突类型、逐点明细 CSV、
以及 4 个 sheet 的核对件 xlsx（核对说明 + 三张表，带回填列、冻结窗格、筛选）。

**`--notes` 是项目特定的话**：优先确认哪几件事、有没有发错版本、有没有整块没填的 sheet。
脚本把数字填准，你把话说清楚——两边不要互相代劳。

`--dry-run` 只打印统计不出文件，用来先看差异分布再决定怎么分类归因。
其余参数（列名映射、回填列自定义）见 `--help`。

## 六、产物落点

| 产物 | 落点 | 给谁看 |
| --- | --- | --- |
| 比对分析报告 `.md` | `output/analysis/<日期>-<主题>比对.md` | 内部：结论、归因、建议动作 |
| 逐点差异明细 `.csv` | `output/analysis/<日期>-<主题>差异明细.csv` | 内部：全量可筛可查 |
| **核对件 `.xlsx`** | `output/docs/<日期>-<主题>核对件.xlsx` | **对外：对方回填** |
| 核对件说明 `.md` | `output/docs/<日期>-<主题>核对件说明.md` | **对外：可直接当邮件正文** |
| 待确认问题 | 一问一文件落 `output/questions/`（旧工作空间才追加 `open-questions.md`） | 内部：编号接着往下编，见下文 |

分析报告的骨架：

```markdown
# <主题>比对（日期）
> 比对对象：甲方口径 / 我方口径 / 旁证来源，各自的产物路径

## 0. 先说一句：这版和上一版有没有实质变化
## 1. 总量对账          三方数量表 + 三集合关系
## 2. 差异一：仅甲方有   按类别 + 按分组，点出业务含义
## 3. 差异二：仅我方有   整组漏列 / 近乎整组 / 零星，标出现场有数的
## 4. 差异三：口径冲突   按冲突类型分，说清是不是双向矛盾
## 5. 清单本身的质量问题 没填的 sheet、字形差异、结构不一致的分区
## 6. 结论与建议动作     每条差异对应一个可执行动作和责任方
```

**每条结论都要能指回来源**，推断标 `[推断]`。这是工作空间的硬要求，比对报告尤其容易违反——
「这 317 个点是防汛判断的直接输入」如果资料里没写，就是你的推断，要标出来。

## 七、核对件的三条纪律

1. **左侧数据列锁死，右侧回填列留白。** 在说明里明确写「其余列请勿改动，编码是唯一对齐依据」。
   对方一旦改了编码列，回传的表就对不回来了。
2. **回填列要能直接回答问题，不要开放式提问。** 「该点实际情况」比「备注」有用得多，
   最好把可选项写进说明（如：集控侧有采集未上传 / 现场未采集 / 已废弃）。
3. **口径声明写在核对说明里，不要藏在末尾。** 旁证的统计窗口、类别是怎么归的、
   分组名从哪来——对方看不到这些就会误读，误读之后的返工成本比写清楚高得多。

## 八、发现未决问题怎么落

**走 [`pm-open-questions`](../pm-open-questions/SKILL.md)，不要自己发明格式。**
先看一眼 `output/`：

- 有 `output/questions/` 目录 → **一问一文件**，新建 `output/questions/Q<四位编号>.md`（编号取当前最大加一；**目录空不等于从 Q0001 起**，先查 git 历史用过的最大编号）
- 只有 `output/analysis/open-questions.md` → 旧工作空间，照旧往表格里追加，**不要擅自迁移结构**

新结构下每条必须填 `source`（触发这条问题的文档路径）与 `context`
（触发时在做什么，一句话）—— 溯源锚点挂在**条目**上，不挂在分节上。
`blocks` 填它阻塞的在途交付物，判断不了就写 `backlog`，不要瞎填。
`evidence` 与 `ai_*` 刚提问时留空；**查不到依据只能写 `我方推断`，且不能置 `answered`**。

**双通道：正文归正文，问题归问题。** 分析结论写进文档，延伸出的未决问题写进问题文件，
**两边不许互串** —— 文档里不再放「待确认问题」表格（要提就写一句「见 `questions/Q0134`」），
问题条目里也不抄分析正文。同一条问题两处存在，很快就会对不上。

## 九、数字改了要一路改到底

比对做到一半发现解析有误、数字要修正，这是常态（列位看错、多算了一个 sheet）。
**修正后要把所有已产出的文件一起改**：分析报告、明细 CSV、核对件 xlsx、
核对件说明、以及问题文件里的问题描述。

漏改一处，对外发出去的数字和内部报告对不上，比一开始就算错更糟。
改完复述一遍改了哪几个数、为什么改——用户需要知道哪些结论动过。
