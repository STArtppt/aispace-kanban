# 甲方清单的解析陷阱

甲方的 Excel 是人手工维护出来的，不是系统导出的。下面每一条都是真实踩过的坑，
**代价是差异数字算错、已经发出去的报告要返工**。

比对结论的可信度全建立在解析正确上，所以解析完先做第四节的自检，再往下走。

---

## 1. 同一份文件里，不同 sheet 的列位不一样

最贵的一个坑。一份 xlsx 的 11 个 sheet 里，10 个是这样：

```
电站 | 测点名称 | 测点点号 | 实时 | 小时 | 日 | 旬 | 月      ← 编码在第 3 列
```

第 11 个 sheet（`集控中心水务计算`）却是这样：

```
实时水务计算 | 分中心 | 电站 | 测点名称 | 测点点号 | 公式 | 数据库表   ← 编码在第 5 列
```

**首列被拿去放分段标题了**，整体右移一位。按第 3 列取编码，这个 sheet 一条都取不到——
静默丢掉 5 个编码，总数从 1,538 变成 1,533，三集合的每个数字都跟着错。

**处理**：不要用一套硬编码列位跑全表。逐 sheet 用第四节的自检定位编码列，
差异大的 sheet 单独写解析分支，并在解析结果里记下它来自哪个 sheet。

## 2. 分段标题混在数据行里

接上条。`集控中心水务计算` 用首列的「实时水务计算 / 小时水务计算 / 日水务计算」
把表切成三段，但**这些标题不是独占一行**——它和该段第一条数据挤在同一行：

```python
rows[0]  = ['实时水务计算', '分中心', '电站', '测点名称', '测点点号', '公式', '数据库表']
rows[9]  = ['小时水务计算', '沙溪流域', '安砂', '安砂全厂出力(含银河)', '1330412400', ...]
```

`rows[0]` 是标题 + 表头，`rows[9]` 是标题 + 数据。写成
`if row[0].endswith("水务计算"): continue` 就会连着数据一起丢掉。

**处理**：标题列用 forward-fill 记住当前分段，**但不要因为首列有值就跳过整行**——
先看这一行有没有编码，有就当数据行处理。

## 3. 合并单元格 forward-fill 会污染归属列

Excel 里合并的「电站」列，导出成 CSV 后只有首行有值，后续行为空。
用 forward-fill 补齐是对的，但要小心**填过头**：

```
池潭 | 池潭坝上水位   | 1330510001     ← 电站 = 池潭
     | 芦蓭滩#1机组出力 | 1330542001    ← forward-fill 填成「池潭」，但这是芦庵滩的点
```

`芦庵滩`、`金溪` 是挂在「池潭」sheet 下的独立电站，合并单元格没覆盖到它们。
结果对外核对件里「芦庵滩全厂出力」的电站列写着「池潭」，发出去会让对方困惑。

**处理**：归属列（分组）的取值优先级——

1. **权威字典**：标准化表 / 主数据表里的 `sta_name`、`module`，最可信
2. **名称前缀投票**：同一编码前缀组内，按条目名称前缀取众数
3. **原表的分组列（forward-fill 结果）**：最后兜底

pm-list-diff 的归一步骤就是干这个的：把三层来源收敛成一个 `分组` 列再交给脚本。

## 4. 编码列位自检（每次都做）

不要读表头猜列位，让数据自己说：

```python
from collections import Counter
import csv, re

def probe(path, pattern=r"\d{6,}"):
    rows = list(csv.reader(open(path, encoding="utf-8-sig")))
    pos, noise = Counter(), []
    for i, r in enumerate(rows, 1):
        hit = [j for j, c in enumerate(r) if re.fullmatch(pattern, c.strip())]
        if hit:
            pos[tuple(hit)] += 1
        else:
            noise.append((i, r[:5]))
    print(f"{path}\n  编码列位分布: {dict(pos)}\n  无编码行 {len(noise)} 条:")
    for i, r in noise[:6]:
        print(f"    行{i}: {r}")
```

看两件事：

- **列位分布只有一项** → 列位稳定，放心用。**有多项** → 表内有结构断层，往上翻第 1、2 条。
- **无编码行** → 应该只有表头、分段标题、小计行。如果数量可疑，说明编码格式有变体
  （前后空格、全角数字、`'1330410001` 这种文本前导撇号、编码里带短横线），
  放宽正则再跑一次。

## 5. 解析完先对总数

分 sheet 统计去重编码数，加起来跟全表去重数对比：

```python
per_sheet = {name: len(codes) for name, codes in parsed.items()}
union = len(set().union(*parsed.values()))
print(per_sheet, "分表合计(含重复)", sum(per_sheet.values()), "去重并集", union)
```

**跨 sheet 重复是正常的**（同一个点在流域表和汇总表都出现），但要知道重了多少、重在哪。
真实案例：33 个编码出现在汇总 sheet，其中 5 个是该 sheet 独有——
这 5 个恰好是漏解析时最先丢掉的那批。

## 6. 名称字形差异

对齐一律用编码，就是因为这个：

| 差异类型 | 实例 |
| --- | --- |
| 形近字 | 芦**蓭**滩 / 芦**庵**滩 |
| 全角半角 | `#1机组` / `＃1机组` / `1#机组` |
| 中英标点 | `古田（一级）` / `古田(一级)` |
| 数字写法 | `古田一级` / `古田1级` |
| 空格 | `棉花滩 坝上水位` / `棉花滩坝上水位` |

**这些差异本身是产出**，不是噪音——写进核对件，问对方哪个是正式名称。
不然下次做按名称的自动关联还会再踩一次。

## 7. 「新版」可能不是新的

对方发来「更新后的文件」，先验内容有没有真的变：

```bash
git diff --stat input/converted/<产物路径>       # 有没有实质 diff
git diff input/converted/<产物路径>              # 变在哪
```

真实案例：sha256 变了、`converted_at` 变了，逐字节比对下来**11 个 sheet 只差一个尾随空单元格**——
对方只是重新另存了一遍。如果对方以为自己回应了上一轮的缺口，这件事得先说清楚，
比任何差异统计都重要。

## 8. 空白和「明确不提供」是两回事

属性列里，**空白**（没填）和 **`/`、`—`、`N/A`**（填了，表示不提供）含义完全不同：

- 空白 → 请对方**补填**
- 标了「不提供」而我方说有 → **口径矛盾**，得当面定权威版本

真实案例里这两类分别是 67 条和 55 条，对应的追问方式完全不同，混成一类就没法行动。

**处理**：归一时把 `属性` 列（解析出的多值集合）和 `属性原文` 列（原始单元格文本）
都填上。脚本用前者算集合、用后者分冲突类型，就能把两者分开。

顺带一提：整个 sheet 大面积空白值得单独报出来。真实案例里某个 sheet 的 138 行里
136 行属性列全空——这不是「138 条口径冲突」，是「这张表没填」，结论完全不同。
