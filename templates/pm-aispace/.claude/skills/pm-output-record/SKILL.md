# 产出物记录的建立与维护

`output/` 下每份产出物都有生命周期：一份分析会被后续文档吸收或者过时、
一份交付文档发出去之后会收到反馈、一条决策会被推翻。
**但文件系统只记得修改时间** —— 看板和你都看不出一份产出物现在还作不作数。

`output/records/` 就是补这个缺口的：一份产出物一份记录，记录里有状态、有状态变更的流水。
记录是**我方视角的私有元数据**，旁挂在产出物边上 ——
产出物文件本身不因为建记录而改变一个字节（`docs/` 是要发出去的，YAML 头对收件人是噪音）。

手写 Markdown 的写法见工作空间 `AGENTS.md` 的「Markdown 写法」一节，这里不复述。
**字段契约的唯一事实源是 [`output/records/README.md`](../../../output/records/README.md)**，
下面只是够你干活的摘要，有出入按那份走。

## 先认工作空间的形态

| 看到什么 | 怎么做 |
| --- | --- |
| 有 `output/records/` 目录 | 照本技能往下做 |
| 没有这个目录（旧工作空间） | 先问用户要不要开始用记录。**用户不要就别擅自建** —— 建了就等于要求以后每份产出物都配一份 |
| 有目录、但 `decisions/` 里的存量决策没有记录 | 提议跑一次 `python3 scripts/migrate_decisions.py`（默认预演），见最后一节 |

## 四件事

### 一 · 建一份记录

**时机：你刚产出一份 `analysis/` / `docs/` / `decisions/` 文件，同一轮里顺手建。**
不要攒着回头补 —— 补的时候状态和当时的判断都已经记不清了。

编号：`I<四位编号>`，取当前最大编号加一。
**目录为空不等于从 `I0001` 开始** —— 整批归档之后目录就是空的，
从头编号会让此前所有外部引用指向一条内容无关的新记录，那比悬空引用危险，
因为它看起来完全正常。空目录先查历史：

```bash
git log --all --name-only --pretty=format: -- 'output/records' | grep -o 'I[0-9]\{4\}' | sort -u | tail -1
```

查不到（真的是新工作空间）才从 `I0001` 开始。

```markdown
---
id: I0007                 # 必填，与文件名一致，四位补零
kind: docs                # 必填。analysis / docs / decisions，它决定 status 的合法取值
title: SC-01 交底包需求规格说明书   # 必填。一句话说清这份是什么，清单只显示它
target: output/docs/SC-01交底包需求规格说明书.md   # 必填。工作空间相对路径，必须落在 kind 对应的子目录下
status: draft             # 必填。见下面三套状态机；新建的分析写 drafting，文档写 draft，决策写 pending
created: 2026-09-22       # 必填
status_changed: 2026-09-22
updated: 2026-09-22
resolved_by:              # 人写区。进终态时才填
---

## 这份产出物是什么

一两段说清它覆盖什么、给谁看、依据哪些资料。

## 状态流水

### 2026-09-22 · draft

建立记录，初稿完成待内部评审。
```

`title` 不是文件名的复述 —— 文件名说「叫什么」，`title` 说「是什么」。

### 二 · 按 `kind` 选状态机

**三类不共用一套状态。** 分析中间产物不存在「发给对方」，决策不存在「待修订」——
硬套一套会让每类都带着两三个永远用不上的状态。

| `kind` | 状态 | 终态要求 |
| --- | --- | --- |
| `analysis` | `drafting` → `absorbed` / `stale` | `absorbed` 必须填 `resolved_by`（被哪份吸收） |
| `docs` | `draft` → `delivered` → `revising` → `final` / `superseded` | `superseded` 必须填 `resolved_by`（被哪个编号取代） |
| `decisions` | `pending` → `confirmed` → `overturned` | `overturned` 必须填 `resolved_by`（被哪条推翻） |

三套都**没有「已归档」** —— 归档改变的是文件位置，不是产出物的状态。

`docs` 的「发出去很久没回音」不是一个状态：它仍然是 `delivered`，
由 `status_changed` 与当天的差值表达。状态不表达时间的流逝。

### 三 · 维护 AI 写区

你写的是 `target`、`updated`、以及正文除「## 状态流水」以外的一切。
**`status` / `resolved_by` / `status_changed` 与「## 状态流水」是人写区** ——
人在看板上改，你不要改。看板服务端对载荷里带 AI 写区字段的请求一律 400，
反过来你也不要替人置位状态（看板改不了 `target`，你改不了 `status`，这就是并发方案本身）。

唯一的例外是你在工作空间里自己判断出来的状态变更 —— 比如你刚把一份分析的内容
整段吸收进一份 PRD：这时**先改记录的 `status` 为 `absorbed` 并追加一条流水**，
在同一轮里告诉用户你改了哪一条。不要静默改。

**产出物改名或移动时跟进 `target`。** 只有你能看到文件系统，
看板只能标「指向丢失」。做法：

```bash
grep -rl "旧的相对路径" output/records/
```

改 `target`，正文不动，并把 `updated` 写成当天。
**不要因为产出物改名就改编号或建新记录** —— 编号是外部引用的锚点。

### 四 · 状态流水怎么写

每次状态变更在「## 状态流水」下**追加**一条 `###` 子节，标题是 `日期 · 状态值`，
正文是一句话级的说明（为什么变成这个状态）。

- **只追加，不改写已有条目。** 流水是历史，改历史等于把判断过程抹掉。
- front-matter 的 `status` 必须等于流水**最后一条**的状态值。
- 长篇内容（对方完整的评审意见、逐条修订清单）写进正文别处，不要塞进流水条目里。

## 体检

```bash
python3 scripts/check_markdown.py
```

它会报：`id` 与文件名不符、`kind` 不在三值内、`status` 不属于该 `kind` 的状态机、
终态缺 `resolved_by`、`status` 与流水末条不一致、`target` 与 `kind` 不匹配或指向不存在的文件。
**报出来的不一致不要替它遮掩**，逐条看一遍再改 —— 这种不一致只会来自手工编辑。

## 给存量决策补记录

存量 `output/decisions/` 的状态写在正文 bullet（`- 状态：已确认 | 待确认 | 已推翻（被 0007 取代）`），
解析器读不到它。迁移脚本为每条决策建一份记录、把状态填进 front-matter：

```bash
python3 scripts/migrate_decisions.py            # 预演，不落盘
python3 scripts/migrate_decisions.py --write    # 确认后落盘
```

- **决策正文里那行 bullet 不删** —— 它是给人读的，删了反而丢信息。两处都留着。
- 正文里读不出状态、或写法不认识的，脚本标成**待人工确认**（`status: pending` + 流水里写明），
  不猜一个状态填进去。这些条目要人过一遍。
- 只处理 `decisions/`。`analysis/` 与 `docs/` 的存量产出物没有可读的状态来源，
  要补记录就一份份建，状态由用户判断。

## 不要做的事

- **不要往产出物文件里加状态字段。** 记录是旁挂的，单向反链；
  `docs/` 加了 YAML 头就等于给收件人塞噪音。
- **不要删记录、不要改记录编号、不要复用编号。** 进终态的记录保留文件。
- **不要替人改 `status` 之外的人写区字段**（`resolved_by` / `status_changed` 同理），
  除了上面说的那个例外，且改了要当场说。
- **不要自动推导 `absorbed`。** 「这份分析被某份文档引用了」不等于「被吸收了」——
  那需要判断，不是字符串匹配能定的。推错一条就是在骗人。
