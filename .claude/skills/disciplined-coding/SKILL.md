# 克制式编码(Disciplined Coding)

> 上游来源:[multica-ai/andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills) ——
> 基于 Andrej Karpathy 对 LLM 编码常见错误(臆测假设、过度工程、擅自改动)的观察。
> 本文件是 aispace-kanban 的本地化改写版。

## 何时使用

- 接到任何「实现 / 修改 / 重构」任务,**写第一行前**。
- 尤其在改 `src/server/**` 时 —— 那里没有类型检查也没有测试,过度改动的代价最高。

## 四原则

**1 · 先想再写**
**说出你的假设**。不确定就问,别默默假设往下写。需求有多种解读时,摆出解读与取舍,
而不是替人拍板。本仓最常见的模糊点:这块数据该由服务端算还是前端算?
新字段旧进程没有时该显示什么?—— 这两个问清了,返工基本消失。

**2 · 简洁优先**
**解决问题的最少代码,不写任何投机性的东西。** 不加没要求的功能、不做过早抽象、
不留"以防万一"的配置项和灵活性。这是个 3000 行的只读看板,不是平台。

**3 · 外科手术式改动**
**只动非动不可的地方,只清理自己造成的脏。**
沿用邻近代码的风格(现有代码风格很一致,照抄它);**不重构没坏的代码**;
不"顺手"改无关文件的格式;不动 `components/ui/**` 的 vendored 快照。
每一行改动都要能直接对应到用户的诉求。

**4 · 目标驱动执行**
**先定义成功标准,循环到验证通过为止。** 把"加个功能"翻成具体可验证的目标:
界面上哪个位置、显示什么、数据从哪来、怎么点出来。收尾交给 [[verification-before-completion]]。

## 本仓特有的克制点

- **不引入新技术栈**:服务端不改成 TypeScript / Express;前端不加状态管理库、不加路由库。
  想加,先问人。
- **不为现有代码补大规模测试**:本仓目前没有测试框架,冒烟就是闸。
- **不"顺手"扩大只读边界**:任何往工作空间写文件的想法都要先问人(红线见 AGENTS.md 第 1 节)。
- **不上彩色**:设计约束是黑白灰 + orange 只给"需要注意",别自己发明配色([[design-tokens]])。

## 见效的样子

diff 里没有多余改动;不因过度工程返工;**动手前**就把模糊点问清了,而不是出错后才发现。

## 与其它纪律的关系

- 本技能管「写之前怎么想 + 写多少」;[[systematic-debugging]] 管「出 bug 怎么查」;
  [[verification-before-completion]] 管「敢不敢说做完了」;[[dashboard-feature-flow]] 管「按什么顺序改」。
- 与 [[project-conventions]] 谈风格时以本地约定为准,本技能只补「克制」这层心法。
