# records/ —— 产出物记录，一份产出物一个记录

产出物本身在 `analysis/` `docs/` `decisions/` 里，这个目录放的是**我方视角的私有元数据**：
这份产出物现在处于什么状态、为什么变成这个状态、被谁吸收或取代。
**本文件是记录文件的唯一字段契约**，技能、校验脚本、迁移脚本、看板都以它为准。

## 为什么要有它

不然 `output/` 下三类产出物都只有一个修改时间：
一份分析有没有被后续文档吸收、一份交付文档发出去之后对方说了什么、
一条决策是不是已经被推翻 —— 看板和 AI 都无从知道。
产出物的生命周期断在「文件存在」那一刻，唯一的组织维度只剩时间序，列表只会单调变长。

**为什么记录不写进产出物本身。** `docs/` 是要发出去的，任何我方视角的元数据对收件人都是噪音
（`output/README.md` 已有的立场）；而 `docs/` 的 front-matter 本来就不强制，
加了等于强制。所以记录旁挂，用 `target` 单向反链到产出物 ——
产出物文件**一个字节都不因为建记录而改变**。

**为什么和 `analysis/` 平级、又不进看板的三组列表。** 与 `questions/` 同一条理由：
三类合计的记录数会把「分析中间产物」那份清单整个淹掉，而那份清单是给人扫现状基线、
需求拆解用的。记录有自己的入口（看板 ⌘K 工作台的「产出物」页），不该在文件列表里再占一遍位置。

## 文件布局

```
output/records/
├── README.md        ← 本文件
├── I0001.md
├── I0002.md
└── …
```

- 文件名 `I<四位编号>.md`，编号在一个工作空间内**唯一且只增不复用**。
- 进终态（`absorbed` / `stale` / `final` / `superseded` / `overturned`）的记录**保留文件**,
  不删除、不改名 —— 编号是外部引用的锚点（会议纪要、别的分析文档会写「见 I0007」）。
- 新增时取当前最大编号加一。
- **目录为空不等于从 `I0001` 开始。** 整批随阶段结束归档之后目录就是空的，
  这时从头编号会让此前所有外部引用指向一条内容无关的新记录 —— 那比悬空引用危险，
  因为它看起来完全正常。空目录先查历史用过的最大编号：

  ```bash
  git log --all --name-only --pretty=format: -- 'output/records' | grep -o 'I[0-9]\{4\}' | sort -u | tail -1
  ```

  查不到（真的是新工作空间）才从 `I0001` 开始。
- `decisions/` 自己的 `0001-短标题.md` 文件名序号与记录编号是**两套互不相干的编号**：
  前者是决策在目录里的序号，后者是记录的锚点。记录编号不与它对齐、不复用它。

## front-matter 字段

front-matter **必须是扁平的**：只用 `key: value` 与 `key:` + `  - item` 两种形态，
**不用嵌套对象**。这不只是为了迁就解析器 —— 扁平限制强制 `title` 是一句话、
`target` 是一个路径，**条目长度由结构管住，不靠自觉**。长文一律进正文。
语法子集的唯一事实源是 [AGENTS.md](../../AGENTS.md) 的「Markdown 写法」一节，
本文件只保留记录字段契约。

```markdown
---
id: I0007
kind: docs
title: SC-01 交底包需求规格说明书
target: output/docs/SC-01交底包需求规格说明书.md
status: revising
created: 2026-08-14
status_changed: 2026-09-02
updated: 2026-09-02
resolved_by:
---

## 这份产出物是什么

（由技能填。一两段说清它覆盖什么、给谁看、依据哪些资料。）

## 状态流水

### 2026-08-14 · draft

建立记录，初稿完成待内部评审。

### 2026-09-02 · revising

甲方信息化回了三条意见，主要是测点命名口径，待修订。
```

### 必填

这六个键**必须存在**，缺一个校验脚本就报错。

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `id` | 记录编号 | 必须与文件名一致（`I0007.md` → `I0007`） |
| `kind` | 产出物类别 | `analysis` / `docs` / `decisions` 三者之一，决定 `status` 的合法取值 |
| `title` | **一句话**说清这份产出物是什么 | 清单只显示它；超过 60 字校验脚本会警告 |
| `target` | 产出物的工作空间相对路径 | 必须指向 `kind` 对应的那个子目录下的文件 |
| `status` | 当前状态 | 必须属于该 `kind` 的状态机，见下节 |
| `created` | 记录建立日期 | `YYYY-MM-DD` |

### 可选

| 字段 | 含义 |
| --- | --- |
| `resolved_by` | 被哪个编号吸收 / 取代 / 推翻。进 `absorbed` / `superseded` / `overturned` 时**必填** |
| `status_changed` | 状态最后一次变更日期 `YYYY-MM-DD` |
| `updated` | 记录内容最后一次更新日期 `YYYY-MM-DD` |

### 人写区 —— 看板可写，agent 约定上不写

| 字段 | 取值 |
| --- | --- |
| `status` | 见状态机 |
| `resolved_by` | 一个记录编号（`I0012`）。终态必填 |
| `status_changed` | `YYYY-MM-DD`，看板保存时自动写当天 |
| 正文「## 状态流水」小节 | 每次状态变更追加一条，见下文 |

### AI 写区 —— agent 写，**看板一律不写**

| 字段 | 取值 |
| --- | --- |
| `target` | 产出物路径。**产出物改名或移动时要跟进** —— 只有能看到文件系统的 agent 有依据判断 |
| `updated` | `YYYY-MM-DD` |
| 正文除「## 状态流水」以外的一切 | 自由 markdown |

建立时写定、之后都不改的是 `id` / `kind` / `title` / `created`。

**为什么要分区**：人在看板上改状态、agent 同时在更新正文与 `target`，两者动同一个文件是预期行为。
分区让它们**物理上落在不同字段与不同小节**，不需要锁，比检测冲突再让用户处理更简单也更可靠。
看板服务端会硬拒绝载荷里带 AI 写区字段的请求（400 且不落盘）。

## 三套状态机，按 `kind` 分化

三类产出物**不共用一套状态**。硬套一套会出荒谬状态：分析中间产物不存在「发给对方」，
决策不存在「待修订」—— 每类都会带着两三个永远用不上的状态。
而这正是 `questions/README.md` 那条教训的反面：**状态必须对应分化的后续动作**,
不对应的状态就是噪音。

### `kind: analysis` —— 过程产物，问的是「这份还作数吗」

| `status` | 含义 | 可流转到 |
| --- | --- | --- |
| `drafting` | 在写 | `absorbed`、`stale` |
| `absorbed` | 已被后续产出物吸收，`resolved_by` **必填** | `drafting`（重开） |
| `stale` | 过时，没被用上 | `drafting` |

「这份分析后来发现是错的」不单独立一态 —— 它和「过时没用上」的后续动作一样（都是归档）,
是哪一种由补充说明说清。

### `kind: docs` —— 交付物，问的是「发出去之后怎么了」

| `status` | 含义 | 可流转到 |
| --- | --- | --- |
| `draft` | 草稿，还没发出（含内部评审） | `delivered` |
| `delivered` | 已发出，等对方反馈 | `revising`、`final` |
| `revising` | 收到反馈，待修订 | `delivered`、`final` |
| `final` | 已定稿 | `superseded` |
| `superseded` | 被新版取代，`resolved_by` **必填** | —— |

**「发出去很久没回音」不是一个状态**：它仍然是 `delivered`，由 `status_changed` 与当天的差值表达。
状态不表达时间的流逝，否则每个状态都要派生一个「很久没动的」双胞胎。

### `kind: decisions` —— 决策，问的是「这条还生效吗」

照搬 `output/README.md` 里**已有**的三态约定，不另立一套 ——
只是把它从正文 bullet 提到 front-matter，让解析器读得到。

| `status` | 含义 | 可流转到 |
| --- | --- | --- |
| `pending` | 待确认 | `confirmed`、`overturned` |
| `confirmed` | 已确认 | `overturned` |
| `overturned` | 已推翻，`resolved_by` **必填** | —— |

### 三套都没有「已归档」

归档改变的是**文件位置**，不是产出物的状态。把位置混进状态机，
会让「这份是归档了还是过时了」永远分不清，也让归档功能无处下手。

### 终态必须说清被谁消解

`absorbed` / `superseded` / `overturned` 三个值**必须有 `resolved_by`**：
终态意味着「别看这份了」，不说清该看哪份，外部引用就无处可去。
`stale` 与 `final` 不要求 —— 前者是「没被用上」（没有下一份），后者是「就是它了」。

## 状态流水

每次状态变更在正文「## 状态流水」下**追加**一条 `###` 子节，格式：

```markdown
### 2026-09-02 · revising

甲方信息化回了三条意见，主要是测点命名口径，待修订。
```

- 标题是 `日期 · 状态值`，正文是**一句话级**的补充说明（为什么变成这个状态）。
- **只追加，不改写已有条目** —— 流水是历史，改历史就等于把判断过程抹掉。
- 长篇内容（对方完整的评审意见、逐条修订清单）写进正文别处，由 agent 维护；
  补充说明只放一句话的注解。
- front-matter 的 `status` **必须等于流水最后一条的状态值**。
  两者不一致时**以 `status` 为准**（解析器读它做分组），校验脚本会报告不一致 ——
  这种不一致只会来自手工编辑。

## 记录由技能建立，看板不新建

建记录是 `pm-output-record` 技能的活：技能产出一份文档，顺手建一份记录。
**看板只改已存在的文件** —— 编号不存在一律 404，不新建、不删除、不改名。

这不是能力不足，是那条写入例外里最硬的一条：一旦开了「看板能建文件」的口子，
下一个功能就会照着「反正已经能建了」推广。技能建产出物时顺手建记录，成本是零。

## 状态不自动推导

状态由人在看板上、或 agent 在工作空间里**明确置位**，系统不自动置位任何状态。
`analysis` 的 `absorbed` 理论上能从溯源反链推出来（这份分析被某份 `docs` 引用了）,
但「这份到底算不算被吸收」需要判断，不是字符串匹配能定的 —— 推错一条就是在骗人。

## 记录的正文不喂溯源反链

看板统计「一份资料被几篇产出引用」时**不读记录正文**。
状态流水会抄产出物原文与资料引用，喂进去会把计数顶虚高，
让「转换好了却没人用」这个缺口提示失真。这与 `questions/` 的处理**不同**
（问题正文是喂反链的），差异在看板的扫描代码里注明了理由。

## 校验

```bash
python3 scripts/check_markdown.py            # 记录目录的字段校验并在其中
python3 scripts/check_markdown.py --json     # 给程序用
```

查这些：`id` 与文件名不符、`kind` 不在三值内、`status` 不属于该 `kind` 的状态机、
终态缺 `resolved_by`、`status` 与流水末条不一致、`target` 指向的子目录与 `kind` 不匹配、
front-matter 里出现长文。

## 给存量决策建记录

存量 `output/decisions/` 的状态写在正文 bullet（`- 状态：已确认 | 待确认 | 已推翻（被 0007 取代）`）,
看板的解析器读不到。迁移脚本为每条决策建一份记录，把状态填进 front-matter：

```bash
python3 scripts/migrate_decisions.py            # 预演，不落盘
python3 scripts/migrate_decisions.py --write    # 确认后落盘
```

- **不删决策正文里那行 bullet** —— 它是给人读的，删了反而丢信息。
- 正文里读不出状态、或写法不认识的，标成**待人工确认**，不猜一个状态填进去。
