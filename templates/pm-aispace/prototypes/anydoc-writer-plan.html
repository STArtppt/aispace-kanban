给 anydoc 的文档模型写一个 Markdown 序列化器

目标是把 .docx .odt .rtf .epub 四种格式彻底从 pandoc 上摘下来， 同时不丢图片。做法是复用 anydoc 已经解析好的文档模型，只重写它渲染 Markdown 的那一段—— 解析器一行不碰。

01

要做的到底是哪一段

已有 · anydoc
Reader
吃下 OOXML / ODF / RTF 控制字 / EPUB 容器，处理样式继承、编号定义、WPS 方言。几万行的活。
→
已有 · toDocument()
Document 模型
强类型、已规范化。表格是标准网格，样式已解析成布尔值，图片字节挂在 assets 上。
→
要写 · 本方案
Writer
递归下降 + 字符串拼接。没有 IO、没有格式方言、没有容错。图片落盘后写成 ![](相对路径)。

anydoc 自带的 Writer 在 Rust 里，不导出也不给 hook——包的导出面只有 toDocument（模型，无 writer） 和 toMarkdown（成品字符串，图已丢），中间没有接口。所以只能整段重写，但也仅此一段。

为什么值得做，而不只是省一个 brew install

anydoc 的 Reader 在你的语料上比 pandoc 准。那份 WPS 导出的 PRD 用纯数字 styleId （w:styleId="1"），pandoc 认出 19 个标题，anydoc 认出 20 个而且保住了 Word 的自动编号 （## 3.1 需求列表 vs pandoc 的 ## 需求列表）。 走这条路，摘掉 pandoc 的同时标题结构反而更好。

02

接缝设计：让两条路可以互换

先定 Python 侧的调用契约，再去实现 Writer。契约定得对，将来 Writer 做砸了可以原地换成 pandoc-wasm，ingest.py 一行不动。这是这个方案里最该先想清楚的一件事。 

# scripts/anydoc.py 新增，与现有 to_markdown() 并列
def to_markdown_with_assets(
    src: Path,          # 源文件
    assets_dir: Path,   # 图片落盘目录（绝对路径）
    link_prefix: str,   # 正文里图片链接的前缀，已过 md_link() 转义
) -> str:               # → Markdown 正文（不含 frontmatter）

实现上复用 anydoc.py 里现成的 find_bin() 四级查找链（ANYDOC_BIN → 工作空间 .env → runtime.json → PATH）、_argv() 的 node 解析、 _run() 的 UTF-8 强制。只是 argv 换成跑我们自己的 helper： 

node scripts/anydoc_writer.mjs <src> \
     --anydoc-module <从 find_bin() 推出的 index.js 路径> \
     --assets-dir    <绝对路径> \
     --link-prefix   <转义过的相对前缀>

# stdout = Markdown 正文    stderr = 诊断
# exit 0 成功 / 1 转换失败（映射 anydoc 的 ConvertErrorCode）/ 2 用法错
已验证

helper 不需要自己装 @firecrawl/anydoc。runtime.json 里的 anydocBin 指向 cli.js，同目录的 index.js 就是 API 入口， import(pathToFileURL(...)) 侧载在任意 cwd 下都成功——我实测过了。 看板注入和终端直跑两条路径共用同一个二进制，跟现在的行为完全一致。

为什么图片落盘交给 Writer，而不是把 base64 吐回 Python

那份 PRD 只有 14 张图，转成 data URI 的 Markdown 就是 11.8 MB（我拿 officeparser 实测的）。 走管道回传等于把整份文档的图片在内存里复制两遍。Writer 直接写文件、正文里只留路径， Python 侧沿用 convert_pandoc() 已有的做法数图片个数填进 frontmatter 的 extracted_images。

05

三个硬决策

主干是一下午的机械劳动，真正花时间的是这三处。它们决定产出能不能读， 所以我建议都做成开关，用真实文档两种都跑一遍再定死。

决策 ① 表格跨行列怎么降级 影响 2091 个格子

GFM 表格没有 rowspan / colspan。anydoc 把跨格表达成 covered 槽回指 origin，我们必须选一种拍平方式：把 origin 内容复制进每个被覆盖格， 还是留空，还是整表退回 HTML <table>。

倾向留空（与 pandoc 一致）。复制会让 AI 在做需求分析时把同一条内容统计两遍—— 你那份采购技术规范里 2091 个 covered 格，翻倍的后果是实打实的。 留 --span=fill 开关备用。

决策 ② 复合编号（markerLabel）怎么写 影响 448 处

源文档里 1-a)、（3） 这类编号，GFM 有序列表的 1. 表达不出来。 pandoc 的做法是转义成普通文本（1\. 第一），代价是列表语义整个丢掉。

倾向：有 markerLabel 时整个 list 降级成带缩进的段落序列，label 原样写在行首并转义， 防止被 Markdown 重新解析成列表。没有 label 的列表正常走 - / 1.。

决策 ③ 转义边界划在哪 最容易出隐蔽 bug

正文里裸露的 * _ [ ] < > \、行首的 # - + 和「数字+点」、表格单元格里的 | 和换行（必须转 <br>）。 code 样式内部则反过来——不能转义，要包反引号并处理内容自带反引号的情况。

图片路径里的空格和括号已经有现成解：layout.py 的 md_link() 直接复用，不要重写。

07

验证闸

本仓 verification-before-completion 要求「没有刚跑出来的证据不许下完成结论」， 而且 src/server/** 和转换脚本都没有静态检查。所以验证是脚本化的三方并排，不是看一眼：

指标基线通过条件
抽出图片数pandoc --extract-media必须相等（硬指标）
标题数pandoc 19 / 372 / 502≥ 基线（anydoc Reader 应更准）
表格数pandoc相等
中文完好—无 标?题? 类残缺（officeparser 就死在这）
裸 HTML 残留—<img / <div 计数为 0
看板渲染—重启 pnpm serve，点开产物看图和目录层级

语料固定为 6 份真实 docx（含 WPS 数字 styleId 那份、372 标题那份、502 标题那份）+ 4 个合成件。 对比脚本只打统计不打全文——这也是控制 token 的关键，我在前面的调研里就是这么跑的。

估算依据，不是拍的：

  • 600 行 mjs 输出 ≈ 8.5K 输出 token，但真实成本在迭代不在首稿；
  • 每轮真实文档回归（跑 + 读统计 + 定位）实测 25–40K，前面调研的每一轮我都在这个量级；
  • 预计 5–8 轮迭代，P3 占大头；
  • 已建立的上下文（index.d.ts、ingest.py、layout.py、实测数据）约 60K，每轮复用。
建议口径

按 400K 立预算，600K 划止损线。超过 600K 说明踩到了 anydoc 模型的未知边界， 这时候继续投入的期望收益已经低于直接换 pandoc-wasm——接缝就是为这一刻留的。

折成人工大约 1.5–2 人日；我连续做是 2.5–4 小时的会话。

09

风险与退路

风险后果缓解
表格 span 降级选错 采购规范类文档读起来就废，2091 个格子的数据被读重或读丢 做成开关，真实文档两种都跑，P2 结束前定死
anydoc 是 0.x，模型无语义化保证 升级后 Writer 崩或静默丢内容 Writer 对未知 kind 走 fallback 吐纯文本而非抛错；package.json 里 pin 住版本
渲染质量长期由我们自己扛 这是与 pandoc-wasm 最本质的差别，不可消除 把验证脚本连同语料一起提交，当回归基线用

退路是明确的：anydoc.py 的 to_markdown_with_assets() 签名不变， 函数体换成调 pandoc-wasm 即可，ingest.py 及以上全部无感。 所以第 02 节的接缝要先定，Writer 后写——顺序反了，退路就没了。

调研数据来自本机实测：anydoc 0.2.3、pandoc 3.9（本机）/ 3.10（wasm）、officeparser 7.8.0， 语料为 ~/Desktop/LIFE/working/ 下 6 份真实 docx 与 4 个合成件。
