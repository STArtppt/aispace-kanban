# 需求分析与拆解

阶段二的第二步。产出 `output/analysis/需求拆解.md`（模块多时按模块分文件）。

拆需求最容易滑向两种失败：拆成一堆「系统应支持 XX 管理」这种没法验收的空话，
或者拆得过细变成几百条谁也看不完的清单。判断标准只有一个：
**每一条都能被单独确认「做完了没有」，并且能说出「为谁解决什么问题」。**

手写 Markdown 的写法（front-matter 形态、标题层级、文档间链接、哪些语法现在先别用）见工作空间 `AGENTS.md` 的「Markdown 写法」一节，这里不复述。

产出之后**一并建一份产出物记录**（`kind: analysis`），走 [`pm-output-record`](../pm-output-record/SKILL.md)——没有记录的产出物在看板上只有一个修改时间，看不出还作不作数。

## 输入

先读 `output/analysis/现状基线.md`。没有基线就先走 `pm-project-handover`——
跳过盘点直接拆需求，会把推断当事实拆进条目里，后面全要返工。

再读未决问题（新工作空间在 `output/questions/`，旧的在 `output/analysis/open-questions.md`）。
**被未决问题阻塞的需求不要硬拆**，标记 `⛔ 阻塞于 Q0003` 留空，不要用你的猜测填满它。

拆解过程中新冒出来的问题，按下面这节落盘。

## 拆解粒度

按「用户任务」拆，不按「界面」或「数据表」拆。

- ✅ 「运维人员确认一条告警并记录处理结论」——一个完整任务，能验收
- ❌ 「告警管理模块」——太粗，无法验收
- ❌ 「告警列表页的确认按钮变成灰色」——太细，是实现细节不是需求

一条需求的合理体量：一个人能在一句话里说清它的价值，开发能在几天内做完。
拆完检查一遍：如果某条需求的验收标准写了十条以上，它其实是好几条需求，该再拆。

## 需求条目格式

```markdown
### R-告警-003 确认告警并记录处理结论

- **谁**：变电站运维人员
- **要做什么**：对一条告警标记「已确认」，并填写处理结论
- **为什么**：未确认的告警会持续占据首页，值班交接时分不清哪些已处理（来源：现状基线 §遗留问题）
- **来源**：input/converted/需求规格.md §4.2 ｜ input/converted/告警管理/告警管理.csv（确认状态字段）
- **优先级**：P0（必须有）
- **依赖**：R-权限-001（需要先有角色区分，只有运维角色能确认）
- **验收标准**：
  1. 列表和详情页都能发起确认；确认后状态由「未确认」变为「已确认」
  2. 处理结论必填，长度 1–500 字
  3. 已确认的告警不能再次确认，按钮置灰
  4. 记录确认人和确认时间，在详情页可见
  5. 确认操作留痕，可在审计日志中查到
- **未决**：确认后是否允许撤销？（→ Q7）
```

**验收标准是这份文档最有价值的部分。** 写的时候盯住这些容易漏的地方：

- **边界值**：数量、长度、金额、时间的上下限，超限怎么办
- **异常路径**：网络失败、并发冲突（两人同时确认同一条）、数据不存在
- **状态限制**：什么状态下不允许这个操作，此时界面怎么表现
- **权限**：谁能做、谁不能做，无权限时是隐藏还是置灰
- **留痕**：谁在什么时候做了什么，要不要可查

一条经验：验收标准里出现「等」「相关」「合理」「友好」这些词，就是还没想清楚，重写。

## 优先级

用 MoSCoW，并且**必须写清判断依据**——不写依据的优先级会在评审时被随意推翻。

| 级别 | 含义 | 判断依据 |
| --- | --- | --- |
| P0 必须有 | 没有它这个版本不能上线 | 核心业务流程走不通，或合规硬要求 |
| P1 应该有 | 没有它能上线但体验明显受损 | 有替代手段（人工处理 / 后台改数据） |
| P2 可以有 | 有余力就做 | 提升效率但不阻塞任何流程 |
| P3 本期不做 | 明确排除 | 记进「明确不做」清单，避免范围蔓延 |

P0 占比超过一半时要警惕——通常意味着优先级根本没排，只是把所有需求都标成了重要。
这时回到业务目标去问：哪些是达成目标必需的？答不出来就说明业务目标本身不清楚，
这是比需求排序更根本的问题，要先解决。

**优先级最终由业务方拍板，不是由你决定。** 你的产出是「带依据的建议」，
在文档里明确标注哪些优先级已确认、哪些是待确认的建议值。

## 依赖与冲突

拆完所有条目后专门过一遍，这一步经常被跳过但价值很高：

**依赖**：A 必须在 B 之后做。写成 `依赖：R-xxx`，并检查有没有环——
出现循环依赖说明拆分边界不对，要重新划分。依赖链最长的那条决定了最短工期。

**冲突**：两条需求要求不同的行为。这是接手项目的高发问题，
因为需求来自不同时期、不同人、不同文档。典型形态：

- 同一字段两处规则不同（一处说必填，一处说可选）
- 同一状态两种流转路径
- 权限规则互相矛盾（一处说管理员可见全部，一处说按部门隔离）

**发现冲突不要自己调和。** 把两个说法、各自来源、以及「按哪个做会怎样」写清楚，
落成一条未决问题交给业务方裁决。你私自选一个的代价是：
上线后另一方说「这不是我要的」，而你没有依据。

### 发现未决问题怎么落

**走 [`pm-open-questions`](../pm-open-questions/SKILL.md)，不要自己发明格式。**
先看一眼 `output/`：

- 有 `output/questions/` 目录 → **一问一文件**，新建 `output/questions/Q<四位编号>.md`（编号取当前最大加一；**目录空不等于从 Q0001 起**，先查 git 历史用过的最大编号）
- 只有 `output/analysis/open-questions.md` → 旧工作空间，照旧往表格里追加，**不要擅自迁移结构**

新结构下每条必须填 `source`（触发这条问题的文档路径）与 `context`
（触发时在做什么，一句话）—— 溯源锚点挂在**条目**上，不挂在分节上。
`blocks` 填它阻塞的在途交付物，判断不了就写 `backlog`，不要瞎填。
`evidence` 与 `ai_*` 刚提问时留空；**查不到依据只能写 `我方推断`，且不能置 `answered`**。

**双通道：正文归正文，问题归问题。** 分析结论写进文档，延伸出的未决问题写进问题文件，
**两边不许互串** —— 文档里不再放「待确认问题」表格（要提就写一句「见 `questions/Q0134`」），
问题条目里也不抄分析正文。同一条问题两处存在，很快就会对不上。


## 追溯矩阵

在文档末尾放一张表，回答「每条需求从哪来」和「每份资料被覆盖了没有」：

```markdown
| 需求 ID | 来源资料 | 位置 | 状态 |
| --- | --- | --- | --- |
| R-告警-003 | 需求规格.md | §4.2 | 已确认 |
| R-告警-004 | 会议纪要-0715.md | 第 3 条 | 口述待确认 |
| R-告警-005 | — | — | 新增建议（我提的） |
```

反过来也要检查：**有没有资料里写了但你没拆成需求的内容？**
这是漏需求最主要的来源。逐份资料对一遍，漏的补上，确认不做的记进「明确不做」清单。

我方主动提的新增建议要显式标出来（来源写「—」），
别混在原始需求里——业务方有权知道哪些是他们要的、哪些是你建议的。

## 新增需求的影响评估

项目中途来新需求时，不要直接追加条目，先评估：

1. 与既有需求冲突吗？
2. 有哪些需求依赖它 / 它依赖哪些？
3. 挤掉了哪些原有需求（同等资源下）？
4. 改变了范围边界吗？需要重新确认分期吗？

把这四点的答案给用户，让 TA 有依据去跟业务方谈范围，
而不是默默把需求塞进来最后交不出。这类范围变更定下来后记一条 `output/decisions/`。
