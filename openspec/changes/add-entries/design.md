## Context

**三个入口现在都不在看板上。** 新建工作空间只有一个纯文本路径框;MinerU 的 key 和数据库连接
要用户自己想起来工作空间里有 `pm-env-config` 这个技能,再自己拼一段话发给 AI。
模板那边其实已经把契约定死了 —— `pm-env-config/references/kanban-prompt.md`
写着「这份是给**以后看板「添加」按钮**用的」,连字段表和固定头都冻结了,只差看板这一半。

**大库快照的实测(脱敏后)。** 拿一个 PostgreSQL 兼容库(KingbaseES)做了两轮采集,
连接信息、库名、表名一律不写进这里,只留量:

| 口径 | 单 schema | 白名单放到 5 个 schema |
| --- | --- | --- |
| 表 / 视图 | 366 | 975 |
| 列 | 4 693 | 11 466 |
| 三条 `information_schema` 查询合计 | 0.67 s | 0.97 s |
| `db_ingest.py schema` 端到端 | 1.45 s | 1.30 s |
| 摘要 `_manifest_<源名>.md` | 59 KB / 391 行 | 141 KB / 1000 行 |
| 单表明细文件 | 366 份 / 1.4 MB | 975 份 / 3.8 MB |
| 摘要的 Markdown 解析(Node,去掉 frontmatter) | 35~64 ms | 90~119 ms |

两个源都在的那个工作空间(合计 1 341 张表)扫一次:

- `scanWorkspace` 耗时 **16 ms**,产出 JSON **330 772 字节**;
- 其中单表明细清单(`items[].tables`)占 **325 004 字节 —— 98.3%**;
- 而前端对这个数组只做了一件事:`tables.length`,渲染成一行「N 张表的明细」。

结论很清楚:**采集不是瓶颈,产物形态和扫描载荷才是。** 而且这份载荷不是一次性的 ——
`input/` 一有动静 SSE 就推一次,前端重新拉整份 scan。

**顺带撞到一个静默 bug。** 同一个库,先用 psycopg2 直连能读出 366 张表,
走 `db_ingest.py` 却报「没读到任何表」并把快照写成 0 张。定位到 PG 那三条查询的
`WHERE table_schema = ANY(%s)`:psycopg 3 不带类型地传列表参数时,
KingbaseES 推不出参数类型,**不报错、直接返回 0 行**。加 `::text[]` 显式转型后立刻恢复
366 行;数组字面量写法也正常。这条链路上没有任何东西会喊 —— 日志只会说
「schema 快照已更新(0 张表 / 视图)」。

## Goals / Non-Goals

**Goals:**

- 三件要配的事在看板上都有一个明确的入口,且入口产出的东西**是给 AI 的一段话**,
  不是看板自己动手改工作空间。
- 凭据的经手范围收到最小:输入框 → 剪贴板,不进接口、不进磁盘、不进日志、刷新即丢。
- 表多的库加进来以后,界面不因为快照而变卡;摘要仍然是「一份就能读进 AI 上下文」的东西。
- 每一处新能力都有**退回改动前**的降级路径:选择器起不来能手填,旧服务进程没接口就不显示按钮。

**Non-Goals:**

- 看板直接写 `.env` / 写 `input/sources/*.yaml`。那是 `pm-env-config` 的活,
  也会撞只读红线 —— 本 change 一个字都不往工作空间写。
- 看板连数据库做连通性测试。连通性由 `db_ingest.py list` / `schema` 验证,看板进程不碰库。
- 在看板里浏览整台机器的文件系统。
- 把上千份单表明细合并成几份。先做前面两刀,不够快再说。
- 支持 KingbaseES 以外的国产库,或把 KingbaseES 变成一个独立引擎 —— 它照旧按
  `engine: postgresql` 接,本 change 只是让那条路别静默出错。

## Decisions

### 决策 1:目录选择器走**服务端起系统原生对话框**(已拍板)

**已定,按本节实现。** 新增 `POST /api/pick-directory`,服务端按平台起对话框,拿到用户选的路径回给前端。
命令收在 `platform.mjs`(不变量:三平台差异只写在这一份):

- macOS:`osascript -e 'POSIX path of (choose folder …)'`
- Windows:`powershell -NoProfile -STA` + `System.Windows.Forms.FolderBrowserDialog`
- Linux:`zenity --file-selection --directory`,退而求其次 `kdialog --getexistingdirectory`

**备选 A:浏览器的 `showDirectoryPicker()`。** 不选 —— 它**拿不到绝对路径**,
只给一个目录句柄和目录名。而看板需要的恰恰是那串绝对路径(要存进注册表、要传给
`init_workspace.py`)。`<input webkitdirectory>` 同理,只有相对路径。这条路从根上不通。

**备选 B:服务端出一个「列目录」接口,前端自绘目录树。** 不选 —— 跨平台、无外部依赖是优点,
但它把**整台机器的文件系统变成一个可读接口**,是本仓目前没有的攻击面
(现有的一切读都被 `resolveInside` 圈在工作空间内);而且要在看板里重造一个文件选择器,
UI 工作量远大于收益。真到 Linux 上两个对话框都没有的场景,手工输入本来就还在。

**关键约束:**

- **必须过 `rejectIfRemoteWrite` + `rejectIfForeignOrigin`。** 它虽然不写任何东西,
  但「让服务器那台机器弹一个窗」显然不该由远程访问者触发。非环回一律 403,与写接口同级。
- **一次只允许一个。** 对话框是模态的,请求会挂到用户选完为止。进程里记一个「正在选」的标记,
  第二个请求直接 409 说明「已经开着一个选择框了」,不要弹出两个。
- **要有超时**(建议 120 s)。超时后杀掉子进程并返回「选择框开太久,已经关掉了」,
  不能让一个挂住的 HTTP 请求一直占着。
- **用户取消不是错误。** 三个平台取消的表现各不相同(osascript 非零退出、zenity 退出码 1、
  PowerShell 输出空串),一律翻译成 `{ picked: false }`,前端什么都不做。

### 决策 2:「添加环境参数」只产 prompt,不产接口

弹窗收完字段后,主按钮是**「复制 prompt 给 AI」**,不是「保存」。产出的文本按模板那份
已冻结的契约拼:第一行是能触发技能的固定头,后面是平铺的 `key: value`。

**两个入口各弹一层,不在同一层里切 tab。** API Key 收变量名 + 值;数据库只收显示名 +
一段连接信息原文,看板不拆引擎/主机/口令 —— 拆解是 `pm-env-config` 已经写清楚的判断。

**备选:看板直接写 `.env` 和 yaml。** 不选。三条理由,任何一条都够:
① 撞只读红线 —— 那是工作空间里的文件;② 看板要因此背上「凭据经手方」的责任
(写盘意味着口令进过服务端进程、可能进日志);③ 真正难的部分不是写文件,是
「引擎能不能支持、变量名叫什么、驱动装没装、连不连得上」,那些恰恰是 `pm-env-config`
已经写清楚的判断,复制一份到看板里必然漂移。

**口令的经手路径必须在界面上说清:** 只进剪贴板,看板不存;剪贴板里会有明文,
粘给 AI 之后建议清一下。这句话要写在弹窗里,不是藏在文档里。

### 决策 3:变量名第一版固定,不去读工作空间的 `.env.example`

契约里建议变量名下拉来自 `.env.example`。**第一版不做** —— 那要新开一个「读工作空间某个文件」
的接口,而收益只是省用户敲一次变量名。做法:`kind: api_key` 的变量名字段**预填
`MINERU_API_KEY`、可编辑**;技能那边本来就写着「用户说 MinerU / OCR token 但没给变量名,
就写入 `MINERU_API_KEY`」,两边对得上。

### 决策 4:「数据库源」tab 的出现判据放宽到「有 `input/sources/` 目录」(已拍板)

**已定,按本节实现。**

现在 `scanSources()` 在「没有 `*.yaml` 且没有产物目录」时返回 `null`,前端据此不渲染 tab。
于是**第一个源永远加不进来**:没源 → 没 tab → 点不到那个添加按钮。

改成:`input/sources/` 目录存在就返回数组(可能是空数组),前端的判据从
`sources.length > 0` 改成「服务端给了这个字段」。模板铺出来的工作空间本来就带
`input/sources/`(里面有 README 和 `example.yaml.txt`),所以新建的空间开箱就有这个 tab,
空态里放添加按钮。

**备选:把添加按钮挪到别处**(比如工作空间设置里)。不选 —— 用户找配置的地方就是他看数据的地方,
挪走等于又一次「入口不在看板上」。

**兼容:** 旧前端 + 新服务进程拿到空数组,`sources.length > 0` 仍然是 false,tab 照旧不出现,
行为一字不变。新前端 + 旧服务进程拿不到字段,同样不出现。

### 决策 5:扫描在**表数超阈值时**改发一个数字,不发单表明细清单

`collectSourceProducts()` 现在给每份拆分快照挂一整个 `tables` 数组。实测它占扫描载荷的 98.3%,
而前端只用它的长度。改成:

- 新增可选字段 `tableCount`(数字),**任何情况下都给**;
- `tables` 数组**只在表数不超过拆分阈值时给**,超过就不给。

**备选 A:一律不再给 `tables`。** 不选 —— 那是删掉一个已有字段,旧前端立刻少显示一行副文本,
连小库都受影响。分档之后,小库行为**一字不变**,只有大库的旧前端少一行提示,
符合本仓「宁可少显示一块,不能白屏」的兼容约定。

**备选 B:给一个「按需拉单表明细」的分页接口。** 不选 —— 现在界面上**根本点不开单表明细**
(快照那一行点开的是摘要),为一个不存在的交互先建接口是过度工程。真要做「在看板里按表浏览」
再单开一个 change。

顺带的收益:不发就不用 `stat`,大库上每次扫描省掉上千次系统调用。

### 决策 6:摘要在表特别多时改成**按表名前缀分组的紧凑清单**

现在超过阈值就退化成一张「表 / 类型 / 行数 / 用途 / 明细」五列的 Markdown 表格 ——
975 张表就是 975 行表格。它有两个成本:浏览器里解析 + 渲染近五千个单元格;
以及**它是唯一会被整份读进 AI 上下文的那份文件**,141 KB 的表格是实打实的上下文开销。

改成按表名的前缀分组(`<前缀>_*`),每组一节:组名、表数、组里各表一行紧凑文本
(表名 · 列数 · 有注释的话跟一句注释),明细链接照旧。实测的那个库里,
**前两个前缀就覆盖了七成的表**,分组天然对得上业务模块,AI 找表比扫一张千行表格快得多。

**兜底(必须写):** 表名没有前缀规律时(前缀分不出组、或者分出上百个单表组),
退回**按首字母分段的单一清单**,不要造出一堆只有一张表的「组」。

**备选 A:保持大表格不动,只靠 markdown worker 那条线扛。** 不选 —— worker 化解决的是
「主线程别卡」,解决不了「141 KB 进 AI 上下文」,而后者才是数据库源这条链路的主要成本。

**备选 B:摘要只列表名,注释和列数都不给。** 不选 —— 实测这个库 366 张表里有 223 张带表注释,
那是整份快照里对 AI 最有价值的一列,砍掉它省下的字节远不值。

### 决策 7:PG 白名单加 `::text[]` 显式转型,不改成展开占位符

三条查询的 `= ANY(%s)` 改成 `= ANY(%s::text[])`。**对原生 PostgreSQL 行为不变**
(参数本来就是文本数组),对 PG 兼容库则从「静默 0 行」变回正常。

**备选:照 MySQL 那边的写法,把白名单展开成 `IN (%s, %s, …)` 占位符。** 不选 ——
改动面大(三条查询都要改成模板拼接),而且拼占位符这件事本身就是 MySQL 那边不得已的写法,
没必要让 PG 也退回去。

**同时要补一条护栏:** 采到 0 张表时,`db_ingest.py` 现在会把快照原样写成「0 张表」并报成功。
应当**明确拒绝写盘**并报「一张表都没读到」,让上一份快照原样保留 —— 这与「连不上时保留上一份」
是同一条纪律,0 张表几乎不可能是真实答案。

### 决策 8:单表明细文件数暂不动

975 张表 = 975 份 `.md`,这个数量确实会让 `fs.watch` 在采集期间刷出上千个事件。
但 SSE 那头有 300 ms 防抖把它们收成一次推送,而扫描载荷在决策 5 之后已经不随表数增长。
**先不合并**:合并会牺牲「按需读一张表」的粒度,那正是拆分产物存在的理由。
瘦身之后再实测一次,不够快再单开 change。

## Risks / Trade-offs

- **原生对话框弹到别的窗口后面(尤其 macOS 的 `osascript`)** → 实现时要显式把对话框置前;
  界面上在等待期间给一句「已经打开系统选择框,请在桌面上完成选择」,
  用户找不到窗口时至少知道发生了什么。
- **服务跑在没有桌面的机器上(ssh 里 `pnpm serve`)** → 对话框起不来。返回明确中文说明
  (「这台机器上起不了目录选择框,请手工填绝对路径」),输入框照常可用,**不阻断**。
- **Linux 上 `zenity` / `kdialog` 都没装** → 同上,降级到手工输入。**不把它写成安装前提**,
  也不因此往 `dependencies` 里加任何包。
- **口令进剪贴板** → 这是这套设计的固有代价(换来的是凭据不落盘、不经过看板进程)。
  弹窗里必须写清「只进剪贴板,粘给 AI 后建议清空」,并用 password 输入框。
- **从别的机器用 http 访问看板时没有 Clipboard API** → 已有的 `writeClipboard()` 有
  `execCommand` 兜底;复制失败时必须显式提示失败,不能静默,否则用户会粘出一段空白。
- **前缀分组在表名毫无规律的库上退化** → 决策 6 的兜底路径;上线前拿一个"表名不带前缀"的
  合成用例走一遍,不能只在有规律的库上验。
- **大库上旧前端少一行「N 张表的明细」** → 这是决策 5 分档换来的取舍,已在 proposal 的
  兼容性一节写明:少显示一块,不白屏。
- **`::text[]` 只在一种 PG 兼容库上验过** → 原生 PostgreSQL 上等价、无风险;
  其它兼容库没环境验,所以决策 7 的「0 张表拒绝写盘」是承重的兜底 ——
  下一个静默出错的库会当场被它拦住,而不是悄悄写出一份空快照。
