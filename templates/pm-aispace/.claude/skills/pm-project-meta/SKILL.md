# 项目元信息提取

产出是工作空间根目录的 `project.yaml`。它是整个工作空间的身份证——
看板读它、写 PRD 时引用它、向对方团队确认问题时也基于它。

手写 Markdown 的写法（front-matter 形态、标题层级、文档间链接、哪些语法现在先别用）见工作空间 `AGENTS.md` 的「Markdown 写法」一节，这里不复述。

**这份文件最大的风险是「填得看起来很完整」。** 元信息一旦写错，后面每一份文档都会继承这个错误，
而且因为它长得像事实，没人会回头质疑。所以本技能的第一原则是：
**宁可留 null，不可猜着填。** 留 null 是一个待办；填错是一颗定时炸弹。

## 什么资料能用来提取

只有「定义项目本身」的资料才是元信息的合法来源：

| 资料 | 能提取什么 |
| --- | --- |
| 合同 / 补充协议 | 甲乙方、合同编号、建设周期、质保期、成果要求、验收流程、违约与付款 |
| 招标技术文件 / 需求书 | 建设背景、目标、建设内容、技术要求、性能指标、团队与服务要求 |
| 中标通知书 | 承建方、合同金额、中标时间 |
| 立项报告 / 可研 | 背景痛点、量化目标、覆盖范围、既有系统 |
| 会议纪要 | 干系人、阶段结论——但一律标 `口述待确认` |

**需求文档、设计文档、PRD 不是元信息来源**，它们描述的是系统怎么做，不是项目是什么。
从这些资料里提取需求请走 `pm-requirement-analysis`。

## 怎么做

**第一步，确认资料已入库。** 元信息只从 `input/converted/` 里的产物提取，不要直接读 `input/raw/`。
没有合同类资料就直接告诉用户「目前没有可提取元信息的资料」，不要拿需求文档凑数。

**第二步，读现有 project.yaml。** 它可能已经有人工确认过的内容。
**已经有值的字段不要覆盖**，除非新资料明确推翻了它——那种情况要先告诉用户，让用户决定。

**第三步，逐字段提取，同时记三样东西：**

1. **值** —— 写进对应字段。资料里没写的保持 `null`，不要用"暂无""待定"这类字符串占位。
2. **provenance** —— 字段的点号路径 → 来源文件和小节，例如
   `identity.建设周期.结束: "input/converted/合同.md · 三、工期"`。
   **每一个非 null 的字段都必须有 provenance**，没有来源的值不该存在。
3. **confidence** —— 只有非「资料写明」的才记：`推断` / `口述待确认`。
   资料里白纸黑字写着的不记，默认就是事实。

**第四步，把缺口转成问题。** 提取完之后，所有仍是 `null` 的字段过一遍，
判断哪些是**真的需要向对方团队要的**（比如干系人联系方式、验收标准），
每个缺口落成一条问题，写清楚「缺什么 / 为什么需要 / 该问谁」。
**缺口清单本身就是重要产出**，不要因为文档看起来不完整就心虚。

### 发现未决问题怎么落

**走 [`pm-open-questions`](../pm-open-questions/SKILL.md)，不要自己发明格式。**
先看一眼 `output/`：

- 有 `output/questions/` 目录 → **一问一文件**，新建 `output/questions/Q<四位编号>.md`（编号取当前最大加一；**目录空不等于从 Q0001 起**，先查 git 历史用过的最大编号）
- 只有 `output/analysis/open-questions.md` → 旧工作空间，照旧往表格里追加，**不要擅自迁移结构**

新结构下每条必须填 `source`（触发这条问题的文档路径）与 `context`
（触发时在做什么，一句话）—— 溯源锚点挂在**条目**上，不挂在分节上。
`blocks` 填它阻塞的在途交付物，判断不了就写 `backlog`，不要瞎填。
`evidence` 与 `ai_*` 刚提问时留空；**查不到依据只能写 `我方推断`，且不能置 `answered`**。

**双通道：正文归正文，问题归问题。** 分析结论写进文档，延伸出的未决问题写进问题文件，
**两边不许互串** —— 文档里不再放「待确认问题」表格（要提就写一句「见 `questions/Q0134`」），
问题条目里也不抄分析正文。同一条问题两处存在，很快就会对不上。


**第五步，向用户汇报三件事：**填了哪些、还缺哪些关键项、有没有资料互相矛盾的地方。
矛盾要明说（比如合同写 16 个月、招标文件写 18 个月），不要自作主张选一个。

## 字段规格

完整字段清单直接看工作空间根目录的 `project.yaml`——它自己就是 schema，注释里写了每个字段的含义。
几个容易出错的地方：

- `background.量化指标` 只放能验收的硬指标（`{ 指标: 跨系统数据共享率, 要求: 100% }`），
  「提升效率」这种不可验收的话写进 `background.目标`。
- `scope.明确不做` 极其重要但常常是空的——资料里没有明确排除项时保持 `[]`，
  **不要把「资料没提到」当成「明确不做」**，这是范围失控的主要来源。
- `milestones[].验收方式` 经常缺，缺了就是 null，它是评审会上最容易被追问的字段。
- `constraints.性能指标` 逐条抄准数字和单位，不要概括。
- `documents` 每次提取后追加一条，记下这次读了哪几份资料、什么时候读的。

## 什么时候重跑

新的合同类资料入库后重跑一次，做**增量补全**：只填 null 字段、只追加 documents。
用户明确说「重新提取」时才允许覆盖已有值，覆盖前把将被改动的字段列给用户确认。
