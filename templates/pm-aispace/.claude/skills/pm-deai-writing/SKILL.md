# 去 AI 味：规则库 + 交付稿

AI 起草的文档有一股味道：逐句挂「（依据：…）」、句子中间零散加粗、「赋能」「抓手」「闭环」、
「不是……而是……」、排比三连、段尾再总结一遍。**格式层面**的（批注块标记、手写编号、段中加粗）
转 Word 时脚本会兜底；**文字层面**的只能靠改写 —— 这就是本技能。

改写的依据是一份**有版本的规则库**，而不是每次凭感觉：人每纠正一次，能推广的就沉淀成规则，
下一份文档、下一次去味就不再犯。

| 东西 | 在哪 | 谁写 |
| --- | --- | --- |
| 规则库（当前版） | `.claude/skills/pm-deai-writing/rules/rules.md` | 本技能 |
| 历史快照 | `rules/history/v<版本>.md`（每一版的全文） | 本技能 |
| 变更说明 | `rules/CHANGELOG.md`（新的在上） | 本技能 |
| 交付稿 | `output/delivery/<原稿在 output 下的相对路径去掉 .md>/v<三位序号>.md` | 本技能 |
| 批注 | `output/records/notes/I<编号>.md`（原稿那份记录的批注文件） | 看板追加；你只改 `- 状态：` 与 `- 回执：` |

交付稿的落点与 front-matter 以 [`output/delivery/README.md`](../../../output/delivery/README.md) 为准，
批注格式以 [`output/records/README.md`](../../../output/records/README.md) 的「批注」一节为准，这里只写够干活的摘要。

## 三条铁律

1. **原稿一个字节都不动。** 原稿是「AI 起草的底稿」，交付稿是给人看的那一版，两者分开。
2. **每一版交付稿写出后不再改动。** 要改就出下一版（`v002`、`v003`……），「与上一版对比」看到的就是这一轮改了什么。
3. **事实不变。** 数字、日期、专有名词、表格数据、结论与原稿一致；只改说法。
   删掉的依据引用集中到文末「编制依据」一节，不能凭空消失。

## 摘要怎么算（和看板同一种算法）

front-matter 里的 `source_sha`、`body_sha` 都是 **SHA-256 的十六进制前 16 位**，先把换行规范成 `\n`：

- `source_sha`：原稿**全文**；
- `body_sha`：交付稿 front-matter **之后**的正文（结束的 `---` 那一行之后的全部内容）。

```bash
python3 - <<'EOF' output/docs/方案.md output/delivery/docs/方案/v001.md
import hashlib, re, sys
def norm(p): return open(p, encoding="utf-8").read().replace("\r\n", "\n").replace("\r", "\n")
def sha(t): return hashlib.sha256(t.encode("utf-8")).hexdigest()[:16]
src = norm(sys.argv[1]); print("source_sha", sha(src))
if len(sys.argv) > 2:
    t = norm(sys.argv[2]); m = re.match(r"^---\n.*?\n---\n", t, re.S)
    print("body_sha", sha(t[m.end():] if m else t))
EOF
```

`body_sha` 写的是**写出时**的正文摘要：写完文件再算一遍填进去（front-matter 不参与计算，所以填进去不会改变它）。
看板用它发现「有人绕过批注直接改了文件」。

## 用法一 · 去味：原稿 → 下一版交付稿

**输入**：一份原稿（`output/analysis/`、`output/docs/`、`output/decisions/` 下的 `.md`）；当前规则库。

**步骤**：

1. 读 `rules/rules.md`，记下 `version`；只用 `状态：启用` 的规则。
2. 算交付稿目录：原稿 `output/docs/方案/总体设计.md` → `output/delivery/docs/方案/总体设计/`。
   序号取目录里已有最大序号加一（没有就是 `v001`），**不覆盖已有版本**。
3. 逐条规则改写正文。格式类规则（R002 段中加粗、R003 批注块标记、R004 手写编号）转 Word 时脚本也会处理，
   这里照样改：交付稿在看板里也要读着干净。
4. 统计每条规则命中了几处，写进 `hits`。
5. 写文件，front-matter 如下（扁平，一个键一行），然后按上一节算 `body_sha` 填回去：

```markdown
---
source: output/docs/方案/总体设计.md
source_sha: 3f2a9c0d1e4b5a67
version: v001
based_on: source
notes:
rules_version: 3
created: 2026-09-30
body_sha: 9b8c7d6e5f4a3b2c
hits: R001×13, R002×40, R005×6
note: 首版去味，依据集中到文末
---
```

**自检**（写完逐项核对，不过关就改到过关）：

- [ ] 原稿文件没有被改动（`source_sha` 与原稿当前全文一致）；
- [ ] 数字、日期、专有名词、表格逐项和原稿一致，没有新增原稿里没有的事实；
- [ ] 删掉的依据引用都在文末「编制依据」里；
- [ ] 标题层级、表格、图片链接都在；
- [ ] `hits` 里的每条规则都是启用状态；`rules_version` 是改写时规则库的版本；
- [ ] `body_sha` 是写完后算的。

最后告诉用户：交付稿在哪、命中统计的前几条、有没有拿不准没改的地方。转 Word 时选**交付稿**，不是原稿。

## 用法二 · 批注修订与同步沉淀

人不直接改交付稿：在看板里打开某一版交付稿、写批注、点「复制提示词」。批注落在**原稿那份记录**的批注文件里，
这一批的标题下多一行 `- 对象：output/delivery/…/v001.md`，说明批注针对的是哪一版。提示词会写明下一版的路径。

**同一轮里做完三件事：**

1. **改出下一版**：以批注针对的那一版为底，按批注逐条改，写成 `v<下一个序号>.md`。
   front-matter 的 `based_on` 写那一版（如 `v001`），`notes` 列出本版处理的批注编号（如 `N0004, N0005`），
   `source` / `source_sha` 照抄底版，`rules_version` 写改完之后规则库的版本。**批注针对的那一版不改。**
2. **判断能不能推广**，逐条：

   | 这条批注是…… | 怎么处理 | 例子 |
   | --- | --- | --- |
   | 只关乎这份文档内容的更正 | 只改交付稿，不沉淀 | 「站点数写错了，是 12 个」「这段挪到第三节」「错别字」 |
   | 可推广的写法偏好 | 改交付稿，并沉淀进规则库 | 「不要写『全面提升』这种没有指标的话」「段尾不要再总结一遍」 |

   判据：**把这份文档换成另一份，这条意见还成立吗？** 成立就是写法偏好。拿不准的不沉淀，回执里说明「未沉淀：只针对本文内容」。
   沉淀的做法：已有规则覆盖得到的，给它补反例 / 正例 / 判据；覆盖不到的，新增一条规则（编号取最大编号加一）。
3. **同批只升一个版本**：这一批里不管沉淀了几条，规则库只升**一个**版本，按「规则库怎么改」写快照和 CHANGELOG，来源写批注编号。
   一条都没沉淀，规则库不动。
4. **回写批注**：按 `N` 编号逐条只改 `- 状态：` 与 `- 回执：`（格式见 `pm-output-record` 的「回写批注」）。
   沉淀过的，回执末尾加沉淀标记，可以有多个：

   ```markdown
   - 状态：adopted
   - 回执：已删掉段尾总结。沉淀为 R014（规则库 v4）
   ```

   标记必须严格写成 `沉淀为 R<三位编号>（规则库 v<版本>）`，看板靠它显示成可点的标签。
   `rejected` 仍然必须写原因 —— 只写沉淀标记不算原因。

**被直接改过时**：底版的正文摘要和它的 `body_sha` 不一致，说明有人绕过批注直接改了文件。先提醒用户
「v002 被直接改过，改交付稿请走批注，直接改动不会沉淀成规则」，然后**以当前文件为底**继续出下一版，
不从直接改动里归纳规则。

**自检**：用法一的全部项，加上：

- [ ] 批注针对的那一版没有被改动；
- [ ] 新版的 `based_on` / `notes` 写对了，`notes` 只列这一批里真正处理了的；
- [ ] 每条批注的状态都回写了（处理不了的留 `pending` 或写 `unclear`），没有改批注文件的其它行；
- [ ] 沉淀了的：规则库只升了一个版本、快照和 CHANGELOG 都写了、回执里的标记和规则编号对得上；
- [ ] 没沉淀的回执里没有「沉淀为」。

新沉淀的规则**立即适用**于之后的去味。沉淀错了（把一次性修改当成了通用偏好），由人再发一条批注或在体检时停用，
**不删规则**。

## 用法三 · 体检

**只给建议，不改规则库。**

1. 读 `rules/rules.md`，找：意思重复的规则、互相冲突的规则（一条要求 A、另一条要求非 A）、判据写得太宽会误伤的规则。
2. 扫 `output/delivery/**/v*.md` 的 `hits`，汇总每条规则的命中次数；列出长期零命中的规则（可能判据太窄，也可能用不上）。
3. 输出一份建议清单：每条写「建议停用 / 合并 / 改判据 R0xx：理由」。人确认后，再按「规则库怎么改」执行，
   CHANGELOG 的来源写「体检（日期）」。

## 规则库怎么改

`rules.md` 的格式：扁平 front-matter（`version` 正整数、`updated` 日期），每条规则一个三级标题 `### R<三位编号> <短名>`，
下面依次是列表项 `类别`（引用 / 强调 / 结构 / 措辞 / 格式）、`状态`（启用 / 停用）、`判据`、`反例`、`正例`、`改法`、`来源`。
每项写在一行里（看板按行解析），反例、正例用「」括起来。

- 编号只增不复用；规则**不删除**，不再适用的改成 `停用`，并在 CHANGELOG 里说明原因。
- 每次变更（新增、修改、停用）**同时做三件事**：
  1. `version` 加一、`updated` 改成当天；
  2. 把变更后的**全文**另存为 `rules/history/v<新版本>.md`（与 `rules.md` 逐字相同）；
  3. 在 `CHANGELOG.md` 顶部（标题之后）追加一节：

     ```markdown
     ## v4 · 2026-10-08

     - 新增 R014：段尾不再总结一遍
     - 修改 R005：补充反例「全面提升管理水平」
     - 来源：output/delivery/docs/方案/v001.md 的批注 N0002, N0003
     ```

- 反例一律用合成的句子，不要把客户资料的原文抄进规则库 —— 规则库会随技能带到别的工作空间。
