## Context

看板目前是单向的:扫工作空间 → 渲染 → 人看。人看出问题之后,反馈要绕出看板、
在终端里重新描述一遍上下文。而看板手上已经有把"页面上这一块"翻译成
"某个源文件的某个字节区间"所需的全部信息 —— 阅读器的 markdown 走的是
`react-markdown` 管线,渲染树上每个节点都带着源码位置。

立这个 change 之前先做了一轮技术验证(产物未入库),结论直接决定了下面的技术选型:

- **位置信息能穿过整条渲染管线**,包括 `rehype-raw` 重新解析出来的裸 HTML 片段和表格单元格,
  元素级覆盖率 100%。
- **但元素级锚点只是"粗锚"** —— 表格单元格的区间会连着单元格分隔符一起带进来。
- 用本仓的 `AGENTS.md`(约 300 行,含嵌套列表、引用块、表格里的行内代码和链接)
  做了约 300 次随机选区压测,下面选定的混合算法**没有出现真实锚点错误**。

一条值得单独记下来的教训:**验证"锚点对不对"本身需要一个可靠的判定器**。
验证过程中用正则近似"markdown → 渲染后纯文本"来做判定,反复出现假阳性 ——
行内代码里的 `**` 通配符被当成粗体标记、引用块的 `>`、表格分隔行、
分隔线、有序列表编号、裸 HTML 标签、代码围栏的语言标识,补了一轮又一轮。
每一次"失败"都是判定器不准,不是算法错。写验收测试时不要重蹈覆辙(见决策 9)。

## Goals / Non-Goals

**Goals:**

- 用户在 markdown 预览上划选 → 写想法 → 一键复制成完整提示词 → 粘给本机 agent →
  agent 改完 → 预览自动刷新。
- 提示词里给的是**可直接定位的源码区间**,不是"页面上某处"。
- 看板保持纯只读:不起子进程、不写工作空间、连服务端都不改一行。

**Non-Goals:**

- 不起 agent 子进程、不做协议层。看板只负责把话说清楚,谁去执行是用户的事。
- 不做跨版本重锚。批注是一次性的评审批次。
- 不做原型页(iframe 里的任意 HTML)批注 —— 那是另一套宿主,v1 再说。
- 不做浏览器扩展。扩展只为"任意外部网页"存在,而本仓的内容都在看板自己手里。
- 不改阅读器对图片、表格、图库、原型的现有行为。

## Decisions

### 1. 锚点用「文本节点定位 + 元素兜底 + 标记吸附」的混合算法

一个仓内的 rehype 插件把源码位置盖到 DOM 上:每个元素挂一个位置属性,
每个**带位置的文本节点**额外包一层 `span` 也挂上位置。求锚点时:

1. 选区端点优先取所在文本节点的位置 + 节点内偏移 —— 精确到字符;
2. 取不到就退回最近的、带位置的祖先元素区间;
3. 端点若落在行内标记(强调 / 行内代码 / 链接 / 图片)**内部**,向外吸附到该标记的完整边界。

**备选一:只用元素级锚点 + 在这段源码里搜选中的原文。** 不选,因为选区跨行内标记时
搜不到(渲染文本 `一个链接` 在源码里是 `[一个链接](...)`),只能整段退回,粒度太粗;
跨块选择时连共同祖先都找不到。

**备选二:只用文本节点级锚点。** 不选,因为两个死角:代码块的文本节点是渲染管线
**合成**的、不带位置,直接失效;而且端点落在标记内部时会把标记切断,
切出来的是开头没有结尾的强调标记、或者被腰斩的链接 —— agent 拿去改会写坏文档。

**备选三:只用 W3C 的 `TextQuoteSelector` 做文本模糊匹配。** 不选,因为它是为
"没有源码、只有渲染结果"的场景设计的(网页批注)。看板有源码,放着精确信息不用、
反而去做模糊匹配,是把简单问题做难。

第 1、2 条互补是这个算法成立的关键:元素级语法完整但粗,文本级精确但会切断标记、
且在合成文本上失效。

### 2. 位置属性按外部契约 A2 命名,看板是这条协议的第一个声明方

rehype 插件往 DOM 上盖的位置属性,名字与语义 MUST 用相邻仓 annotation-collect 定死的
**契约 A2**(它的 `AGENTS.md` §4,v0 已定稿):

```html
<article data-source-file="output/方案.md" data-source-range="1204,1876">
```

路径相对工作空间根,区间是源文件**字节**区间、**左闭右开**,两个属性同时存在才算声明,
缺任一个视为没声明。

这条不是为了迁就谁,是**白捡的**:插件本来就要往 DOM 上盖两个属性,叫什么名字成本一样。
按 A2 命名之后,那边的「修改款」(浏览器扩展在任意页面上批注、锚到源码区间)
在看板的预览页上**零适配**就能工作 —— 看板成为这条协议的第一个自愿声明方。
反过来,改动前想不到、做完再改要动 rehype 插件 + 锚点算法 + 那套重新渲染的判定器,
连带 300 次压测的基线一起重跑。

⚠️ A2 只能由宿主主动声明到 DOM 上:扩展从外部看不到渲染管线内部的 position 数据,
那只活在渲染过程里。这就是这条协议存在的理由,也是为什么它必须由我们这边出。

**备选:自己起一套名字(如 `data-pos` / `data-src-range`)。** 不选。省不下任何东西,
却把一个现成的、已经有第二个实现方在等的协议拒之门外。

### 3. 文本节点长度对不上时退到节点边界

行内代码的文本节点值是 4 个字(`行内代码`),源码区间却是 6 个字节(含两个反引号)。
判据很简单:`文本长度 !== 区间长度` 就说明中间有转义或标记,不能线性映射,
此时退到该节点的区间边界。这条兜底在压测里生效多次。

### 4. 批注是一次性评审批次,不做重锚

**备选:按 W3C Web Annotation Data Model 存三层选择器,文档改写后用模糊匹配重新贴回。**
不选。理由不是做不到,而是**不需要**:批注交给 agent 之后,这段对话的记录在 agent
自己的会话里,看板没有义务在改写后的文档上再显示一遍旧意见 —— 那反而是噪音。
砍掉重锚同时砍掉了这个 change 里最大的技术风险和一大块状态管理。

代价写清楚:批注不构成文档的历史评审记录。要这个能力得另立 change。

### 5. v0 不起 agent 子进程,改成组装提示词让用户自己粘贴

看板只把批注组装成一段完整的提示词、复制到剪贴板,用户粘到自己已经开着的 agent 会话里。

**备选一:服务端起一个 agent CLI 子进程,流式回显、可取消。** 推迟到 v1。
它要多写一个桥模块、一组会话接口、一套流式回显与取消的前端状态,
还要处理命令不存在 / 子进程崩溃 / 权限交互卡住这几类降级 —— 而这些**都不是**
这个 change 要验证的东西。要验证的是:锚点准不准、提示词组得好不好、agent 改得对不对。
这三件事,用户自己粘贴一样能验,而且验得更快。

**备选二:接 Zed 的 Agent Client Protocol。** 更远。ACP 是 **stdio 上的 JSON-RPC**,
浏览器够不着,无论如何都要在服务端写一个「浏览器长连接 ↔ stdio」的桥 ——
也就是说它并不能省掉备选一的工作量,只是把桥的另一头换成协议。协议本身还年轻、
适配器是移动靶,现在绑上去,调试的会是别人的 bug。等闭环被验证过、确实需要
"换 agent 不改看板"时再上。

**这个决定顺带消掉了一整块治理成本:** 不起子进程,看板就完全没有改动工作空间的路径,
`AGENTS.md` 第 1 节的只读红线一个字都不用改,也不需要给新接口加"非环回禁写"的口子。
上一版提案里那段"需要人拍板"的内容整段不存在了。

代价:回路上多一次人工粘贴,而且看板不知道这批批注有没有被处理 —— 由决策 7 补上。

### 6. 批注落浏览器本地存储,复用仓内已有的模式

`hooks/usePins.ts` 已经有一套「纯前端偏好、工作空间只读、按工作空间分键」的持久化:
模块级 store + `useSyncExternalStore` 广播 + localStorage。批注批次正好是同一个形状
(多处要同时看见、要跨刷新保留、不能写进工作空间),照着写。

**备选一:存服务端注册表旁边。** 不选 —— 在 v0 里没有任何一方需要服务端读到批注
(提示词在前端组装,源码正文本来就已经在浏览器里)。为了一份马上就要被清掉的临时数据
去加一组接口和一次进程重启,不划算。

**备选二:写进工作空间。** 不选 —— 直接破只读红线。

已知代价:换浏览器、无痕窗口、清站点数据就没了。批注本来就是一次性的,接受。
v1 真接了 agent 桥、服务端需要读批注时,再把存储搬到服务端,搬的是一个 hook 的内部实现。

### 7. 清空靠用户点,文档变化时给提示

没有子进程就没有"执行完了"的信号,所以不能自动清。做法:复制**不**清空;
现有的目录监听(SSE)捕获到这篇文档变化时,在批注面板顶部提示
「这篇文档刚被改动过,批注可能已处理」,给「清空 / 保留」两个按钮。

**备选一:点复制就清空。** 不选 —— 用户可能只是想再看一眼、或者粘贴失败,
清早了就白写了。
**备选二:文档一变就自动清。** 不选 —— 文档变化的原因不止"agent 处理完了"
(用户自己编辑、别的工具改的、转换产物刷新),自动清会吃掉没处理过的批注。
提示而不代劳。

### 8. 提示词里要交代什么,以及为什么倒序

提示词 = 文件相对路径 + 每条批注(选中原文引用 + 源码区间 + 结构提示 + 用户意见)
+ 可改动范围的限定。

- **同时给区间和原文引用**:区间是精确定位,原文引用是校验 —— agent 改完前一条之后,
  后面几条的坐标就不准了,让它以原文引用做最终定位。
- **按区间倒序排列**:先改文档后面的,前面的坐标才不会被顶掉。
- **给结构提示**:表格行、列表项这类区间必然包含渲染时看不见的东西
  (`| --- |` 分隔行、`- ` 标记),不说清楚 agent 容易误判。
- **不需要交代文档该怎么写**:由模板铺出来的工作空间自带自己的协作规范与技能,
  用户的 agent 就跑在那个目录里,这部分是白送的。

### 9. 验收测试的判定器:重新渲染,不要用正则近似

判断一个锚点对不对,正确做法是**把源码切片重新跑一遍同一条渲染管线,
取渲染后的纯文本再和选中内容比对**,而不是用正则把 markdown 近似成纯文本。
后者在验证阶段已经证明会持续产生假阳性,把人的注意力引到不存在的问题上。

注意表格行、列表项这类切片单独拿出来不一定能解析成原来的结构,
判定器要对这类切片放宽,或者按块边界取切片。

## Risks / Trade-offs

- **一批批注一起处理时,前面的改动会让后面的区间失效** → 提示词里同时给区间**和**原文引用,
  并按区间倒序排列(决策 8)。
- **剪贴板接口在非安全上下文里不可用**:`http://localhost` 算安全上下文,
  但用 `--host` 起在局域网地址上时走的是普通 http,**不算** → 退回一个已全选、
  可手动复制的文本框,并说明原因。不能只报一句"复制失败"。
- **看板不知道批注有没有被处理** → 决策 7 的提示机制;这是不起子进程的直接代价,
  写进用户可见的文案里说明白。
- **给每个文本节点包一层 `span` 会改变 DOM 结构** → 只包"能放行内内容"的容器里的文本节点,
  跳过表格与列表的结构性节点和纯空白节点,否则会生成非法 HTML 被浏览器挪走。
  长文档的渲染开销需要在实现时实测一次。
- **批注只活在这一个浏览器里** → 决策 6 的已知代价,不缓解。
- **批注不构成历史记录** → 决策 4 的已知代价,不缓解。

## Migration Plan

纯前端改动,分两段,每段都能独立回滚:

1. **锚点层**:rehype 插件 + 锚点算法 + 验收测试。这一层可以脱离界面单独验证。
2. **界面层**:选区浮层、批注高亮、批注面板、提示词组装与复制。

**回滚**:前端不渲染批注入口即可退回纯只读看板。服务端、契约、CLI 都没动,
不存在需要重启常驻服务或兼容旧进程的问题。

- 提示词要不要给用户一个可编辑的预览(复制前能改两句),还是直接进剪贴板?
