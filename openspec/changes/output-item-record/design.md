## Context

`output/` 下有三类产出物,各自有自己的生命周期,但看板现在对它们一视同仁:
只能读到标题、字数、`mtime`。

- `analysis/` —— 过程产物。技能一轮轮往里写,**没有任何机制标记「已被吸收」**,
  于是旧版一直躺着,分不清哪份还作数。
- `docs/` —— 交付物。发出去之后有没有被评审、对方说了什么、这版是不是最终版,全都读不到。
  `output/README.md` 说「版本交给 git」,但看板扫的是文件系统当前状态,git 历史在看板里不可见。
- `decisions/` —— 只追加不改历史(这是设计,不是病)。模板 README 的示例里**已经有**
  「状态:已确认 | 待确认 | 已推翻(被 0007 取代)」,但它写在**正文 bullet 里**,
  而 `scan.mjs` 的 `describeOutput` 只抽 front-matter 的 `meta.status` —— 这个指向关系解析器读不到,
  所以失效的决策在列表里和生效的长得一模一样。

`output/questions/` 是本仓已经走完的同类改造。它的经验直接适用,尤其两条:
**条目长度由结构管住**(扁平 front-matter,长文进正文)、
**状态必须对应分化的后续动作**(那份 README 里「高/中/低」通胀到一半标「高」是反面教材)。

## Goals / Non-Goals

**Goals:**

- 三类产出物都有一个带状态的实体,状态能回答该类真正要问的那个问题。
- 状态变更与补充说明是一次交互,反馈有地方落且不污染 `output/docs/` 里要发出去的文档。
- 记录不挤占 `output/` 三组列表。
- 写入面的边界写死在 spec 里,不靠自觉。
- 为后续两个 change(批注搬家、归档链路)准备好它们各自要挂载和要读的东西。

**Non-Goals:**

- **不做批注搬家与批注闭环**。它依赖本 change 的记录文件作为挂载点,单独立 change。
- **不做归档搬运**。它是 `spawn` 形状,且要读本 change 的状态,单独立 change。
- **不改 `open-questions` 的 `blocks` 字段**。
- **不碰三个目录里产出物文件本身**。记录是旁挂的,单向反链。
- **不自动推导状态**。`analysis/` 的「已被吸收」理论上能从溯源反链推出来,
  但推错一条就是在骗人 —— 本轮一律人工/agent 明确置位,自动推导留作以后。

## Decisions

### 1. 记录反链产出物,不是产出物指向记录

记录的 front-matter 写 `target: output/<子目录>/<文件名>`,单向。

备选:在产出物文件的 front-matter 里加字段指回来。**不选**,`docs/` 是给收件人的,
任何我方视角的元数据都是噪音;而且 `docs/` 的 front-matter 本来就不强制,加了等于强制。
单向反链的代价是「从产出物找记录」要遍历,这个量级下可以忽略。

### 2. 一个统一的记录目录,靠 `kind` 区分三类

`output/records/I<四位编号>.md`,`kind` 取 `analysis` / `docs` / `decisions`。

备选 A:每类一个记录目录。**不选**,三个目录要维护三个编号最大值,
「空目录不等于从头编号」那个坑要踩三遍。
备选 B:三类各用自己的编号前缀(`A0012` / `D0007` / `C0003`)。**不选**,
外部引用需要的是稳定锚点,不是类别信息 —— 类别从记录里一读就有,
而三个编号池的维护成本是实打实的。

注意 `decisions/` 自己的 `0001-短标题.md` 文件名编号**与记录编号是两套**,互不冲突:
前者是决策在目录里的序号,后者是记录的锚点。

### 3. 三套状态机,按 `kind` 分化

| `kind` | 状态机 | 终态要求 |
| --- | --- | --- |
| `analysis` | `drafting`(在写) → `absorbed`(已被吸收) / `stale`(过时,没被用上) | `absorbed` 必须说明被哪份产出物吸收 |
| `docs` | `draft` → `delivered` → `revising` → `final` / `superseded` | `superseded` 必须说明被哪个编号取代 |
| `decisions` | `pending`(待确认) → `confirmed`(已确认) → `overturned`(已推翻) | `overturned` 必须说明被哪条决策推翻 |

备选:统一一套五态。**不选**。分析中间产物不存在「发给对方」,决策不存在「待修订」——
每类都会带着两三个永远用不上的状态,而这正是 `questions` 那条教训的反面:
状态必须对应分化的后续动作,不对应的状态就是噪音。
`decisions` 那套是**照搬模板 README 已有的约定**,不是新发明的 —— 不照搬就是凭空造出第二套口径。

三套都 MUST NOT 包含「已归档」:归档改变的是文件位置,不是产出物的状态。
把位置混进状态机会让归档 change 无处下手。

### 4. 状态与补充说明是一次交互,落成状态流水

界面上是「选一个该类的标准状态 + 紧跟一个补充说明输入框」,保存成正文
「## 状态流水」下的一条 `###` 子节(带日期与状态值)。

备选:状态写 front-matter,反馈另开一个「## 交付反馈」小节,两次交互。**不选**。
反馈的绝大多数场景就是「为什么改成这个状态」——把它做成状态变更的注解,
一次交互完成,而且天然解释了两者为什么放在一起。
长篇的对方评审意见仍然可以由 agent 写进正文别处,补充说明只放一句话级的注解。

front-matter 里保留 `status` 当前值(解析器要读它做分组),
流水是历史;两者的关系是「`status` 等于流水最后一条的状态值」。

### 5. 记录不进产出列表,也不喂溯源反链

`scan.mjs` 的 `scanOutput` 只遍历 `['analysis', 'docs', 'decisions']`,新目录天然不在其中 ——
和 `questions/` 提到 `analysis/` 同级之后的效果一样,不需要额外的排除逻辑。

但有一处要与 `questions/` **不同**:questions 的正文照样喂给 `attachReferences`
(一份资料被某条问题引着,就算「被产出引用」)。记录**不喂**。
理由和 `scan.mjs` 排除 questions 目录里过程件的理由是同一条:状态流水会抄产出物原文
与资料引用,喂进去会把「被 N 篇产出引用」顶虚高,让「转换好了却没人用」这个缺口提示失真。

附带好处:不喂反链就不必读它们的正文,扫描只做 `stat` 加一次 front-matter 解析。

### 6. 编号唯一且只增不复用

`I<四位编号>`,一个工作空间内唯一。终态、归档之后 MUST 保留编号 ——
编号是外部引用的锚点(会议纪要、别的分析文档会写「见 I0007」)。
「空目录不等于从 I0001 开始」这个坑连同查历史最大编号的做法,照抄 `questions/README.md`。

### 7. 看板不新建文件,记录由技能建立

看板的写入一律是「改已存在的文件」,文件不存在返回 404。

备选:允许看板新建记录。**不选**。「看板不新建、不删除、不改名」是 `writeQuestion` 那条例外里
最硬的一条,也是最容易被侵蚀的一条 —— 一旦开了口子,下一个功能就会照着
「反正已经能建了」推广。技能建产出物时顺手建记录,成本是零。

### 8. 统一工作台,⌘K 里分「未决问题 / 产出物」两页

备选:另开一个弹窗和快捷键。**不选** —— 两者形状高度相似(清单 + 卡片 + 就地写入),
分两个入口会让用户记两个快捷键,而且将来第三类(归档待整理清单)又要再开一个。

代价是要动存量:`QuestionsDialog.tsx` 有 1240 行,整体重构有弄坏存量功能的实际风险。
**所以切法是「提壳,不动内脏」**:

- 新建工作台外壳组件,只管 Dialog 容器、两页切换、快捷键;
- 现有 `QuestionsDialog` 的**内部整块保留**成工作台的一页,内部逻辑、状态、
  `useQuestions` 的接线一行不改 —— 只把最外层的 Dialog 容器和 `QuestionsFab` 剥出去;
- 产出物那一页是全新组件,与 questions 那页之间**不共享状态**。

`QuestionsFab` 的待处理计数保持只数未决问题,不改成两页合计 ——
改计数口径会让这个数字的既有语义漂移。

### 9. 写入的并发方案是分区,不是锁

人写区(`status`、状态流水)由看板写;AI 写区(`target`、`updated`、正文其余部分)
由工作空间的 agent 写。载荷里出现 AI 写区字段一律 400 且不落盘。
写入走「先写临时文件再原子替换」。这套照抄 `writeQuestion`,连理由一起:
物理隔开写区本身就是并发方案,不用引入锁。

`target` 归 AI 写区:产出物文件改名时要跟进,而只有能看到文件系统的 agent 有依据判断。

## Risks / Trade-offs

- **三套状态机让前端多三个分支** → 接受。状态值的合法集合由 `kind` 决定,
  服务端校验、前端渲染各写一处映射表,不要散在组件里。
- **`decisions/` 的状态要从正文 bullet 迁进 front-matter** → 存量决策文件都得改。
  迁移脚本默认预演,且**只加 front-matter 字段、不删正文那行 bullet** ——
  正文那行是给人读的,删了反而丢信息。
- **记录与产出物可能脱钩** → `target` 指向的文件被改名或删除时,记录变成悬空。
  看板标「指向丢失」并照常列出(用 orange,这正是「需要注意」的语义),
  MUST NOT 隐藏、MUST NOT 报错崩溃。
- **工作台化动到了 1240 行的存量弹窗** → 按决策 8 的「提壳不动内脏」切,
  `QuestionsDialog` 内部不进改动范围。但它毕竟换了挂载位置,
  验收时必须**单独走一遍存量 questions 的完整回路**(⌘K 唤出、分组筛选、卡片翻页、
  保存一条人工反馈、复制 prompt),不能因为「只动了外壳」就跳过。
  这是本 change 里唯一会碰到已上线功能的地方。
- **记录数会随三类产出物一起长** → 本 change 只保证记录本身是短的(长文进正文、
  清单只下发短字段)。记录目录自己的堆积由归档 change 处理,
  那也是它必须能读到状态的原因。

## Migration Plan

1. 模板侧先落地:`output/records/` 骨架 + 目录 README(字段契约的事实源)+ 技能里的新建步骤;
   `decisions/` 的状态约定挪进 front-matter(迁移脚本默认预演)。
2. 服务端加读接口(只读,先不写),前端工作台提壳 + 产出物页能看到清单。
   此时老工作空间没有这个目录,显示空态。
3. 加写接口(状态 + 补充说明),按 `writeQuestion` 的六条约束逐条实现。
4. 回滚:第 3 步之前的改动都是只读的,回滚只需回退前端入口与工作台外壳。
   第 3 步之后回滚不会丢数据 —— 已经写进记录的状态流水是普通 Markdown,agent 照样读得懂。

## Open Questions

- **`analysis` 的 `stale` 与 `absorbed` 够不够?** 还有一种是「这份分析后来发现是错的」——
  它和「过时没用上」的后续动作一样(都是归档),所以倾向不单独立一态,
  由补充说明说清是哪种。
- **`status` 与状态流水最后一条不一致时以谁为准?** 倾向以 `status` 为准
  (解析器读它做分组,流水是给人看的历史),但要在 spec 里写明,
  并让校验脚本报告不一致 —— 这种不一致只会来自手工编辑。
