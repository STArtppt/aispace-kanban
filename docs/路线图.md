## 1. `output/` 的分组改成数据驱动

### 问题

`src/server/scan.mjs` 的 `scanOutput` 里，产出分组是写死的三个名字：

```js
for (const group of ['analysis', 'docs', 'decisions']) { … }
```

这三个名字来自模板的 PM 流水线（分析中间产物 / 对外交付文档 / 决策记录），
`src/app/components/OutputPanel.tsx` 的 `GROUPS` 常量里连标题和说明文案都是 PM 语境的
（「PRD、需求规格、评审材料」）。

看板已经把自己定位成**通用的 AI 知识工作看板**（README 开头那一节），
准入门槛也只有 `input/` + `output/` 两个目录（`config.mjs` 的 `inspectWorkspace`）。
于是出现一个矛盾:

- 做市场调研的人建了 `output/竞品/`、`output/报告/` —— **看板一个字都不显示**，
  文件在磁盘上、界面上却是空的。这比不显示更糟：它让人以为 AI 没写。
- 反过来，`output/decisions/` 是空的时候，界面照样给一块「决策记录 · 一个决策一个文件」的
  空态，对一个写稿子的人来说是纯噪音。

**判据一句话：目录约定是产品的一部分，但目录的「名字」不该是。**

### 怎么改

按 `dashboard-feature-flow` 的顺序，服务端 → 契约 → 前端。

**服务端**（`scan.mjs`）：扫 `output/` 下的一级子目录，而不是查表。

- 保留 `analysis` / `docs` / `decisions` 三个键，让老前端和老服务都不受影响（见下面兼容性）。
- 新增 `groups: { key, name, files }[]`，key 用目录名，顺序：已知的三个排前面（保持现在的观感），
  其余按目录名 `localeCompare(zh)`。
- 沿用 `listFiles` 的 `SKIP` 集合和 `rel()`，别另起一套。
- `output/` 下的**散文件**（不在任何子目录里）现在是被忽略的，一并收进一个默认组，
  否则用户在 `output/` 根上直接写一篇就消失了。

**契约**（`src/app/lib/api.ts`）：`output` 加 `groups?: OutputGroup[]`，**可选**。
三个老字段一个都不删 —— 用户完全可能跑着旧服务进程配新前端。

**前端**（`OutputPanel.tsx`）：

- `groups` 存在就按它渲染；缺失（旧服务进程）就退回现在的 `GROUPS` 常量，行为完全不变。
- 标题文案：已知的三个 key 沿用现在的中文名和说明；未知 key 直接显示目录名，**不编说明文案**
  （编不出来就别编，目录名本身已经是用户起的名字）。
- 空目录不再无条件给空态：只有已知的三个组保留空态提示，用户自建的组为空时不渲染。

### 顺带要动的

- `templates/pm-aispace/project.yaml` 的 schema 是乙方交付项目的字段（甲方 / 承建方 / 合同编号 / 质保期）。
  **`meta.mjs` 的 `walk()` 其实完全通用** —— 它不认识任何字段名，只统计叶子节点空不空，
  所以这块不用改看板。按场景铺不同的 `project.yaml` 和技能集是各模板自己的活，
  与本条改动可以分开做，别混在一个提交里。
- `OverviewPanel` 的「工作空间进度」四阶段也是按固定目录判的，等本条落地后一起看。

### 验收

- 建一个只有 `output/竞品/`、`output/报告/` 的工作空间，两组都能列出来、能点开。
- 老三样目录的工作空间，界面和改动前**逐像素一致**（这条是回归线，不达标就是改坏了）。
- 用旧服务进程（不重启 serve）配新前端，产出视图仍按三栏正常显示，不白屏。

## 2. 幻灯片渲染

### 问题

看板的第二个用途是**把 AI 产出的裸 Markdown 变成能给人看的东西**（见 README
「让产出能直接给人看」）。现在这条路走到「渲染成好读的网页」为止，
但知识工作的最后一公里往往是**开会讲**：评审、汇报、给客户过方案。

到了这一步，现在的做法是把 `output/docs/` 里的 Markdown 手动导成 PPT。
两个后果：一是费时间，二是**导出的那一刻就和源文件脱钩了**——
AI 改完文档，投影上那版还是旧的，而这正是看板一开始要解决的问题。

### 怎么改

**这是纯前端改动**：文件内容已经由 `/api/projects/:id/file` 给出来了，
服务端和契约（`api.ts`）一个字都不用动，也就不存在「忘了重启 serve」那类坑。

- **哪些文档能放幻灯片**：不要新增 `output/slides/` 这种硬编码目录——那跟第 1 条
  「目录名不该是产品的一部分」的方向正好相反。改成**阅读器里的一个「幻灯片」开关**，
  任何 markdown 都能切；文档想默认以幻灯片打开，就在 frontmatter 里写个标志位
  （`slides: true`），沿用 `frontmatter.mjs` 已经能解析的扁平 kv，不引额外依赖。
- **怎么分页**：按顶层 `---` 分隔符切（marp / reveal 的通行写法），没有 `---` 时退回按
  `##` 切。注意 `parseFrontmatter` 是靠开头的 `---` 认 frontmatter 的，
  切页要从正文（`body`）上做，别在原文上正则，否则第一页会把 frontmatter 吃进去。
- **必须继续能用的东西**：mermaid 图和 Shiki 高亮在幻灯片里要照常渲染——
  它们是 `Markdown.tsx` / `MermaidBlock.tsx` / `MarkdownCodeBlock.tsx` 现成的能力，
  幻灯片模式复用同一套渲染管线，不要另写一份。
- **放映**：全屏、左右方向键翻页、页码。字号要跟着容器放大，不能沿用正文的 `text-sm`。
- **导出**：走浏览器打印（`@media print` 每页一屏 + `window.print()`）出 PDF。
  **不要往工作空间里写导出文件**——只读红线，导出只能落到用户的下载目录。

### 验收

- 一篇带 mermaid 和代码块的文档，切成幻灯片后图和高亮都在。
- 没有 `---` 的普通文档切过去也能用（按 `##` 分页），不报错、不空白。
- 关掉幻灯片开关回到正常阅读视图，行为和现在完全一致。
- 深色模式下投影可读（深色底白字，不是一片灰）。

## 4. PDF / PPTX 先走本地引擎，MinerU 退成兜底

### 问题

`templates/pm-aispace/scripts/ingest.py` 现在把 PDF / PPTX 全交给 MinerU 在线 API。两个后果：

- **网络是单点**。MinerU 是整条入库链路里唯一外发资料的环节，也是唯一会因为网络失败的环节。
  轮询 5 秒一次、上限 900 秒，赶上服务抖动就是等一刻钟拿一个失败。
  它还有 200 页 / 200MB / 每天 1000 页的硬限制，稍厚一点的规程、标准、教材根本进不来。
- **没 key 时的兜底会静默损坏中文**。实测 markitdown 转中文 PDF，会把「水」写成康熙部首 `U+2F54`、
  「门」写成 `U+2ED4`：产物肉眼看着没问题，但 `grep 水库` 一条都搜不到。
  看板搜索和后面所有 AI 分析都建立在这份产物上——这比转失败更糟，转失败至少台账上是红的。

### 引入什么

`@firecrawl/anydoc`（MIT，Rust 单二进制，无运行时依赖；npm 包装 10KB + 平台二进制 6.7MB，按平台只装一个）。

**不要单独再引 `pdf-inspector`**：anydoc 的 PDF 后端就是它，引 anydoc 等于引了它；
而且它的 npm 包没有 darwin-x64 预编译，Intel Mac 上装不上。

本机实测（macOS arm64 / Node 22 / anydoc 0.2.3）：

| | markitdown（现兜底） | anydoc |
| --- | --- | --- |
| 中文 PDF 码位 | ✗ 康熙部首，搜不到「水库」 | ✓ 全对 |
| 标题层级 | ✗ 全丢 | ✓ `#` / `##` 还原 |
| 369 页中文 PDF（8.4MB） | — | ✓ 1.3 秒 / 24.6 万字 / 560 行表格（MinerU 超 200 页会被拒） |
| 真实中文 PPTX | — | ✓ 0.7 秒，91 个标题 + 137 行表格 |
| 扫描件 | 静默产出空文件 | ✓ 明确报错，带类型和页数 |

**它做不到的三件事，就是 MinerU 必须留着的理由**：

1. **PDF 里的图一张都拿不到**。不是 CLI 的问题：Python 绑定调 `to_document()` 对 PDF 直接抛
   `UnsupportedError: PDF converts directly to Markdown`。现在 `write_mineru_result()` 是会把图
   落进 `input/assets/` 的，这条能力只有 MinerU 有。
2. **不做 OCR**。npm CLI 连 `--ocr` 选项都没有（OCR 是 Rust 的 build-time feature，
   还要外挂 PDFium + ONNX Runtime）。
3. **版式启发式是基于字号的**，封面、目录、多栏这类页会翻车（369 页那份出了 897 个标题，
   版权页被当成表格）。MinerU 的版面模型在这类页上明显更好。

PPTX 的图：CLI 出的 markdown 不带图，但 Python 绑定的 `to_document()` 能拿到原始图片字节
（实测那份 pptx 有 76 张）。**本条不走 Python 绑定**——`ingest.py` 的「零 Python 依赖」是硬约束，
为抽图破例不值当。所以 PPTX 的默认引擎维持 MinerU，anydoc 只接管它的兜底位。

### 怎么改

引擎从「MinerU 或 markitdown」二选一，改成一条阶梯：

```
PDF   ① anydoc（默认，本地，不联网）
      ② anydoc 报 Scanned / ImageBased → 配了 key 就自动升级 MinerU --ocr；没配就记警告
      ③ --pdf-engine mineru → 直接走 MinerU（要抽图、要公式、版式复杂时）
PPTX  维持 MinerU；没 key 时兜底从 markitdown 改成 anydoc
.msg  继续 markitdown —— 这是留着它的唯一理由
```

第 ② 步不需要额外的探测工具：anydoc 的报错串里自带类型和页数，正则抓一下就能路由。

**新增 `templates/pm-aispace/scripts/anydoc.py`**，接口对齐同目录的 `mineru.py`
（`available()` / 自带异常类型 / 只依赖标准库）：

- `find_bin()`：先读环境变量 `ANYDOC_BIN`（看板注入的），再 `shutil.which("anydoc")`。
  **不要自动 fallback 到 `npx`**——npx 首次会联网下载，正好把这条改动要解决的问题请回来了。
- `available() -> bool`。
- `class AnydocError(RuntimeError)`；`class NeedsOcrError(AnydocError)`，带 `pdf_type` / `pages`
  两个字段，从 stderr 的
  `unsupported input: PDF has no extractable text (Scanned, 369 pages): OCR is required` 里解析。
- `to_markdown(src: Path) -> str`：`subprocess.run([bin, str(src)], capture_output=True,
  encoding="utf-8", errors="replace")`。**必须显式给 `encoding="utf-8"`**，不能只写 `text=True`
  ——Windows 上默认跟系统 locale 走，中文正文当场炸，和 `ingest.py` 顶上那段 `reconfigure`
  是同一个坑。退出码：0 成功、1 转换失败、2 用法错；版本号 `anydoc -V` 直接打印 `0.2.3`。

**`scripts/ingest.py`** 的改动点（行号是现状锚点，动手前先确认上下文）：

- L68 附近：`import anydoc`，与 `import mineru` 并排。
- L92 常量区：新增 `ANYDOC = {".pdf", ".pptx"}`；`MARKITDOWN` 的注释改成「只为 .msg 保留」。
- `resolve_pdf_engine()`（L952）：四档——显式指定就用指定的；`auto` 时
  `anydoc.available()` → `anydoc`，否则 `mineru.available()` → `mineru`，都没有 → `markitdown`。
- `plan()`（L984）：`anydoc` 分支排在 `mineru` 前面。
- 新增 `convert_anydoc()`，放在 `convert_markitdown()`（L813）旁边。`frontmatter()` 的 `tool`
  写 `anydoc <版本>`，`extra` 里 `kind: document`。**不要抄 markitdown 那段「体积不小却几乎没有文字」
  的启发式警告**——anydoc 遇到这种情况是直接报错的，那段判断在这条路径上永远不会命中。
- `main()` 的 dispatch（L1170）：`how == "anydoc"` 时 try / except `NeedsOcrError` →
  配了 MinerU key 就 `deferred.append((src, digest, target))` 并打一行「扫描件，转交 MinerU OCR」；
  没配就记 `⚠ 扫描件需 OCR`，**不要算进 `failures`**（它不是失败，是缺配置；算进去会让整批退出码
  变 1，看板整条飘红）。注意升级进 `deferred` 的文件必须让 `mineru.parse_batch(is_ocr=True)`，
  不能沿用命令行 `--ocr` 的默认 `False`——它们本来就是扫描件。
- argparse（L1105）：`--pdf-engine` 的 choices 加 `anydoc`，help 重写。
- L1127 那两行提示：现在是「没配 MINERU_API_KEY，退回 markitdown」，
  改成「PDF 走本地 anydoc；扫描件才需要 MinerU」。

**`src/server/http.mjs`**：

- `startIngest()`（L355）的 `spawn(..., { env: process.env })`：把解析到的 anydoc 二进制路径
  作为 `ANYDOC_BIN` 注入。用 `createRequire(import.meta.url).resolve('@firecrawl/anydoc/cli.js')`，
  **包一层 try/catch，解析不到就不注入**（用户可能自己 `npm i -g` 了，`ingest.py` 会走 PATH）。
- `summarizeIngestLog()`（L224）：新增「扫描件需 OCR」和「找不到 anydoc」两条分支，
  且**必须排在现有 mineru 那条分支前面**。那条的判断是
  `/mineru|MINERU_API_KEY/i.test(text) && /失败|error|…|缺/i.test(text)`，
  吃的是**整段日志**而不是某一行——只要日志里任何地方出现过 mineru 和「缺 / 失败」，它就先命中，
  用户看到的就变成「检查 token 是否正确」这种驴唇不对马嘴的话。

**根 `package.json`**：`dependencies` 加 `@firecrawl/anydoc`。

⚠ **组包脚本这里有个坑，必须一起改**：`scripts/build-npm-package.mjs`（L100-133）是靠正则扫
`src/server/**` 和 `bin/cli.mjs` 里的**裸 import 字面量**来决定发布包 `dependencies` 的。
`createRequire(...).resolve('@firecrawl/anydoc/cli.js')` 匹配不上那条正则（`createRequire(` 里是
大写 R，参数也不是字符串字面量），结果就是本地跑得好好的、发出去的包里没这个依赖，
装包的人一转 PDF 就悄悄退回兜底。改法：给 `used` 显式补一个「运行时用到但不是静态 import」
的集合，并把原因写在注释里。

### 顺带要动的

- `.claude/skills/pm-doc-ingest/SKILL.md`：格式分派表那一行、以及整节「MinerU 相关」要按阶梯重写。
  尤其「资料涉密 → 用 `--pdf-engine markitdown` 本地处理」这条要改成 anydoc，
  并把默认行为的变化说清楚：**改完之后默认不外发文件了**，只有显式走 MinerU 才会上传。
  这是这条改动对用户最重要的一句话。
- `templates/pm-aispace/.env.example`：`MINERU_API_KEY` 那段注释现在写的是「不填也能用，
  退回 markitdown，还原质量差」，改成「不填也能用，PDF 走本地 anydoc；
  MinerU 只在扫描件、要抽图、复杂版式时才需要」。
- `templates/pm-aispace/AGENTS.md`、`README.md`、`input/README.md` 里凡是写「PDF → MinerU」的地方。
- `scripts/migrate_converted.py` 不用动（它不认引擎名）。
- `npm-package/` 是 `build-npm-package.mjs` 生成的，不要手改。

### 验收

`src/server/**` 和 `scripts/*.py` 都没有静态检查，typecheck 绿不算做完
（见 [`verification-before-completion`](../.claude/skills/verification-before-completion/SKILL.md)）：

- `pnpm typecheck` + `pnpm build` 绿。
- 命令行：一份中文 PDF → 产物里能 `grep` 到正文中的中文词，frontmatter 的 `converted_by` 是 `anydoc`。
- 命令行：一份扫描版 PDF，**没配** `MINERU_API_KEY` → 台账是 `⚠ 扫描件需 OCR`，脚本退出码仍是 0。
- 命令行：同一份扫描件，**配了** key → 自动走 MinerU OCR 出正文。
- 命令行：`--pdf-engine mineru --force` 重转一份带图的 PDF → 图仍落进 `input/assets/`，
  链接在产物里点得开。**这是回归线**，别把抽图能力弄丢了。
- 重启 `pnpm serve`，在看板里点一次「转换」：正常路径出结果；再把 `ANYDOC_BIN` 指到一个
  不存在的路径点一次，提示要是人话，不是一段 traceback。
- `pnpm build:npm && node scripts/smoke-package.mjs`：干净目录装包后能转 PDF ——
  这一步专门验上面那个组包依赖的坑，跳过它等于没验。

## 其余候选（还没排期，按价值粗排）

- **「上次看之后 AI 动了什么」**：把「上次查看时间」记进注册表 `~/.pmwork/`（可写，不碰只读红线），
  给未读标记和最近变更流。现在只有 mtime，看不出「这轮对话动了哪些」。
- **全文检索**：跨 `input/converted` + `output` 的关键词接口。几十上百篇之后没搜索，
  就只能回去问 AI —— 而那等于让它自己给自己打分。
- **多工作空间横向首页**：现在一次只看一摊，做知识工作的人常同时开三五摊。
  一个「每摊各有多少缺口、最近谁动了」的总览才撑得起「看板」这个名字。
- **原型视图从「Axhub 导出包查看器」变成「原型库」**。扫描这一半已经做完了：
  `prototypes.mjs` 认的是任何 `<子目录>/index.html` 或 zip 包，跟 Axhub 已经没有耦合，
  AI 生成的方案页、可视化、演示页放进去就能列出来（约定见
  `templates/pm-aispace/AGENTS.md` 的「阶段四：原型」）。剩下两件事：
  一是 `prototypes.mjs:210` 的空态文案还写着「axhub-make 导出的 zip」，口径要跟上；
