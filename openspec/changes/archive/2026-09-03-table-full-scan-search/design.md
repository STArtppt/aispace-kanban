## Context

现状(改动前):

- `/api/projects/:id/table` 用 `readline` 流式逐行读 csv/tsv,只返回表头 + 一页行 + 总行数;
  行数按 `路径 + mtime` 缓存,翻页时不必再扫全文(`src/server/http.mjs` 的 `readCsvPage`)。
  这套设计就是为了躲开"整表塞进 JSON"撞出来的 413。
- 前端 `PaginatedCsvTable` 每页 50 行(`TABLE_PAGE_SIZE`),分页状态 `page` 是它自己的
  `useState`,外部拿不到也推不动;渲染出来的 `<tr>` 上没有绝对行号,只有页内下标 `i`。
- 预览窗检索 `PreviewSearch` 全程本地:`collectBlocks()` 对着当前正文根建块索引,
  表格形态按 `<tr>` 分块(一行一条,单元格文本用空格拼),`searchBlocks()` 打分排序,
  选中后 `SearchJumper` 滚动 + 加两秒 class。它**只能看见 DOM 里已有的东西**,
  所以数据页的检索天然只覆盖当前这一页。
- 匹配内核 `src/app/lib/fuzzySearch.ts` 是纯函数、零依赖、不碰 DOM:`normalize()`
  (全角折半角、英文小写,**逐码元处理、长度不变**,所以归一串的下标能直接当原文下标用)、
  `tokenize()`(连续 CJK 一段、连续字母数字一段)、打分与片段切分。

约束:

- 看板对工作空间**只读**,一切工作空间内路径过 `resolveInside()`;不允许为检索落索引文件。
- 服务端 `.mjs` 没有类型检查也没有测试;前端 TS strict,`tsconfig` 的 `include` 只有 `src/app`。
- 常驻服务不热更,新字段一律可选 + 前端兜底(用户可能跑着旧进程配新前端)。
- 组包脚本只拷 `bin/cli.mjs` + `src/server/` + `dist/` + `templates/`(`scripts/build-npm-package.mjs`),
  服务端引用到的任何新目录必须同步加进去。

## Goals / Non-Goals

**Goals:**

- 数据页的检索覆盖**整张表**,并且大表(十万行以上、几十 MB)下不把整表拉进浏览器、不 OOM、
  不撞 413。
- 命中能**定位**:知道是第几行,能翻到那一页并高亮那一行。
- 扫描**有边界**:命中够了就停、时间到了就停,并如实说明停在哪。
- 旧服务进程 + 新前端不炸,退回到改动前的行为。
- 匹配语义在两侧**可解释**:哪怕整表检索与文内检索规则不同,也要在界面上说清楚。

**Non-Goals:**

- 不做跨文件、跨表检索(那要服务端建索引,是另一件事)。
- 不做正则 / 大小写敏感 / 整词匹配等高级选项,不做列筛选与排序。
- 不做命中结果的导出、另开列表页、批量操作。
- 不为检索维护任何常驻缓存或磁盘索引(`/table` 已有的行数缓存不在此列)。
- 不改 csv 的解析口径:服务端仍然不引 CSV 解析库。

## Decisions

### D1 · 整表检索放服务端流式扫描,不放前端

**选:** 新接口 `GET /api/projects/:id/table-search?path=&q=&limit=`,复用 `readCsvPage` 那套
`readline` 流,逐行归一后判定,命中就记 `{ row, line }`,攒够 `limit` 就 `rl.close()` 提前返回。

**为什么不选前端循环翻页拉全表再本地搜:** 分页接口存在的理由就是"整表进不了 JSON",
为了搜索再把整表拉回浏览器,等于把当初躲开的 413 与内存压力原样搬回来,而且十几万行的
DOM/JS 对象在切文件时还得靠 GC 收拾。

**为什么不选建索引 / 塞进 SQLite / 调 ripgrep:** 索引要落盘,直接撞只读红线;SQLite 要加依赖、
要处理失效与重建;`rg` 不在 PATH 时还得写一条降级路径。这三条都远超"本机只读看板"的定位,
而流式扫一遍几十 MB 的文件在本机是百毫秒级的事,不值得为它换架构。

### D2 · 匹配语义:同一行命中**全部**关键词,结果按**行号**先后排

**选:** 查询串按现有 `tokenize()` 切词,一行的归一文本必须**包含每一个词**才算命中;
结果不排序,按文件里的先后给出。

**为什么不沿用文内检索那套"命中一部分也算、按命中词数排序":** 那套要给全表每一行打分、
维护一个 top-N 堆,**必须读完整个文件**才能确定前 50 名 —— 提前收流的省事就没了,而且
十几万行的表里"只中一个词"的行可能上万条,排出来的前 50 条对用户没有意义。
按行号先后 + 全词命中,既能在攒够结果时立刻停,语义也更贴表格的用法("找到那一行")。

**代价(必须写进 spec 与界面):** 同一份转换包,「摘要」页(markdown,模糊排序)和「数据」页
(整表,全词命中)的搜索结果口径不同。界面上用结果区的说明文字点破:整表检索标明
"整表 · 按行号",零命中时说明"要求一行里出现全部关键词"。

**备选(已否决):** 服务端也做模糊打分 + 全表读完 —— 大表下每次改词都要完整读一遍文件,
输入防抖也救不回来;收益只是口径统一,不值当。

### D3 · 匹配内核抽成共享 `.mjs`,不各写一套

**选:** 把 `normalize()` / `tokenize()` 两个纯函数搬到 `src/shared/textMatch.mjs`(JSDoc 注类型,
零依赖、不碰 DOM、不碰 Node API),`src/app/lib/fuzzySearch.ts` 从它 re-export 并继续对外提供
现有签名(调用方一个都不用改),`src/server/http.mjs` 直接 import 同一份。
`tsconfig.json` 打开 `allowJs`(不开 `checkJs`)让 TS 从 JSDoc 推类型;
`scripts/build-npm-package.mjs` 的拷贝清单加上 `src/shared`。

**为什么:** 两侧切词口径必须一致。不一致的表现很隐蔽 —— 服务端判定命中、前端却因为切词
不同而一个词都加不了粗,或者用户输入全角关键词在数据页搜得到、在摘要页搜不到。
这类 bug 没有类型检查兜底,只能靠"只有一份实现"来杜绝。

**备选 A(已否决):** 服务端复制一份四十行的归一分词,
加一个 `scripts/check-text-match.mjs`,用 `node --experimental-strip-types` 同时 import
TS 版与 `.mjs` 版,在一组固定语料上比对 `tokenize` 输出并接进 CI(仓库已有 `test:anchor`
用同样的手法)。好处是不动目录结构、不动 tsconfig、不动组包脚本;坏处是两份实现真的会漂,
校验脚本只在有人跑的时候才拦得住 —— 否决就否决在这一句。

**备选 B(否决):** 前端直接 import `src/server/**` 里的模块 —— 平面反向依赖,比多一个共享目录
更坏。

**已拍板走这条。** AGENTS.md 第 3 节现在只描述两个平面,新开 `src/shared/` 是文档级约定的变更,
落地时同步改那份文档,并写死这个目录的边界(只放纯函数)。

### D4 · 服务端按**原始行文本**判定,片段留给前端切

**选:** 服务端不解析 CSV,直接对整行原始文本做归一 + 包含判定,命中就把 `{ row, text }`
原样返回(`row` 是从 0 起的数据行序号,不含表头)。前端拿到后用已有的 papaparse 解析**这一行**,
把单元格用空格拼成展示文本 —— 与 `collectBlocks()` 里表格分块的拼法一致 ——
再用现成的 `toSnippetParts()` 切出加粗片段。

**为什么:** 服务端不必引 CSV 解析库,也不必处理引号内换行的多行记录(见风险);
片段切分与加粗的逻辑只有前端一份,渲染口径天然一致。

**代价:** 分隔符与引号本身参与匹配。搜 `a,b` 这种带逗号的串可能匹配到"a 列结尾 + b 列开头"
的拼接处。`tokenize()` 会把逗号当分隔符切掉,所以实际影响只落在"关键词跨列相邻"这种边角情形,
与文内检索按行拼接单元格的行为其实一致,可以接受。

### D5 · 扫描的边界:命中上限 + 时间预算 + 客户端中断

- **命中上限** `limit`(默认 200,上限 500):攒够就 `rl.close()`,响应带 `truncated: true`。
- **时间预算**(默认 5s):每扫若干行看一次时钟,超了就停,响应带 `partial: true` 与
  `scannedRows`,界面如实说"只扫到第 N 行,后面没扫"。**宁可说没扫完,不能让用户以为搜遍了**。
- **客户端中断**:`req.on('close')` 里关流,前端用 `AbortController` 在改词 / 关检索条 / 换文件时
  取消上一次请求。不这么做的话,用户连打五个字就有五次全表扫描在后台跑到底。
- 前端对远端检索的防抖比本地长(约 350ms),避免逐字触发扫描。

**为什么不做扫描结果缓存:** 同一路径 + 同一 query 命中的缓存收益极小(用户很少原样重搜),
而缓存失效要跟 mtime 绑,复杂度不划算。行数缓存已有,继续复用。

### D6 · 命中定位:行号 → 页码 → `<tr>`

- `CsvGrid` 给每个 `<tr>` 挂 `data-row-index`(绝对行号 = `page * pageSize + i`)。
- `PaginatedCsvTable` 通过 `useImperativeHandle` 暴露 `jumpToRow(row)`:算出目标页,
  已在该页就直接找 `<tr>` 交给 `SearchJumper`;不在就 `setPage()`,等这一页数据到位后
  (在 fetch 的 `then` 里根据一个"待跳转行"的 ref)再定位。
- `Reader` 持有这个 ref 并传给 `PreviewSearch` 的选中回调。

**为什么不把 `page` 提到 `Reader`:** 分页是表格自己的事,提上去会让 `Reader` 多背一份与
sheet 切换、路径变化纠缠的状态;命令式句柄的耦合面更小,只暴露"跳到第 N 行"这一件事。

**为什么不改用锚点/滚动位置持久化:** 跳转是一次性动作,用完即弃,不需要状态。

### D7 · `PreviewSearch` 用"结果源"抽象容纳异步

给组件加一个可选的异步结果源(签名形如
`source?: (query, signal) => Promise<{ hits, total, truncated, partial, scannedRows }>` +
`onPick(hit)`),不传就是现在的本地 DOM 检索。开合、防抖、上下键、Enter、Esc、输入法让位
这些行为一份实现,两种数据源共用。异步态多出三种展示:检索中、失败、部分结果。

**为什么不另写一个 `TableSearch` 组件:** 键盘与输入法那套(`isComposing` / `keyCode 229` /
组合期让出整条快捷键链)是这个功能里最容易写错的部分,复制一份必然漂。

### D8 · 旧服务进程的降级

`api.tableSearch()` 收到 404(旧进程没有这条路由)时,前端**退回改动前的行为**:
对当前页的 DOM 做本地检索,并保留"表格只搜当前这一页,不是整张表"的说明。
判据只认 404,其它错误(500 / 网络断)如实报错,不静默降级成"只搜了一页"——
那会让用户以为整表里没有。

## Risks / Trade-offs

- **引号内含换行的 CSV 记录会被拆开判定** → 行内换行的记录,`readline` 看到的是两"行",
  匹配可能落在半条记录上,行号也会与 papaparse 在前端算出的记录序对不齐。
  这个偏差**现有的 `/table` 分页早就存在**(它也是按物理行分页的),本 change 不引入新问题,
  但也不修:修它要在服务端做带引号状态机的行切分,属于另一件事。在 spec 里写明这一限制。
- **大表全扫的耗时** → 命中稀少的关键词在几十 MB 的表上要读完整个文件。时间预算兜住上限,
  界面显示"检索中",且用户改词时上一次扫描会被中断。
- **两处搜索口径不同引发困惑**("摘要页搜得到、数据页搜不到") → 结果区文案点明"整表 · 按行号,
  要求一行里出现全部关键词";零命中文案也照此说明。
- **共享目录带来的第二处跨平面耦合** → 只放纯函数(无 DOM、无 Node API、零依赖),
  并在 AGENTS.md 里写清这个目录的边界;组包脚本同步拷贝,靠 `pnpm pack:npm && pnpm smoke:npm`
  兜住"装出来跑不起来"。
- **扫描期间表格被改写** → 响应带 `mtime`;点结果时若表格当前 `mtime` 已变,提示重搜,
  不假装跳成功(行号可能已经不指向那条记录)。
- **`allowJs` 打开后的连带影响** → 只影响被 import 到的 `.js/.mjs`;不开 `checkJs`,
  不会把服务端那堆无类型的 `.mjs` 拖进 `tsc`。落地时用 `pnpm typecheck` 确认耗时与报错数不变。

## Migration Plan

无数据迁移。上线顺序:服务端先加路由(纯新增,不改 `/table` 的任何行为)→ 同步 `api.ts` 契约 →
前端接入 → 组包脚本补目录。回滚就是撤掉前端接入,接口留着也不影响任何现有页面。
用户侧要做的只有一件:**重启常驻服务**,否则新前端会一直走 404 降级(功能可用,只是仍旧
只搜当前页)。

## Open Questions

- `limit` 默认 200 / 时间预算 5s 是拍的数,要在真实大表上试过再定;结果列表在超过百条时
  是否需要"继续扫描"的按钮,先不做,等实际用下来再说。
- 多表转换包里,是否需要"在本包所有表里搜"?现在明确只搜当前选中的表 —— 等有人真的要了再说,
  那会是新的一次 change。
