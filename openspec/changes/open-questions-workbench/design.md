## Context

工作空间模板里，未决问题一直存放在单份 `output/analysis/open-questions.md` 的 markdown 表格里。
9 个技能会往里追加，没有任何技能负责取出。一份真实在用的工作空间实测：231 条、175 条未关闭、
41 个按日期追加的分节、平均 200 字/条（最长 900+ 字）全挤在表格单元格里、未关闭里约一半标「高」、
另有 12 条正文已写「已解决」但编号没划掉。

约束来自三处：

- **看板对工作空间只读**（AGENTS.md 不变量 1）。本 change 的三期要突破它，是第四条窄例外，
  且与前三条不同 —— 前三条都是「看板只 `spawn`、工作空间自己的脚本写盘」，这次是看板自己写。
- **服务端没有类型检查也没有测试**，`src/server/**` 是 `.mjs`，改完只能靠重启 + 手点验证。
- **`templates/` 是另一套语境**，本仓编码规范不适用于它内部，而且「放进去就是发出去」。

前端与服务端的既有件基本够用：`src/server/frontmatter.mjs` 是手写的扁平 YAML 解析器，
`src/server/scan.mjs` 已经在做「扫目录 + 读 front-matter + 路径守卫」，
`ImageLightbox.tsx` 已有方向键翻页的范式，`dialog.tsx` / `scroll-area.tsx` / `badge.tsx` 已 vendored。
缺的是全局快捷键 —— 本仓现有 keydown 全是组件局部的。

## Goals / Non-Goals

**Goals:**

- 让问题清单从「只有入口没有出口」变成有进有出：每条问题都有一条低成本的消解路径，
  不是只有「被回答」一种结局。
- 让排序轴从自我评估的优先级换成客观的「阻塞哪个在途交付物」。
- 把 AI 的推断与实证在数据上分开，使「未知被伪装成确定事实」在结构上无处藏身。
- 让 agent 每次只拿到一个分组的几条问题，而不是一份两百多条的大文件。
- 为后续突破只读（产出文档归档）留下一个可复用的写入收口，而不是每加一个功能开一个新口子。

**Non-Goals:**

- **不做产出文档的归档管理。** 它是另一个突破只读的契机，但不在本 change。
- **不做问题的自动分类与自动回答。** 凭据与阻塞对象都不自动推断。
- **不做多人协作与冲突合并。** 看板是本机单人工具，并发只发生在「人」与「本机 agent」之间。
- **不改 `output/decisions/` 的写入方式。** 决策草稿仍由 agent 生成，看板不写。
- **不追求把存量 231 条一次补全。** 迁移只负责搬运与标记，补 `blocks` / `evidence` 是持续的人工动作。

## Decisions

### 1. 一问一文件，服务端扫目录现算索引

**选**：`questions/Q<编号>.md` 一问一文件；服务端扫目录读 front-matter 拼出清单，不落任何索引文件。

**备选 A：单文件结构化数据（questions.yaml），markdown 由脚本生成。**
不选，因为卡片正文是长 markdown（要渲染引用、表格、链接、跳转）。塞进 YAML 的多行字符串里，
渲染别扭，而且 git diff 仍然是整块重写 —— 现在「200 字/条」的病会原样复发。
迁移成本确实更低，但它把问题留在了原地。

**备选 B：一问一文件 + 生成一份 `index.yaml` 供快速读取。**
不选。生成物会漂：agent 改了某个问题文件、忘了重新生成索引，索引就开始骗人。
**而「状态写在正文、索引没跟上」正是现存那 12 条冲突的成因** —— 不能用同一个机制去修它自己造成的病。

扫目录的成本是可接受的：只读每个文件的 front-matter 段（不读正文），两百个文件在几十毫秒量级，
与 `scan.mjs` 现在做的事完全同构，SSE 目录监听也是现成的。

### 2. front-matter 保持扁平，不引入 YAML 依赖

**选**：字段形状限制在 `key: value` 与 `key:` + `- item`，复用现有 `frontmatter.mjs`。

**备选：启用已在 `dependencies` 里的 `yaml@2.9`，支持嵌套结构。**
不选。现有解析器的注释明说「不引入 yaml 依赖」，这是服务端刻意保持瘦的一部分；
更重要的是，**扁平限制反而是这个设计想要的**：它强制 `title` 是一句话、`blocks` 是一个交付物名，
使条目长度由结构管住而不靠自觉。这正是要解决的核心问题。

**代价**：轮次历史无法用嵌套结构表达，只能放进正文的小节里。接受 ——
轮次主要是给人翻的，机器只需要知道「有没有历史」，不需要逐轮结构化读取。

### 3. 并发用字段分区，不用乐观锁

**选**：人只写 `status` / `human_answer` / `human_note` / `due`；
agent 只写 `ai_conclusion` / `ai_evidence` / `ai_source` / `flows_to`。服务端拒写 AI 区字段。

**备选：写入时带 mtime 或 hash 做乐观锁，冲突则提示重载。**
不选。**并发在这个流程里是常态不是意外** —— 流程本身就是「人点保存 → 立刻复制 prompt → agent 开始改同一条」，
两者在几秒内动同一个文件是设计预期的行为。乐观锁会把这种正常情况变成频繁的冲突提示，
而人和 agent 改的其实是**不同字段、根本不冲突**，那些提示全是误报。

字段分区把「不冲突」这件事变成物理事实，比检测冲突再让用户处理更简单也更可靠。

**残留风险**：agent 技术上能写任何字段，约定靠技能文档约束。缓解见 Risks。

### 4. 看板直接写盘，不 `spawn` 工作空间脚本

**选**：服务端自己写问题文件的人写区，收口在一个模块里。

**备选：沿用前三条例外的形状 —— 看板只 `spawn`，由工作空间自己的脚本写盘。**
不选，两个原因：

1. **没有现成脚本可以承接。** 资料转换有 `ingest.py`、新建工作空间有 `init_workspace.py`、
   原型刷新有 `workspace-sync.mjs`，它们本来就存在且有独立价值。为「保存一次人工反馈」专门造一个
   子进程入口，只是为了绕开红线而绕路。
2. **人工反馈是高频小写入。** 用户点一下保存就是一次写入，连着消解十条就是十次。
   每次起一个 Node/Python 进程，延迟和开销都不可接受，交互会变得很钝。

这是第四条例外与前三条的实质差异，已在 proposal 里单独标出留给人拍板。
作为交换，写入面被压到最小：只改已存在文件的指定字段，不新建、不删除、不改名，
且拒绝一切 AI 区字段。

### 5. prompt 贴路径，不贴正文；批量范围跟随分组

**选**：prompt = 指令 + 文件相对路径列表；批量默认只含当前分组。

**备选 A：把问题正文贴进 prompt。**
不选。批量十条会直接把粘贴区撑爆；而且贴进去的是快照，agent 读文件才能拿到最新内容
（人可能刚改过补充输入）。

**备选 B：批量复制「全部待 AI 更新」。**
不选。那批条目会横跨多个交付物，agent 拿到后上下文是散的 ——
**这正是本 change 要消除的问题，不能从 200 条缩到 10 条就当解决了。**
分组本来就是注意力单元，批量范围跟着它走。

### 6. 迁移只搬运与标记，不推断

**选**：`blocks` 与 `evidence` 一律留空；状态冲突与疑似非问题条目单独出一份待裁定清单。

**备选：按分节名推断 `blocks`、按正文关键词推断 `evidence`。**
不选。`evidence` 自动推断是自相矛盾的 —— **自动填出来的凭据本身就是虚假确定性**，
而这个字段存在的全部意义就是防止它。`blocks` 机械推断（按分节名匹配）在原型上试过，
能出结果，但那些结果看着合理、实际靠不住，反而比留空更危险：留空会被人看见，错的分组不会。

存量的 12 条状态冲突同理不自动裁决：它们正文里写的是「已解决」「部分解决」「不再阻塞」
「改写升级为另一条」等好几种不同语义，机械判定必错。

## Risks / Trade-offs

- **[迁移后有大量字段空着，人工补齐工作量大]** → 不要求一次补完。先补在途交付物相关的那几组，
  其余留空沉在 backlog 里。清单默认不显示 `blocks: backlog`，空着不会造成视觉负担。

- **[第四条例外让看板首次自己写工作空间，红线被削弱]** → 三重收口：
  写入面压到「改已存在文件的四个字段」、六条约束逐条写进 AGENTS.md、
  服务端硬拒绝 AI 区字段。并且这个模块要设计成后续归档功能能复用的形状，
  避免「每加一个功能开一个新口子」。

- **[agent 不遵守字段分区，写了人写区]** → 约定无法用代码强制（agent 直接改文件）。
  缓解：校验脚本能检出非法组合（如 `我方推断` + `answered`）；看板把这类条目显示为 `conflict`，
  让违约可见而不是静默生效。

- **[模板改动「放进去就是发出去」]** → 一期先在单个工作空间里试跑迁移与新技能，
  验证过再进 `templates/`。模板里的旧工作空间不会自动获得新结构，
  技能需要能同时应对「有 `questions/` 目录」和「只有旧表格」两种形态。

- **[服务端无测试，写入逻辑出错会损坏用户数据]** → 写入前读原文、只做字段级替换、
  失败不留半截文件（先写临时文件再原子替换）。手工验证清单进 tasks。

- **[标准答案可能被当成「随手点掉」的按钮，降低思考质量]** → 这是真实代价：
  消解变容易之后，人可能不假思索地点「本期不做」。缓解只能是让 `dropped` 可筛、可回溯、可重开，
  而不是限制消解本身 —— 让问题堆到两百条的代价更大。

## Migration Plan

三期，每期独立验收，前一期不完成不开始下一期。

1. **一期（数据契约）**：迁移脚本 + 新技能 + 单工作空间试跑。此期**不碰看板**，
   验收标准是「问题文件结构可用、人能直接读写、校验脚本能查出非法组合」。
   验证通过后再改 `templates/` 里的 9 个写入方技能。
2. **二期（只读呈现）**：服务端读接口 + 前端弹窗。此期**不写任何文件**，红线未动。
   验收标准是「弹窗能在任意视图唤出、分组与筛选正确、旧服务进程有降级提示」。
3. **三期（写入闭环）**：写入接口 + 标准答案 + prompt 复制。此期动红线，需人拍板后开始。

**回滚**：一期保留原 `open-questions.md`（只在开头加一句指向 `questions/` 的说明，不删内容），
出问题可以直接退回旧流程。二期回滚只需前端不渲染入口。
三期回滚需同时撤掉写接口路由与 AGENTS.md 的第四条例外。

## Open Questions

- **自由文本补充输入要不要保留？** 参考实现（公开项目 [Agira](https://github.com/gdsanger/Agira) issue #342
  的同类机制，它的「标准答案」一节是本 change 四个消解出口的直接来源）标准答案与自由文本都有，
  但自由文本可能把人重新拖回写长文的老路 —— 而那正是「200 字/条」的成因。
  倾向保留但限制长度，一期试跑后再定。
- **`blocks` 的取值从哪来？** 手填容易写出同义不同名的分组（「交底包」与「交底文档」）。
  是否需要在工作空间里维护一份在途交付物清单供选择，一期试跑时观察。
- **归档功能要复用这个写入收口到什么程度？** 归档要移动/改名文件，比本 change 的「改字段」
  写入面大得多，可能撑不下同一套约束。三期实施时一并评估，不在本 change 里预留抽象。
