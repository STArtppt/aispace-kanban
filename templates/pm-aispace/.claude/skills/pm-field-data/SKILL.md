# 现场实测数据核验

资料告诉你**设计上应该有什么**，现场数据告诉你**实际上有什么**。两者差多远，
决定了一个场景现在能不能做、要先补什么。这个技能负责把后者变成可查、可引用的证据。

**核心纪律：不要把导出文件或事实表读进上下文。** 几十万行进上下文既烧 token 又不准，
一律走 SQL 取回需要的几十行。

手写 Markdown 的写法（front-matter 形态、标题层级、文档间链接、哪些语法现在先别用）见工作空间 `AGENTS.md` 的「Markdown 写法」一节，这里不复述。

## 三步

### 1. 放进 `input/raw/` 的一个子目录

一个数据集一个目录，例如 `input/raw/现场数据/`。目录名就是产物目录名，起个能认出来的名字
（`现场数据`、`水情实时数据-8月`、`SC-02发电数据`）。**别散放在 `input/raw/` 根下**——
按目录成集是脚本识别数据集的方式。

### 2. 转换

```bash
python3 scripts/realdata.py --dry-run   # 先看识别到的列映射和时间格式对不对
python3 scripts/realdata.py             # 实际转换（幂等，内容没变就跳过）
python3 scripts/realdata.py --force     # 强制重建
```

脚本靠**表头**识别，不看扩展名。两种形态：

- **测点时序**：测点标识 + 时间 + 数值 → `实测数据.sqlite`
- **日指标**：期间 + 组织 + 指标 + 数值（太极 `t02_product_day` 这类）→ `日指标.sqlite`，组织名连已转换的组织表，指标名连指标字典

**一个导出文件 = 一个数据集 = 一个库**（现场常一次导好几张表，各表互相独立，合成一个反而混）。
产物按镜像规则落在 `input/converted/<raw 相对目录>/`。测点时序以 `wds_real_data.csv` 为例：

| 文件 | 用途 |
| --- | --- |
| `现场数据/_manifest_wds_real_data.md` | **先读这个**。规模、时间范围、覆盖分布、质量体检、表结构、SQL 范例都在里面 |
| `现场数据/SplittingObject/wds_real_data/实测数据.sqlite` | 主产物。`测点` 维表 + `实测` 事实表 + `日统计` + `v_实测` / `v_日统计` 视图 |
| `现场数据/SplittingObject/wds_real_data/测点覆盖清单.csv` | 一行一个测点，可直接发给现场对接人核对 |
| `现场数据/SplittingObject/wds_real_data/日统计.csv` | 一行一个测点一天，Excel 就能看趋势 |
| `现场数据/SplittingObject/wds_real_data/未匹配测点.csv` | 字典里查不到的测点（有才生成）——**这就是缺口本身** |

日指标（`t02_product_day.csv`）主产物是 `日指标.sqlite`（`组织` / `指标` / `日指标` / `覆盖` / `v_日指标`）+ `覆盖清单.csv`。查厂站日值先读它的 `_manifest_*.md`。

具体路径别硬记，从 `_manifest_*.md` 的 frontmatter `payload:` 读，或直接看脚本输出。

`--dry-run` 输出里要盯三件事：

- **列映射对不对**（时序是 `测点=senid 时间=time 数值=v`；日指标是 `期间=period_id 组织=orgz_code 指标=measure_code 数值=measure_value`）。认错了在 `scripts/realdata.py` 顶部的别名表里加一行，别改数据。
- **时间格式对不对**。`13/8/2026` 这种斜杠日期，两段都 ≤12 时脚本判不出日月顺序，
  会在台账里写明；确认后用 `--time-format "%m/%d/%Y %H:%M:%S"` 重跑。
- **一个文件都没识别到** → 表头缺三类列之一，先看看是不是导出时漏了列名行。

### 3. 读 `_manifest.md`，然后用 SQL 核验

台账已经把「有多少测点、覆盖哪些场站、采样间隔多少、哪些恒定不变、哪些完整率低」算好了。
在这个基础上做下面的体检，**每一项都用 SQL 取证，不要凭印象说**。

## 五项标准体检

查询模板见 [`references/sql-cookbook.md`](references/sql-cookbook.md)，那里是可直接改用的 SQL。
日指标把「测点」换成「组织 × 指标」，查 `覆盖` 和 `v_日指标`，不要套用测点时序的采样间隔口径。

| 体检项 | 问题 | 结论怎么用 |
| --- | --- | --- |
| **覆盖** | 场景需要的测点，现场有没有？ | 拿场景测点清单逐条对 `测点` 表。缺的进待确认清单，不要写"应该有" |
| **频率** | 实际多久来一条？和场景要求（如 5 分钟刷新）差多少？ | 看 `采样间隔秒`。整点小时数据支撑不了分钟级态势 |
| **连续性** | 有没有断流、缺测？集中在哪几天？ | 看 `完整率%` + 相邻点最大间隔。断在同一时段说明是采集侧问题 |
| **值域** | 值合不合物理常识？恒定不变的是不是卡死？ | 水位比对特征参数表的正常/死水位，流量出力不该为负 |
| **一致性** | 同一件事的几个测点对不对得上？ | 如全厂出力 ≈ 各机组出力之和；发电流量与出力的关系是否合理 |

## 写成产物

核验结论落到 `output/analysis/<日期>-现场数据核验-<数据集名>.md`，骨架：

```markdown
## 结论（一句话）
这批数据能支撑 X、支撑不了 Y，原因是 Z。

## 数据概况
时间范围、测点数、覆盖场站（引用 _manifest.md，不重复贴表）

## 按场景看可用性
| 场景 | 需要的测点 | 现场情况 | 判断 |
（"现场情况"列必须是 SQL 查出来的事实：记录数、间隔、完整率）

## 发现的问题
一条一个，带证据（测点ID + 数字），标注是**事实**还是 [推断]

## 要向现场确认的（每条同时落一份问题文件，见下节）
```

## 措辞纪律

- 台账里的 `完整率%`、`采样间隔秒`、`恒定值` 都是**统计口径**，不是现场承诺的指标。
  写成「按导出数据统计，该测点 8/13–8/20 实到 1540 条、约每 5 分钟一条、完整率 69.6%」，
  不要写成「该测点采集频率是 5 分钟」。
- 测点中文名、场站、单位来自 `input/converted/` 里的**测点字典**，字典本身未经现场确认。
  引用到对外文档前提醒用户核对，来源在 `测点` 表的 `字典来源` 列。
- **状态码 / 质量位的含义资料里通常没有**。看到 `状态码分布` 里有多种取值，
  不要自己解释成"异常"，写进待确认清单去问。
- 数据缺失 ≠ 现场没有这个测点：可能是这次导出没导、可能是测点在别的系统。
  区分「本次导出里没有」和「现场没有」，前者是事实，后者是推断。

## 遇到新形态

现场数据以后会不断来，形态会变（不同厂家、不同系统、不同导出工具）。扩展点都在
`scripts/realdata.py` 顶部，改一处即可，**不要为一次性数据写一次性脚本**：

- 列名不一样 → 加进对应别名表（时序：`ID_ALIASES` / `TIME_ALIASES` / `VALUE_ALIASES`；日指标：`PERIOD_ALIASES` / `ORG_ALIASES` / `MEASURE_ALIASES`）
- 时间格式不一样 → 加进 `TIME_FORMATS`（纪元秒/毫秒已支持）；日指标期间是 `YYYYMMDD`
- 测点字典 / 组织表 / 指标字典换了一份 → 脚本会自动扫 `input/converted/`，新字典转换进来就能用
- 日指标（一行 = 某组织某指标某一天）已经是正式分支，不要再写一次性脚本
- 真的对不上（比如一行一个时刻、一列一个测点的宽表）→ 那是新的形态，
  在脚本里加一个解析分支，并在这里补一行说明

## 衔接

- 上游：`pm-doc-ingest`（资料入库）、点表走 `scripts/pointtable.py`
- 下游：`pm-requirement-analysis`（用数据可用性调整需求优先级和验收标准）、
  `pm-prd-writing`（PRD 里的数据前提要引用核验结论）
- 缺口一律同时落成未决问题——**没有数据本身就是重要产出**

### 发现未决问题怎么落

**走 [`pm-open-questions`](../pm-open-questions/SKILL.md)，不要自己发明格式。**
先看一眼 `output/`：

- 有 `output/questions/` 目录 → **一问一文件**，新建 `output/questions/Q<四位编号>.md`（编号取当前最大加一；**目录空不等于从 Q0001 起**，先查 git 历史用过的最大编号）
- 只有 `output/analysis/open-questions.md` → 旧工作空间，照旧往表格里追加，**不要擅自迁移结构**

新结构下每条必须填 `source`（触发这条问题的文档路径）与 `context`
（触发时在做什么，一句话）—— 溯源锚点挂在**条目**上，不挂在分节上。
`blocks` 填它阻塞的在途交付物，判断不了就写 `backlog`，不要瞎填。
`evidence` 与 `ai_*` 刚提问时留空；**查不到依据只能写 `我方推断`，且不能置 `answered`**。

**双通道：正文归正文，问题归问题。** 分析结论写进文档，延伸出的未决问题写进问题文件，
**两边不许互串** —— 文档里不再放「待确认问题」表格（要提就写一句「见 `questions/Q0134`」），
问题条目里也不抄分析正文。同一条问题两处存在，很快就会对不上。

数据类的问题填 `evidence` 时特别要守住：核验结论有 SQL 查出来的数字撑着就是 `资料实证`，
只是「看起来应该是这样」就是 `我方推断` —— **推断不能关闭问题**。
