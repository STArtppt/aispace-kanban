## Why

不做的话,`output/` 下三类产出物都只有一个 `mtime`:一份分析有没有被后续文档吸收、
一份交付文档发出去之后对方说了什么、一条决策是不是已经被推翻 ——
**看板和 AI 都无从知道**。产出物的生命周期断在「文件存在」那一刻,
于是唯一的组织维度只剩时间序,列表只会单调变长。

`output/questions/` 已经解过同一个病:入口多、出口零,长到两百多条就被整份放弃。
那次的解法(一条一文件、扁平 front-matter 管住条目长度、客观排序轴、
人写区与 AI 写区物理隔开、四个标准答案一次点击消解一条)可以原样搬过来。

## What Changes

- **一份产出物一个记录文件。** `output/records/I<四位编号>.md`,与 `analysis/` `docs/`
  `decisions/` `questions/` 平级。记录是**我方视角的私有元数据**,不是产出物本身 ——
  `output/docs/` 里要发出去的文档保持干净,不塞状态、不塞反馈
  (`output/README.md` 已有的立场:「YAML 头对收件人是噪音」)。
  记录用 `target` 字段反链到产出物的工作空间相对路径,用 `kind` 字段区分三类。
- **三类产出物各有自己的状态机**,不共用一套 —— 分析中间产物不存在「发给对方」,
  硬套一套会出荒谬状态。`decisions/` 那套直接照搬模板 README 里**已有**的
  「待确认 / 已确认 / 已推翻」,只是把它从正文 bullet 提到 front-matter 让解析器读得到。
- **状态与反馈是一次交互。** 从该类的标准状态里选一个,紧跟一个补充说明输入框,
  保存成正文「## 状态流水」下的一条。反馈不是独立的一块,它就是状态变更的注解。
- **记录文件不进 `output/` 的三组列表。** 复用 `questions/` 的口径 ——
  三类合计的记录数会把「分析中间产物」那份清单整个淹掉。
  它走 ⌘K 工作台里自己的一页(不是「界面上不可见」,否则无处可点着写)。
- **⌘K 从「未决问题弹窗」变成工作台,分「未决问题 / 产出物」两页。** 现有 `QuestionsDialog`
  的内部整块保留成其中一页,只把最外层的 Dialog 容器剥出来做工作台外壳 —— 提壳,不动内脏。
- **看板可写状态与反馈。** 写入面压到 design 与 spec 里逐条列明,见下面「放宽只读红线」。

**本 change 不含**(各自独立立 change,因为**写入形状不同**,每种要单独论证红线):

- **批注搬进工作空间 + 逐条闭环** —— 服务端直写,但体量与频率的特征和状态写入不同;
  且要给每条批注加「已采纳 / 未采纳 / 待确认」并让 agent 回写,是对 `preview-annotation`
  的成套修改。**它依赖本 change 的记录文件作为批注的挂载点。**
- **归档链路** —— 点「归档」把陈旧产出物移进 `output/<三个目录>/一次归档/`,
  是 `spawn` 工作空间脚本的形状(看板自己不能 `rename`)。
  **它要读本 change 产出的状态**来判断哪些该归档。

## Capabilities

### New Capabilities

- `output-item-record`: 工作空间侧的数据契约 —— `output/records/` 的布局、编号规则、
  扁平 front-matter 字段、**按 `kind` 分化的三套状态机**、状态流水的写法、
  人写区与 AI 写区的分界、记录由技能建立。
- `output-item-workbench`: 看板侧的入口与接口 —— 工作台里产出物那一页、
  扫目录现算索引的读取接口、按状态分组的清单、状态与反馈的写入接口及其校验、
  旧服务进程配新前端时的降级。

### Modified Capabilities

- `open-questions-workbench`: 「全局弹窗与快捷键」这条要求变了 —— ⌘K 唤出的从「未决问题弹窗」
  变成工作台,未决问题成为其中一页。问题清单、分组、卡片、写入、prompt 复制这些要求
  **全部不变**(内部整块保留);变的只是它挂在哪、以及 `QuestionsFab` 的待处理计数
  是只数问题还是两页合计。

**已知缺口,本 change 不修**:`open-questions` 的 `blocks` 字段是自由文本的产出物名
(一个字符串),本 change 给了产出物真实编号之后,两边仍然对不上。
改它要动迁移脚本和存量问题数据,且得等编号体系先稳定下来才有得指 —— 留作后续。

## Impact

| 平面 | 影响 |
| --- | --- |
| 服务端 `src/server/**` | 新增 `records.mjs`(扫目录 + 读记录 + 写入收口);`scan.mjs` 确认排除口径并注明不喂反链的理由;`http.mjs` 加路由 |
| 前端 `src/app/**` | ⌘K 弹窗提壳成工作台(`QuestionsDialog` 内部不动,只剥外层容器);新增产出物那一页 |
| 契约 `src/app/lib/api.ts` | **动**。新增记录索引 / 详情 / 状态写入接口的封装与响应类型 |
| CLI `bin/cli.mjs` | 不动 |
| `templates/` | **动**。`pm-aispace` 要加 `output/records/` 骨架 + 目录 README(字段契约的事实源)+ 对应技能;`output/README.md` 要补这个平级目录;`decisions/` 的状态约定要从正文 bullet 挪进 front-matter。注意「放进去就是发出去」 |

**依赖**:不引入新依赖。服务端只用 `node:` 内置模块 + 已在 `dependencies` 里的 `yaml`。

**常驻服务兼容性**:新增接口字段一律可选,前端缺字段时退回改动前的行为。
旧服务进程配新前端时,产出物页取不到索引就显示空态,不白屏、不报错。
改完 `src/server/**` 必须重启 `pnpm serve` / `pnpm dev`。

### 放宽只读红线(已拍板 2026-09-22:同意)

本 change 要**扩大看板服务端对工作空间的写入面**,这是 AGENTS.md 不变量 1 的第六条窄例外,
也是第二条「**看板自己写盘**」形状的例外(与 `writeQuestion` 同形,前面几条都是「看板只 `spawn`,
工作空间脚本写盘」)。AGENTS.md 里 `writeQuestion` 那段现在写着「它与前三条**形状不同**」,
加完之后这个措辞要跟着改。

立项理由与 `writeQuestion` 逐条对得上:状态变更与补充说明是**高频小写入**
(三类产出物、每份多次状态流转);没有现成的工作空间脚本能承接;
为它造一个子进程入口只是绕路;每次起进程的延迟会让交互变钝。

写入面的具体边界(只改已存在的文件 / 不新建不删除不改名 / 只写人写区 /
请求只带编号不带路径 / 必须环回且非跨站 / 先写临时文件再原子替换)在 design 与 spec 里
逐条落定,照 `writeQuestion` 那六条的口径写。
记录文件的**新建**不归看板 —— 和 questions 一样由工作空间的技能负责,看板只改已存在的。

**已拍板**:同意把状态写入作为不变量 1 的第六条窄例外,按上述边界实现。
