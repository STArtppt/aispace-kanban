## Context

一份产出原稿 `output/<组>/<子路径>/<基名>.<扩展名>` 在工作空间里通过两种方式被找到:

1. **路径规则**(看板代码里写死的):交付稿镜像目录 `output/delivery/<组>/<子路径>/<基名>/`
   (`scan.mjs` 的 `deliveryDirOf`、`deliveryOf`),原稿的 Word 成品 `<镜像目录>/<基名>.docx`(`docxTargetOf`),
   还有旧布局下放在原稿旁边的 `<基名>.docx`(`deai.mjs` 的 `docxBeside`)。
2. **文本引用**(写在别的文件里的):
   - 结构性引用：记录 `output/records/I*.md` 的 `target:`(`findRecordByTarget` 靠它把批注挂到原稿上);
     交付稿 `v*.md` 和 `定稿.md` front-matter 里的 `source:`,`定稿.md` 的 `docx:`(`readFinal` 要求它必须落在镜像目录里);
     批注文件 `output/records/notes/I*.md` 的 `- 对象：` 行，里面既有原稿路径，也有 `output/delivery/…/v005.md` 这种交付稿路径;
     问题 `output/questions/Q*.md` 的 `source:` / `flows_to:`(可以带 `#锚点`)。
   - 正文链接：分析、决策等文档里的完整路径(`` `output/docs/x.md` ``)、相对链接 `[](../docs/x.md)`、
     wikilink(`[[output/docs/x]]`、`[[../docs/x|文本]]`、同目录裸名 `[[x]]`)。

在一个真实工作空间里实测过：一份有九版交付稿的原稿，被引用的地方分布在 1 份记录、3 份批注、7 份问题、
3 份分析/决策正文、全部交付稿和定稿的 front-matter,另外工作空间 `.claude/` 规则库的历史条目里也提到了它。

已经有一个可以照搬的先例：第七条"一次归档"(`runArchive` → `scripts/archive_output.py`)。
看板只 spawn,同步等脚本退出，脚本的中文报错原样带回前端。

## Goals / Non-Goals

**Goals:**

- 在看板上改名，原稿、镜像目录和所有引用一次改到位，在看板上点开新名字，和改名前看到的东西完全一样。
- 执行前能看到要改哪些文件、每个文件改几处(Obsidian 的"更新 N 个文件中的 M 处链接")。
- 失败时不留半截状态：要么全改，要么一个字节都不动。

**Non-Goals:**

- 不支持改目录名，也不支持跨目录移动(那是"移动",不是"重命名")。
- 不支持转换产物(`output/converted/`)。它是 ingest 的输出，改名后下次重新转换会再生成一份旧名的。
- 不改交付稿 `v*.md` 的正文(见决策 5)。
- 不改 `.claude/` 规则库、`input/`、`visualization/`、`output/converted/` 里的任何提及。
- 不做撤销按钮。要撤销就再改一次名，脚本对称，改回去的效果相同。

## Decisions

### 1. spawn 工作空间脚本，看板不自己写

和第七条一样，由 `scripts/rename_output.py` 完成全部改动，看板只 spawn。

- 备选：看板服务端直写(直写族，类似第四、六、八条)。**不选**:直写族的前提是"高频小写入、没有现成脚本承接"。
  重命名一次要跨几十个文件，还要按 wikilink 规则解析链接。放在脚本里，工作空间的 agent 和人在终端也能用同一套
  (`python3 scripts/rename_output.py --source … --to …`),规则只有一份。
- 用户说的"配套脚本"就是这个意思。

### 2. 请求只带 `docKey` + 新基名，脚本拿到的是服务端反查出的路径

前端发 `{ docKey, name }`。服务端在新的 docKey 种类 `output-file`(三组下的所有文件)里反查出相对路径，
过 `resolveInside()` 之后，以 `--source <相对路径>` 传给脚本。脚本再校验一遍：路径必须在 `output/<三组>/` 之下，
不能是 `output/delivery/`、`output/converted/` 这类目录，也不能是符号链接。

- 备选：照第七条只收"组名 + 基名"。**不选**:那样子目录里的文件改不了名，而用户恰恰常在子目录里组织交付件。
  第九条已经确立了"不透明键 + 服务端反查"的做法，这里照用。
- 新基名只收**不带扩展名的 stem**,扩展名沿用原文件的。拒绝以下几类：空串、`.` 开头、包含 `/ \ \0` 或 `..`、
  包含 Windows 不允许的字符 `<>:"|?*`、等于 `一次归档`、超过 120 个字符、和原名相同。服务端和脚本各校验一次。
- 为了让非 `.md` 文件也能改名，scan 给三组的**所有**文件下发 `docKey`。前端「转成 Word」本来就按 `ext === '.md'` 判断，
  不受影响;`output-md` 这个种类只在 `.md` 里反查，非 `.md` 的键在第九条的接口上查不到，照样返回 400。

### 3. 先预览，后执行;执行时核对预览指纹

脚本有两种模式:`--dry-run --json` 输出完整计划(要改名的路径对、每个文件改几处、计划指纹 `plan`),
`--apply --expect <plan> --json` 重新计算计划，指纹不一致就退出码 3,服务端转成 409:"预览之后有文件变了，请重新预览"。

- 备选：一步执行，执行完再报告改了什么。**不选**:用户明确要求"先看到会改哪些再确定";而且改链接涉及 AI 写的正文，
  执行前应该让人看一眼。
- 备选：预览结果存在服务端内存里，执行时直接用。**不选**:要维护状态，服务重启就丢;重新计算再比对指纹，是无状态的做法。
- 指纹 = 计划内容(路径对 + 每个文件改写前的 sha + 改写后的 sha)的 SHA-256 前 16 位。

### 4. 链接识别规则与看板渲染器一致，只认"指向这个文件"的写法

改写对象分三类，都按"解析后是不是指向旧路径"来判断，不做纯字符串替换:

| 写法 | 判定 | 改写 |
| --- | --- | --- |
| 工作空间根路径 `output/<组>/…/旧.md`(反引号内、YAML 值、正文中) | 字面匹配，后面紧跟 `#`、空白、引号、反引号、`)`、`]`、`\|`、行尾之一 | 只换掉基名，`#锚点` 保留 |
| 镜像目录前缀 `output/delivery/<组>/…/旧/` 和 `…/旧`(加上上面那组边界字符) | 同上 | 换目录名 |
| 相对链接 `[文本](相对路径)` | 相对于**所在文件**解析后等于旧路径(或在旧镜像目录下) | 只改最后一个对应的路径段，保持相对形式 |
| wikilink `[[目标#标题\|别名]]` / `![[…]]` | 照 `markdownSyntax.ts` 的规则:`./` `../` 按相对路径解析，带 `/` 的从工作空间根算，裸名只认同一目录;省略 `.md` 也算命中 | 只改目标部分，原来有没有 `.md`、`#标题`、`\|别名`,都照原样保留 |

- 备选：全文替换旧基名。**不选**:基名常常就是普通词语(比如"实施方案"),正文里的同名说法会被误改。
- 原稿**自身**里的相对链接不用改：它所在的目录没变。镜像目录里的文件在目录改名之后，彼此之间的相对位置也没变。

### 5. 扫描范围和排除项

**扫描**:`output/**` 下的 `.md` / `.yaml` / `.yml`,以及工作空间根目录的 `project.yaml` / `project.yml`。

**排除**:
- `output/converted/`:ingest 的产物，重新转换时会被覆盖，改了也白改;
- `input/`:原始资料只读;
- `visualization/`:原型目录由同步脚本整份覆盖;
- `.claude/`、根目录的 `AGENTS.md`:规则库的历史条目是"当时针对哪份文件"的记录，模板文件由模板更新管理;
- 交付稿 `v*.md` 的**正文**:模板约定每版"写出后不再改动",而且 `body_sha` 会因此把它判成"有人绕过批注直接改了"。
  只改 front-matter 的 `source`;正文里的命中直接跳过，预览里也不列 —— 不改的东西不该占用户的注意力。

- 备选：扫整个工作空间。**不选**:上面每个排除项都有自己的理由，而且整个工作空间扫一遍会把 `input/` 里的大文件拖进来。

### 6. `source_sha` 跟着更新

另一份原稿 B 的正文因为链接改写而变化后，B 的交付稿里 `source_sha` 等于 **B 改写前 sha** 的那些版本，
`source_sha` 一起换成改写后的 sha;原来就不相等的(原稿在那一版之后真的改过)保持不变。
这样交付稿条不会因为一次改名，在其他文档上误报"原稿已变更"。

- 备选：不处理。**不选**:一次改名会让好几份不相关的文档同时冒出橙色提示，用户会误以为内容被改动过。

### 7. 落盘顺序：先暂存，再改名，最后替换

1. 计算全部改写结果(在内存里)。
2. 对每个要改写的文件，在它**最终所在的目录**旁边写一份临时文件(镜像目录内的文件，按改名后的位置算)。
   做法是先在原目录写 `.rename-*.tmp`,目录改名时它会被一起带走。
3. 改镜像目录名，然后改原稿名，然后改 `<基名>.docx`。任何一步失败都把已经做过的改名改回去，删掉临时文件，退出码 1。
4. 用 `os.replace` 逐个用临时文件替换目标文件。这一步失败的概率极低;万一失败，如实列出哪些文件还没更新，不做回滚。
   和 `archive_output.py` 的态度一样：说清现状，不靠再一次改名去补救。

- 备选：先改链接再改名。**不选**:改名失败时，链接已经指向一个不存在的新路径。

### 8. 冲突一律拒绝，不覆盖

以下情况都退出码 2,服务端返回 409,磁盘上一个字节都不动：新路径已经存在、新镜像目录已经存在、
镜像目录里已经有 `<新基名>.docx`、原稿旁边已经有同名 `.docx`。

### 9. 前端交互

- 菜单项「重命名」放在「归档」上面。转换产物标签的行菜单里显示为置灰，悬停提示
  "转换产物由资料转换生成，改名后下次转换会再生成一份旧名的;要改名请改 input/raw/ 里的原件"。
- 弹窗：输入框预填当前的 stem,扩展名作为不可编辑的后缀显示在旁边。输入停顿后(debounce 300ms)自动预览，
  显示"将改名 K 处，更新 N 个文件中的 M 处链接",可以展开文件清单(含记录的改名留痕)。排除范围里的命中不列。
  校验错误和冲突用 `--destructive` 色(需要注意)。「确定」只有在预览成功之后才可点。
- 执行成功后：收藏置顶里的旧路径换成新路径(`localStorage`,失败就忽略);如果阅读器正打开这份文件，跳到新路径。
  SSE 会自动刷新列表，不用手动重扫。

### 10. 能力探测

scan 新增 `canRename?: boolean`(`scripts/rename_output.py` 是否存在)。前端的判断：
`canRename === false` 时置灰，提示"这个工作空间没有改名脚本，更新模板后可用";
`undefined`(旧服务进程)时也置灰，提示"看板服务是旧版本，重启后可用"。
和归档不同，这里不放行旧进程：重命名弹窗一打开就会请求预览接口，旧进程会直接返回 404。

### 11. 改名在记录的「## 状态流水」里留痕

`target` 指向旧路径的那份记录(如果有),由脚本在「## 状态流水」末尾追加一条:

```
### <今天> · <当前 status>

改名:`output/docs/实施方案.md` → `output/docs/01实施方案.md`(看板「重命名」,状态未变)。
```

- 标题沿用 `### <日期> · <状态>` 的格式，`parseFlow` 能直接解析，记录详情里的流水照常显示;状态写**当前值**,
  不借留痕改变状态。
- 记录没有「## 状态流水」小节时，在文件末尾补上这一节再追加(记录契约本来就要求有这一节)。没有记录的原稿不留痕，
  也不为留痕新建记录(建记录是 `pm-output-record` 的活)。
- 这条追加和其他改写一样，走决策 7 的暂存 + 替换，计入预览和指纹。
- 备选：在 `一次归档/README.md` 那样的独立日志里记。**不选**:看板上找改名历史，最自然的地方就是这份产出物自己的记录;
  另起一份日志，又多一个要维护的文件。
- 备选：不留痕，靠 git。**不选**:工作空间不一定在 git 里，而且 AI 读记录时，需要知道旧名字才能对上历史对话里的提法。

## Risks / Trade-offs

- [改写 AI 写区字段(记录 `target`、问题 `source` / `flows_to`)时，工作空间的 agent 恰好在写同一个文件] →
  指纹核对能挡住预览到执行之间发生的变化;执行窗口在毫秒级，剩下的竞争窗口可以接受。用户说明里写一句"改名前先停下正在跑的 agent"。
- [链接识别有漏网之鱼，比如 HTML 里的 `<a href>`、代码块里的路径] → 只认 decision 4 列出的写法，其他写法不改，
  预览如实列出改了哪些地方。代码块里的路径同样按根路径规则改写，和 Obsidian 的行为不同，但在这里那些也是"指向这份文件"的引用。
- [scan 给非 `.md` 文件也下发 `docKey`,扫描负载略微变大] → 只是对相对路径做一次 SHA-256,和 `.md` 的开销一样，可以忽略。
- [用户手动改名已经造成断链(本次的起因)] → 不在本变更里做"修复断链"。恢复办法是在文件夹里把名字改回去，再到看板上改名。
  写进用户说明。

## Migration Plan

1. 模板新增脚本 → 已有实例通过 `template_update.py` 拿到(本机实例按 `local-source-sync` 推送)。
2. 服务端和前端发版。旧工作空间没有脚本时，菜单置灰并说清原因。
3. 批准后在 AGENTS.md 不变量 1 加第十一条，并在模板 AGENTS.md 里写"改名走看板"。
4. 回滚：删除菜单项和路由即可，脚本留在工作空间也无害(没人调用)。
