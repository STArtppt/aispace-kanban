## Why

不做的话，工作空间里的「待澄清问题清单」会继续涨到没人看的程度，最后被整份放弃 —— 而它恰恰是
接手阶段最有价值的产物之一。

模板里有 9 个技能会往 `output/analysis/open-questions.md` **追加**问题，
**没有任何一个技能负责把问题取出来**。只有入口没有出口，两个月就能长成下面这样
（数字来自一份真实在用的工作空间，写这份提案时实测）：

| | |
| --- | --- |
| 表格条目 | 231 |
| 未关闭 | 175 |
| 其中正文已写「已解决 / 不再阻塞 / 已定案」但编号没划掉 | **12** |
| 未关闭里标「高」优先级 | 约一半 |
| 按日期追加的分节 | 41 |
| 平均篇幅 | **200 字/条**，最长 900+ 字，全挤在一个 markdown 表格单元格里 |

三个症状是连着的：

1. **单条在长胖，不是条数在爆炸。** 两个月 231 条不算多，但每条 200 字 —— 问题条目已经变成研究笔记。
   根因是溯源锚点挂在**分节**上不在**条目**上，条目只能把上下文抄进自己的单元格来自救。
2. **优先级栏已无信息量。** 一半标「高」。因为「高/中/低」是自我评估，必然通胀。
3. **清单只有「被回答」一种出口。** 大量条目是 AI 延伸出的「要不要考虑 X」，
   它们不需要问任何人，但没有消解通道，就只能一直躺着还占着「高」。

更根本的是：这一个文件同时装着四种生命周期不同的东西 —— 待对方回答的活口、已关闭的墓碑、
研究笔记与证据链、以及「会上要点名的几句话」这类根本不是问题的东西。
一个容器四种用途，任何排序规则都不可能同时成立。

对 agent 也一样：单个大 markdown 无法切片，多个 agent 读同一份 231 条的文件，注意力必然涣散。

## What Changes

分三期，每期独立可验收。第三期单独拍板（见下节）。

### 一期：数据契约（落在 `templates/`，不碰看板）

- **一问一文件**：`output/questions/Q<编号>.md`，扁平 YAML front-matter + markdown 正文。
  字段形状迁就 `src/server/frontmatter.mjs` 现有的扁平解析器（`key: value` 与 `key:` + `- item`，
  **不支持嵌套**）—— 这个限制反而是好事，它强制 `title` 是一句话、`blocks` 是一个交付物名，
  **条目长度由结构管住，不靠自觉**。
- **排序轴从「优先级」换成「阻塞了谁」**：`blocks` 指向一个在途交付物。
  不阻塞任何在途交付物的沉到 backlog，不在主视图露面。取消 `高/中/低`。
- **四态状态机**：`open` → `pending_ai`（人已反馈、AI 还没更新）→ `answered` / `dropped`，
  外加 `conflict`（正文与状态不一致，迁移时识别出来的存量脏数据）。
- **凭据字段**：`evidence` 取值 `客户确认 / 资料实证 / 我方决策 / 我方推断`。
  **只有前三种能关闭问题；「我方推断」不能置为 `answered`**，只能进待验证假设。
  这是对「AI 把未知伪装成确定事实」的正面约束 —— 现存那 12 条状态冲突就是它缺位的结果。
- **人写字段与 AI 写字段物理分离**（见下条「并发」）。
- **产出契约改成双通道**：技能生成分析文档时，正文归正文、延伸问题归问题文件，**禁止互串**。
  9 个写入方技能逐个改，并新增一个负责**出口**的技能（关闭、归档、按 `blocks` 生成会议清单）。
- **存量迁移脚本**：解析现有表格 → 生成问题文件。`blocks` 与 `evidence` **不自动推断**
  （自动填出来的凭据本身就是虚假确定性），留空交人工过一遍；12 条状态冲突单独列出来等人裁。

### 二期：看板呈现（只读，不碰红线）

- **全局弹窗 + 快捷键**：任意视图下唤出，不挂在「产出文档」视图的生命周期里。
  本仓目前**没有全局快捷键**，现有 keydown 全是组件局部的，需要新加一个 App 级的 hook。
- **服务端扫目录现算索引**，不生成索引文件 —— 生成物会漂，而「索引和正文对不上」正是现在的病根。
  只读每个问题文件的 front-matter（不读正文），与 `src/server/scan.mjs` 现有的
  「扫目录 + 读 front-matter + 路径守卫」完全同构；SSE 目录监听复用现成的。
- **清单按 `blocks` 分组折叠**，每行只出「编号 + 一句话 + 状态点」。
  **分组计数跟随当前筛选重算**（否则切到「已消解」还看到未处理的分组数，点进去是空的）。
- **卡片翻页**：方向键上下翻，现成范式在 `ImageLightbox.tsx`。卡片正文按需单独取。
- **筛选器四个入口**，与状态机一一对应：`未处理 / 待 AI 更新 / 已消解 / 状态冲突`。
  「待 AI 更新」必须是可点的筛选，不能只是一个计数 —— 它是整个闭环的枢纽。
- **凭据常驻、来源折叠**：凭据只有四个值，一个角标的成本，**不许折叠**
  （折叠 = 默认不看 = 回到「已解决但不知道凭什么」）。
  「我方推断」用 orange，其余灰字。来源路径、轮次历史进 Collapsible。
  卡片上最多两个折叠区（「为什么需要」属于问题，「依据」属于结论），再多会变成手风琴。

### 三期：人机闭环（**需要放宽只读红线，见下节**）

- **四个标准答案**（单选）：`资料里应该有，待查证 / 我方自行决定 / 本期不做、不相关 / 确需对方答复`。
  给问题一个**回答之外的出口**，一次点击消解一条。
- **四个选项走向四条不同的路，按钮区跟着变** —— 它们不是平级的终点：

  | 选项 | 它其实是 | 后续动作 |
  | --- | --- | --- |
  | 资料里应该有，待查证 | 派给 AI | → `pending_ai`，「复制查证 prompt」 |
  | 我方自行决定 | 要产出决策 | → 生成 `output/decisions/` 草稿 |
  | 本期不做 / 不相关 | 真终态 | → 当场关闭，**不出现「复制 prompt」** |
  | 确需对方答复 | 派给人（对外） | → 进会议清单，**必须填「最迟答复」日期** |

  「确需对方答复」不填日期就没有任何机制逼它到期 —— 现存那批积压问题就是这么来的。
- **保存人工反馈**：写问题文件的人写字段区。
- **一键复制 prompt**，单条与批量两种。批量的默认范围**跟随当前分组**，不是全局：
  跨交付物的批量会把 agent 的上下文打散，那正是这个 change 想消除的东西，不能换个规模再犯一次。
  prompt 里贴**路径 + 指令**，不贴内容，让 agent 自己去读。
- **轮次而非覆盖**：AI 回写的结论不满意时要能再问一轮，上一轮痕迹保留，不覆盖。
- **结论回流正文的计数器**：AI 回写结论时一并填 `flows_to`（该更新哪份正文的哪一节），
  看板在已消解视图显示「N 条结论尚未回流正文」。
  问题关闭但知识没收敛，是「只有入口没有出口」的另一面，光靠关闭状态挡不住。

## ⚠ 需要拍板：放宽只读红线（第四条窄例外）

**三期会让看板往工作空间写文件。** 用户已在会话中明确表示要突破只读定位
（问题管理与后续的产出文档归档都是契机），但它改的是 AGENTS.md 不变量 1，
必须在这里单独列清范围，实施时一并写进 AGENTS.md。

与前三条例外不同的是：**这一次看板自己写盘，不是 `spawn` 子进程。**
资料转换、新建工作空间、原型刷新都是「看板只起进程、工作空间自己的脚本写盘」，
而人工反馈没有一个现成的工作空间脚本可以承接，为它造一个子进程只是绕路。
这是本条例外与前三条的实质差异，请一并拍板。

| 写哪里 | 谁写 | 范围 |
| --- | --- | --- |
| `<工作空间>/output/questions/Q*.md` | 看板服务端 | **只改 front-matter 的人写字段区 + 追加一个「人工反馈」小节**；正文与 AI 写字段区不碰 |

约束（越界即为 bug）：

1. **只允许改已存在的问题文件**，不新建、不删除、不改名；文件不存在一律 404。
2. **只允许写人写字段**（`status` / `human_answer` / `human_note` / `due`）与人工反馈小节。
   `ai_conclusion` / `ai_evidence` / `ai_source` / `flows_to` 由 agent 写，
   **服务端拒绝写这几个字段** —— 人和 agent 的写区物理隔开，是并发方案本身（见下）。
3. 必须用户在看板上点「保存」明确发起，无后台、无定时、无自动补全。
4. 必须环回（`allowMutations`）且非跨站（`rejectIfForeignOrigin`）。
5. 请求只带 `id`，**不接受任何路径**；落盘路径由服务端用 `resolveInside()` 拼。
6. `input/`、`output/` 下的其它一切、`project.yaml` 仍然只读。
   `output/decisions/` 的草稿生成走**复制 prompt 交给 agent**，不由看板写。

**并发不是意外，是常态。** 流程本身就是「人点保存 → 立刻复制 prompt → agent 开始改同一条」。
方案不用锁，用**字段分区**：人只写上半区、agent 只写下半区，物理上不打架，
比乐观锁简单也比它可靠。这也是约束 2 存在的理由。

## Capabilities

### New Capabilities

- `open-questions`: 未决问题的数据契约 —— 一问一文件的文件布局与 front-matter 字段、
  四态状态机与合法流转、凭据分级与「推断不能关闭」的约束、人写/AI 写字段分区、
  以及技能侧的双通道产出契约与存量迁移规则。
- `open-questions-workbench`: 看板侧的呈现与闭环 —— 全局弹窗与快捷键、
  扫目录现算索引的读取接口、按 `blocks` 分组的清单与卡片翻页、四个标准答案与分化的后续动作、
  人工反馈写入接口、单条与批量 prompt 复制、结论回流计数。

### Modified Capabilities

无。现有 6 份 spec（`code-preview` / `database-source` / `preview-search` /
`rich-doc-convert` / `spreadsheet-preview` / `table-scan-search`）的需求都不变。

## Impact

**平面影响**：

| 平面 | 改动 |
| --- | --- |
| `templates/` | 9 个写入方技能改产出契约；新增出口技能；新增存量迁移脚本。**另一套语境，本仓编码规范不适用于它内部**；放进去就是发出去 |
| 服务端 `src/server/**` | 新增问题读写模块（扫目录取 front-matter、按 id 取正文、写人写字段）；`http.mjs` 加路由。**无类型检查、无测试，改完必须重启并在浏览器点一遍** |
| 前端 `src/app/**` | 新增弹窗组件与卡片；App 级全局快捷键 hook（本仓首个） |
| CLI `bin/cli.mjs` | 不动 |

**契约**：动 `src/app/lib/api.ts`。新增接口字段一律可选 + 前端兜底 —— 用户可能跑着旧服务进程配新前端，
弹窗在旧进程下应当明确显示「服务端未提供未决问题接口，请重启服务」，而不是白屏或空列表。

**依赖**：不引入新依赖。front-matter 解析器 `src/server/frontmatter.mjs` 已有；
`yaml@2.9` 已在 `dependencies`（若最终需要解析嵌套结构再启用，当前方案刻意不需要）。
前端 `dialog.tsx`、`scroll-area.tsx`、`badge.tsx` 已 vendored 到位。

**不在范围内**：产出文档的归档管理（用户提到的另一个突破只读的契机）不在本 change，
但三期的写入收口应当设计成后续能复用的形状，而不是每加一个功能就开一个新口子。

**验收闸门**：`pnpm typecheck` + `pnpm build` 全绿，且**重启 `pnpm serve` 后在浏览器逐项点过**
—— 服务端没有静态检查也没有测试，typecheck 绿不等于做完。
