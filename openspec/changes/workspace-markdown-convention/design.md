## Context

起因是一个更远的目标:把工作空间的内容也按 Obsidian 式知识网来管
(双链、按属性建视图)。那件事**本变更不做**,但它决定了现在该怎么写字 ——
现在随手写下的每一份文档,将来都是要迁的存量。

现状里有三处具体的不匹配,都是实际读代码确认的:

**一、看板的渲染器不认 Obsidian 扩展。** `src/app/components/Markdown.tsx` 的管线是
`react-markdown` + `remark-gfm` + `rehype-raw`,没有任何 Obsidian 插件。
于是 `[[wikilink]]` 原样显示成裸文本、`> [!note]` 退化成普通引用块且标记露出来、
行首 `#标签` **被当成 H1 混进文档目录**。

**二、front-matter 解析器是自写的扁平 YAML 子集。** `src/server/frontmatter.mjs`
只认 `key: value` 与 `key:` + `  - item`。Obsidian properties 默认写的内联数组
`tags: [a, b]` 会被整体当成字符串 —— 不崩,但语义静默丢掉。

**三、wikilink 的前提在工作空间不成立。** wikilink 靠 vault 内文件名全局唯一来解析,
而 `input/converted/` 是 `input/raw/` 的镜像目录,满地 `_manifest_<名>.md`
与 `SplittingObject/` 下的同名分表,全局解析必然歧义。

与此同时有个现成缺口:`input/` 只吃 docx / PDF / xlsx / pptx,**网页类资料没有入口**。
公开标准、政策文件、友商文档站目前只能走 `visualization/references/` 采集成页面快照,
那是给人看的视觉材料,不是能进 `input/converted/` 被分析、被溯源的文本。

但这个缺口比看上去窄。`src/server/capture.mjs` 的参考采集已经在用
`single-file-cli`(spawn 子进程)抓**渲染后的自包含 HTML**,落在
`visualization/references/<slug>/index.html`;Playwright 是可选依赖,
动态 import、缺了整体降级(参考只出 `index.html`)。
也就是说「把 JS 渲染后的页面拿到本地」这件事**已经解决了**,
缺的只是「从这份 HTML 里提出正文」这最后一段。
这一点直接决定了下面决策五的形状。

约束:本变更全部落在 `templates/`,那是**另一套语境**(发给用户的工作空间模板),
看板三平面一律不动;而且看板对工作空间只读,任何写入方案都不能借道看板。

## Goals / Non-Goals

**Goals:**

- 定出一个**现在就能用、将来不用回头翻修**的 Markdown 写法子集。
- 让违约可见:给规范配一个可执行版本,而不是只写在文档里靠自觉。
- 给存量工作空间一条低风险的迁移路径。
- 补上网页资料入口,并让它从第一天就守这套规范。

**Non-Goals:**

- 不给看板加 wikilink / callout 插件。那是下一阶段,本变更定的子集正是为了**不依赖**它。
- 不引入 `.base` / `.canvas`。看板扫描器不认这两类文件,放进模板等于造一批
  只能在 Obsidian 里打开的死文件。
- 不引入 Firecrawl 或任何需要常驻服务的抓取栈(理由见决策五),
  也不做整站抓取 / URL 发现 —— 本变更的网页入口是**一次一页**。
- 不迁 `input/converted/` 的存量产物 —— 由脚本生成、重跑即覆盖。
- 不把工作空间变成 Obsidian vault(没有 `.obsidian/`、不装插件、不要求 Obsidian 在跑)。

## Decisions

### 决策一:定「双向安全子集」,而不是先给看板补插件

**选择**:先定一个 Obsidian 与看板渲染器**同时支持**的语法子集,禁用项标明
「因为看板暂不渲染,不是永久排除」。

**备选:先给 `Markdown.tsx` 接 wikilink / callout 的 remark 插件,然后全套语法放开。**
不选的理由有两条。其一是顺序:补插件是跨平面改动(前端渲染、可能牵连
锚点定位与目录提取那两个自写 rehype 插件),而写法规范是纯 `templates/` 的事,
把后者压在前者后面,等于让所有新文档在等待期里继续无规范地写。
其二更关键:**子集是单向加法**。今天按子集写的文档,将来插件到位后逐条解禁禁用项,
存量一份都不用改;反过来,先放开语法再发现渲染不了,要翻修的是已经写下的几十份。

**代价**:这段时间里 Obsidian 侧的表达力被压着用 —— 想画个 callout 只能用引用块加粗体。
接受,因为现在的主力阅读界面是看板,不是 Obsidian。

### 决策二:文档间引用一律用相对路径链接

**选择**:`[文本](../analysis/xxx.md)`。

**备选一:`[[wikilink]]`。** 前提不成立(见 Context 第三条),且看板里点不开。
**备选二:裸文件名提一句,不做链接。** 这是现状,看板里点不开、Obsidian 里也不成图。

相对路径链接是**目前唯一两边都支持**的形态:Obsidian 认它;看板的
`Reader.tsx` 会把它过一遍 `resolveRelative` 再转成 `api.fileUrl`,能直接点开。
将来真要转 wikilink,批量改写是机械的,而且那时 vault 结构已经定了、能算出唯一目标。

### 决策三:front-matter 扁平,且沿用 `questions/README.md` 已有的那条

**选择**:只允许 `key: value` 与 `key:` + `  - item`,把 `output/questions/` 已有的
扁平约束**扩到全部手写 Markdown**,不另立一条新规矩。

**备选:给看板换个完整 YAML 解析器,然后允许嵌套。**
不选:那是看板侧改动(服务端无类型检查、要重启验证),而且
`questions/README.md` 里已经写明白了 —— 扁平限制不只是迁就解析器,
它**强制条目长度由结构管住**,长文一律进正文。这个性质值得留着。

顺带一个好处:Obsidian properties 本身就是扁平 YAML,两边天然对齐,
只需要禁掉内联数组这一种写法。

### 决策四:校验与迁移都是工作空间自己的脚本,看板一概不碰

**选择**:`check_markdown.py` / `migrate_markdown.py` / `web_ingest.py` 三个都住
`templates/pm-aispace/scripts/`,由用户或 agent 在工作空间里直接跑。

**备选:让看板在界面上提供「校验 / 迁移」按钮,`spawn` 这些脚本。**
不选:看板对工作空间只读,窄例外清单里没有这一条,而清单的价值恰恰在于不被顺手扩张。
将来真要加界面入口,那要单独按 `AGENTS.md` 不变量 1 评估,本变更**不预留接口**。

`check_markdown.py` 的形态直接抄 `check_questions.py`:只读、只报告、
退出码 0/1/2、带 `--json`、文档字符串写明「契约变了这里要跟着变」。
它的作用不是阻止违约 —— agent 直接改文件谁也拦不住 —— 是**让违约可见,不要静默生效**。

### 决策五:提取的输入是本地渲染后 HTML,不是 URL

**选择**:`web_ingest.py` 的正文提取**吃本地 HTML 文件**,而不是自己去抓 URL。
取 HTML 的优先级是:① 该 URL 已经有 `visualization/references/<slug>/index.html`
就直接用它;② 没有就 spawn 一次 `single-file` 抓到临时目录,提取完即弃,
**不往 `visualization/` 写**(那是看板窄例外的地盘,工作空间脚本不掺和)。

**备选一:defuddle 直接吃 URL(本变更的初稿方案)。** 不选,有两个实打实的毛病。
其一,defuddle 拿到的是**初始 HTML**,SPA 形态的文档站正文是水合出来的,抓下来是空壳;
其二,同一个页面会被抓两次 —— 一次 `single-file` 存参考给人看,一次 defuddle 存
`converted/` 给 AI 看,两份内容还可能来自不同时刻的页面。

**备选二:引入 Firecrawl 自建实例。** 不选。自建栈要
Docker + PostgreSQL + Redis + RabbitMQ + Playwright 五件套,
而工作空间模板的使用者是 PM 不是工程师(`templates/pm-aispace/AGENTS.md` 开篇就写着
「需要用到脚本或命令时,你负责执行」)。更要命的是**自建恰恰拿不到它最值钱的部分**:
反爬层(fire-engine)、托管代理与代理轮换、截图与页面动作都是云端独有,
自建版的抓取底座就是 Playwright —— 而 Playwright 这层本仓已经有了。
付出四个常驻服务的代价,换来的能力与现状重叠。
它真正独有的是 crawl / map(整站抓取与 URL 发现),那是另一个问题,见下面的开放问题。

**代价**:`single-file` 从「参考采集的依赖」变成「网页入口也依赖它」,
它的缺失从影响一个功能变成影响两个。接受 —— 它本来就是采集链路的本体,
而且降级行为已经有成文分档可抄。

### 决策五之二:defuddle 包一层脚本,而不是把官方 skill 拷进模板

**选择**:提取那一步调 `defuddle` CLI,外面包 `web_ingest.py`,
落点、`_manifest_` 命名、忽略清单解析全部复用 `layout.py`。

**备选:直接把上游的 defuddle skill 放进 `.claude/skills/`,让 agent 自己决定落哪。**
不选:那份 skill 教的是「拿到干净 markdown」,对落点一无所知。agent 自己决定落点,
就会出现平铺在 `converted/` 根下、没有 `_manifest_`、没有溯源 front-matter 的产物 ——
「删 `converted/` 的某个子目录就等于删掉那批资料的全部产物」这个性质会被破坏。
两套落点规则并存比没有网页入口更糟。

另外 defuddle 正是 Obsidian Web Clipper 背后的提取库,与本变更的 Obsidian 方向同源 ——
但这只是顺带的好处,不是选它的理由;选它的理由是它只做提取这一件事、
是个单文件 CLI、零基础设施。

### 决策六:网页产物用 URL 充当 source,用正文摘要充当 sha256

既有转换脚本的溯源是 `source`(相对工作空间根的 raw 路径)+ `source_sha256`(原件摘要)。
网页两样都没有:没有 raw 原件,而且内容会在原地变。

**选择**:`source` 记 URL,摘要值记**提取出的正文**的摘要。
字段名沿用既有那套,不为网页另造词汇。
若正文来自某份已有的参考采集,再额外记一条指向
`visualization/references/<slug>/` 的相对路径 —— 那份自包含 HTML 就是这份产物的「原件」,
人要核对时能直接打开它。

**备选一:先把网页存成 `input/raw/` 下的 HTML 再走正常转换链路。**
不选:`input/raw/` 是「人类给的原始资料」且永不改动,往里写会模糊这条边界;
而且 `visualization/references/` 已经在存这份 HTML 了,再存一份是重复。
**备选二:用抓下来的 HTML 的摘要。** 不选:页面的广告位、时间戳、A/B 分桶会让
每次抓取的 HTML 都不同,幂等判断永远为「已变」。正文摘要才对应「内容真的变了没有」。

重抓且内容已变时**不静默覆盖** —— 旧产物可能已经被分析文档引用过了。

### 决策七:两个外部依赖各自明确失败,一律不静默降级

网页入口现在有两个 PATH 上的依赖,缺任何一个都**明确失败**,
分档抄 `capture.mjs` 已有的那套写法:

| 缺什么 | 行为 |
| --- | --- |
| `defuddle` | 打印安装命令、非零退出。提取是这条链路的本体,没有替代 |
| `single-file`(且该 URL 没有现成参考) | 打印安装命令、非零退出 |
| `single-file`(但该 URL 已有参考) | 正常工作 —— 本来就不需要再抓 |

**备选:降级成直接抓 HTML 转 markdown。** 不选:会产出一份看着正常、
实际塞满导航栏和广告、SPA 站干脆是空壳的产物,而它会一路流进后续分析 ——
静默的坏数据比明确的失败贵得多。这与 `ANYDOC_BIN` 解析不到时的处理同理。

注意这里与 `capture.mjs` 的分档**不完全一样**:那边缺 Playwright 是「成功但降级」
(参考少几张截图,本体还在);这边没有等价的可降级部分,
提取不出正文就等于没有产物。Playwright 在这条链路上不是依赖 ——
`single-file` 自带取页能力,截图不在网页入口的职责里。

### 决策八:迁移默认预演

`migrate_markdown.py` 是本变更里**唯一改写人类既有产物**的动作
(另两个脚本一个只读、一个只新增),所以默认只打印、落盘要显式加参数,
与既有 `migrate_questions.py` 同构。

迁移只做两件机械的事:补齐缺失的 front-matter 字段、把裸文件名引用改写成相对路径链接。
不碰正文措辞、不调标题层级 —— 那些要人判断,脚本猜错比不做更糟。
裸文件名在工作空间里匹配到多份同名文档时,跳过并列进「需人工处理」清单。

## Risks / Trade-offs

**[规范写了但 agent 不守] → ** 配 `check_markdown.py` 让违约可见,并在九个技能里各留一句引用。
但要接受:这是约定不是强制,校验闸只在有人跑它的时候起作用。
和 `check_questions.py` 面对的是同一种局面,处理方式保持一致。

**[禁用项将来解禁时,规范与存量文档要同时动] → ** 不会。禁用项解禁是单向加法,
存量文档本来就在子集内,一份都不用改。真正要改的只有 `AGENTS.md` 那一节的措辞。

**[defuddle 与 single-file 都是全局 npm 安装,用户环境不一定有] → ** 明确失败并给安装命令。
两个都不进本仓 `package.json` 任何一侧 —— 它们是工作空间脚本的依赖,不是看板的依赖,
写进去会让所有只用看板的人都装一遍。`single-file` 另有硬约束:它是 AGPL-3.0,
**只能 spawn、永不 import**,理由与做法见 `src/server/capture.mjs` 开头的「AGPL 边界」。
工作空间脚本是 Python、走子进程调用,天然落在安全的那一侧,但这条不能因此忘掉。

**[存量工作空间迁移时改坏文档] → ** 默认预演;落盘走「先写临时文件再原子替换」;
改动范围限死在两类机械改写。几个实例的 `output/**` 都在数十份量级,预演输出能人工过一遍。
另外这些工作空间都在 git 下,真改坏了能还原。

**[给九个技能各加一句引用,是九处可能漂移的地方] → ** 所以只加**指针**不加内容。
指针漂移只会指错位置(一眼能发现),内容漂移会给出互相矛盾的规范(发现不了)。

## Migration Plan

1. 先落规范与校验闸(`AGENTS.md` 那一节 + `check_markdown.py`),此时不动任何存量文档。
2. 在模板工作空间自身跑一次校验,拿它当第一份回归样本 —— 模板里的 md 本身就得合规。
3. 写 `migrate_markdown.py`,在模板上预演、核对输出,再落盘。
4. 九个技能加指针。
5. 最后做 `web_ingest.py`,它依赖前面已经定稿的规范。
6. 存量工作空间由用户各自跑一次迁移(预演 → 人工过目 → 落盘),不集中处理。

回滚:前四步都是 `templates/` 下的文档与新增脚本,回滚就是撤销提交;
存量工作空间的迁移由 git 还原。

## Open Questions

- 校验闸要不要接进 `pm-*` 技能的收尾步骤(写完文档自动跑一次)?
  倾向不接 —— 会让每次写文档都多一次脚本调用。先留成人工触发,看实际漏网率再说。
- `output/docs/` 下的对外交付文档要不要也强制 front-matter?
  它们是要发出去的,front-matter 对收件人是噪音。倾向只要求 `analysis/` 与 `decisions/`,
  `docs/` 放宽 —— 但这条留到实现时按模板现有 README 的措辞再定。
- **整站抓取是已知缺口,本变更不补。** 要吃一整个公开文档站或标准库(几十上百页)时,
  一次一页地贴 URL 不成立。这是 Firecrawl 的 crawl / map **真正独有**的能力
  (也是自建版确实提供的那部分)。真遇到这个需求时再单开一个变更评估,
  且倾向只接云 API(一个 key、一个 HTTP 调用),不自建四个常驻服务。
  注意云 API 意味着把 URL 交给第三方:公网页面没问题,
  内网文档站既不该发也抓不到 —— 那种场景只能走现有的一次一页。
- 提取出的正文与参考采集的 HTML 之间要不要维持长期关联(比如 HTML 被删了产物怎么办)?
  倾向不维持强关联:front-matter 里那条路径是线索不是依赖,指空了也不影响产物本身可读。
