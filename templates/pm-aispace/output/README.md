# output/ — 阶段三：产出

所有分析结论和交付文档都落在这里。`input/` 是别人给你的，`output/` 是你交出去的。

手写 Markdown 的写法见工作空间根目录 [AGENTS.md](../AGENTS.md) 的「Markdown 写法」一节。
`analysis/` 与 `decisions/` 要带最小 front-matter；`docs/` 是要发出去的，front-matter 不强制。

## 五个子目录

### `analysis/` — 想清楚的过程

给自己和 AI 看的中间产物，不对外发。典型内容：

- `现状基线.md` — 接手时项目到底是什么状态（`pm-project-handover` 产出）
- `需求拆解.md` — 按模块拆开的需求条目、优先级、验收标准（`pm-requirement-analysis` 产出）
- `干系人.md` — 谁能拍板、谁提需求、谁验收

建议加日期前缀便于排序：`2026-07-30-计费模块需求拆解.md`。

### `questions/` — 未决问题

接手项目时资料一定不全，
把「资料里查不到、需要向对方确认」的问题攒成一份清单，比硬猜着填满文档有用得多。
它直接就是你跟对方团队第一次对齐会议的议程。

**为什么是一问一文件，不是一张表。** 早先这里是单份 `open-questions.md` 的 markdown 表格。
九个技能往里追加，没有一个负责取出，两个月就长成「两百多条、一半标『高』、
平均 200 字挤在一个单元格里」，最后整份被放弃。改成一问一文件之后：
条目长度由 front-matter 的扁平结构管住、排序轴从自我评估的优先级换成客观的
「阻塞哪个在途交付物」、每条都有「被回答」之外的消解出路。

**为什么和 `analysis/` 平级。** 它一度放在 `analysis/questions/`，结果两百多份问题文件
把「分析中间产物」那份清单整个淹掉 —— 那份清单本来是给人扫现状基线、需求拆解用的。
问题清单有自己的入口（看板 ⌘K 弹窗，按交付物分组、能就地处理），
不需要、也不该在文件列表里再占一遍位置。提到同级之后它不进任何视图的列表。

字段契约在 [`questions/README.md`](questions/README.md)，
落问题和取问题都走 `pm-open-questions` 技能。旧工作空间要迁移跑
`python3 scripts/migrate_questions.py`（默认预演，不落盘）。

### `records/` — 产出物记录

`analysis/` `docs/` `decisions/` 里的每份产出物，在这里有一份带状态的记录：
这份还作数吗、发出去之后对方说了什么、这条决策是不是已经被推翻。
不然产出物只有一个修改时间，生命周期断在「文件存在」那一刻，列表只会单调变长。

记录是**我方视角的私有元数据**,旁挂在产出物边上，用 `target` 单向反链过去 ——
产出物文件不因为建记录而改变一个字节。`docs/` 是要发出去的，把状态塞进它的 YAML 头
对收件人是噪音（见下面 `docs/` 那节的立场）。

**为什么和 `analysis/` 平级、又不进看板的三组列表。** 与 `questions/` 同一条理由：
三类产出物合计的记录数会把「分析中间产物」那份清单整个淹掉，
而那份清单是给人扫现状基线、需求拆解用的。记录有自己的入口
（看板 ⌘K 工作台的「产出物」页，按类别与状态分组、能就地改状态）,
不需要、也不该在文件列表里再占一遍位置。

字段契约在 [`records/README.md`](records/README.md) —— 编号规则、按 `kind` 分化的三套状态机、
状态流水写法、人写区与 AI 写区的分界都在那里。建记录走 `pm-output-record` 技能。
存量决策要补记录跑 `python3 scripts/migrate_decisions.py`（默认预演，不落盘）。

### `<组>/一次归档/` — 不再作数、但还要留着的

`analysis/` `docs/` `decisions/` 只会单调变长：陈旧的分析、被取代的文档和在用的东西平铺在同一个时间序里。
人还能靠搜索凑合，**AI 是全量读**。看板「产出文档」列表行的「更多 → 归档」
会把一份移进同组的 `一次归档/`（写盘的是 `scripts/archive_output.py`，看板只起它）。

**为什么在各组内部，不在 `output/archive/`。** 放在组内，看板的递归扫描照样收得到 ——
归档项照样能搜、能点开预览，AI 需要时照样能读，**可达性一点不降**，只是不再占主列表的位置。
统一一个归档目录会丢掉「这份原本属于哪一组」：被取代的交付文档和过时的中间产物，
回头整理时是完全不同的两堆。移出 `output/` 之外（比如点开头的隐藏目录）就是降低可达性，不这么做。

- **只移动，不删除。** 别处的会议纪要可能正写着「见某某文档」。落点同名时加日期后缀，不覆盖。
- **归档不是状态。** 记录里的 `status` 不因归档而变；记录的 `target` 要跟进到新路径（走 `pm-output-record`）。
- **`一次归档/README.md` 是交接单**：脚本在清单里逐条追加原路径与新路径，
  底下有一段二次归档提示词。攒多了之后把它粘给 agent（走 `pm-output-archive`），
  它会按主题分堆、每堆写一份几百字的 `INDEX.md`。**不产出任何「无需再读」清单。**
- 本轮只能归档组根目录下的文件；组内子目录里的在看板上不可归档，要挪就在终端里自己移。

### `docs/` — 交付给别人的文档

PRD、需求规格说明书、评审材料、验收标准。用 `pm-prd-writing` 生成，格式规范、能直接发出去。

一份文档一个文件，文件名就是文档名，不要 `v2_final_最终版` 这种后缀——版本交给 git。

### `decisions/` — 决策记录

一个决策一个文件，`0001-短标题.md` 顺序编号，**只追加不改历史**。

```markdown
# 0001-计费口径按自然月而非 30 天

- 日期：2026-07-30
- 状态：已确认 | 待确认 | 已推翻（被 0007 取代）
- 决策：计费周期按自然月对齐，跨月订单按自然月切分。
- 背景：原系统按 30 天滚动，与财务对账口径不一致（来源：input/converted/财务对账说明.md）。
- 代价：历史订单需要迁移，影响约 2 万条数据。
- 谁拍的：王××（财务）+ 李××（技术负责人），2026-07-30 对齐会。
```

正文里那行 `状态：` 是给人读的，解析器读不到它 —— 看板按 [`records/`](records/README.md)
里那份记录的 `status` 字段判断一条决策还生不生效，`pm-output-record` 技能建决策时一并建记录。
**两处都保留**：正文那行不要删。

为什么值得单独建目录：接手项目三个月后，一定会有人问「这里为什么这么设计」。
没有决策记录时答案只在某个人脑子里，而那个人可能已经不在项目上了。
被推翻的决策不要删，把 `状态` 改成已推翻并指向新决策——推翻的过程本身是重要信息。
