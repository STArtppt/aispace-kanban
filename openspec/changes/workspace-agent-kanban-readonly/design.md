## Context

工作空间由 `templates/init_workspace.py` 从模板生成，在里面干活的智能体可能是 Claude Code，也可能是其他工具。
它们的行为约束几乎全靠模板里的 `AGENTS.md`。现状有三处缺口：

- `AGENTS.md` 在「Markdown 写法」里写了看板源码的相对路径（如 `src/server/frontmatter.mjs`），
  智能体会顺着它去找本机的看板仓库。那个目录在工作空间外，每次读取都要用户授权。
  （本 change 立项前，已先把这两处改成 GitHub 链接，并加了一小节「看板显示不对时去哪查」；本 change 在此基础上收口。）
- 「模板改动回同步源」一节要求智能体把模板文件的改动写回看板仓库，但没说能写哪些路径。
- 智能体发现看板缺陷时，没有上报渠道。

案例：某个智能体把 `deliverables` 写成字符串数组，概览页的 `ObjectTable` 用 `Object.keys(row)` 取列名，一句话被拆成几十个单字列。
它改了本机看板的 `MetaView.tsx`，只跑了 `tsc --noEmit`。这份改动至今还在看板工作区里，没有提交。

## Goals / Non-Goals

**Goals:**

- 工作空间智能体读看板源码不再需要用户授权（改读 GitHub）。
- 智能体改看板源码的做法，在规则上被禁止；对 Claude Code，还要在工具层拦住。
- 真需要改看板时，有一条从工作空间到看板仓库、再回到工作空间的完整路径。
- 本次案例按正规流程收尾。

**Non-Goals:**

- 看板不做反馈单的展示或管理界面。以后要做，另开 change，并且要按只读红线评估。
- 不自动提 GitHub issue。
- 不管其他工具（WorkBuddy、Codex 等）的权限配置格式，只靠规则和它们自己的沙箱。
- 不把概览页 `identity` 里还没有渲染入口的字段（项目别名、合同金额、工期等）一并补上。这是另一个产品决策。

## Decisions

### 1. 读 GitHub，不读本机

- **选择**：模板里凡是提到看板源码的地方都给 GitHub 链接；排查时用 `raw.githubusercontent.com/.../main/<路径>` 读原文。
- **备选**：把看板根目录加进工作空间的读权限 allow。**不选**，因为路径每台机器不一样，而且读的权限一开，写就只差用户一次误点。
- **代价**：GitHub 的 `main` 可能和本机跑的版本不一致（本机没推送，或者装的是旧版 npm 包）。
  规则里要求版本对不上时照实说，不下结论。

### 2. 反馈单放隐藏目录 `.kanban-feedback/`

- **选择**：放在工作空间根目录，一个问题一份文件。
- **备选 A**：`output/kanban-feedback/`。在看板里能看到，但 `output/` 下多一个目录会进扫描和各个视图，
  要改服务端和前端，是跨平面的改动。**不选**，先把流程跑起来。
- **备选 B**：直接提 GitHub issue。仓库是公开的，复现片段很容易带上客户资料；提 issue 也是对外动作，要用户确认。**不选**。
  反馈单在看板仓库这边处理并脱敏后，用户想转成 issue 再转。
- **备选 C**：写进 `output/questions/`。那是给业务方的未决问题，性质不同，会污染对齐会议清单。**不选**。

### 3. 回执由用户转交，两边的智能体都不跨目录写

- **选择**：看板仓库的会话给出回执文本，用户转给工作空间智能体，由它回写状态、撤掉临时绕法。
- **备选**：看板仓库的会话直接写工作空间里的反馈单。**不选**，这正是本 change 要禁止的那种「跨目录顺手写」，只是方向反过来。

### 4. 在 `.claude/settings.local.json` 里生成 deny 规则，逐个列出顶层条目

- **选择**：`init_workspace.py` 知道看板根目录（它自己所在目录的上一级），逐个列出根目录下的顶层条目，
  为除 `templates/` 以外的每一项写 `Edit(//<绝对路径>/**)`；`templates/` 下除本模板以外的条目也同样处理。
  Claude Code 的 Edit 规则对它的所有内置写文件工具都生效。
- **为什么逐个列出，而不是整个根目录一条 deny 再给 `templates/pm-aispace` 放行**：Claude Code 里 deny 优先于 allow，放行写不出来。
- **备选**：整个看板根目录全部 deny，模板同步也改走反馈单。更严，但每次同步模板都要跨两个会话，太麻烦。**不选**。
  如果以后发现模板同步本身也常常越界，再收紧到这一步。
- **为什么写 `settings.local.json` 而不是 `settings.json`**：里面是本机绝对路径，不应该入库，也不能随工作空间复制到别的机器上。
  模板 `.gitignore` 同步忽略它。
- **补规则开关**：给已有工作空间用，只合并这一个文件的 `permissions.deny`。它由用户在命令行手动运行，看板不调用。

### 5. 本次案例：审完再决定是否保留那份遗留改动

- **选择**：`MetaView.tsx` 的遗留改动按本仓规则重新审（spec 见 `project-meta-view`），通过就保留并提交，不通过就改到通过为止。
  它的思路（原始值行进单列、补上「验收标准」）和 spec 一致。
  同时从根上修：模板 `project.yaml` 补「形如」注释，`pm-project-meta` 技能补对象数组的约定。
- **备选**：整份撤掉，只修模板。**不选**，渲染器对字符串数组静默拆字本身就是缺陷，只修模板防不住手写的情况。

## Risks / Trade-offs

- [deny 规则拦不住 shell 写法（`sed -i`、重定向）] → 规则层是主防线，deny 只防误点授权；在 design 和模板里都照实写明，不宣称是硬隔离。
- [其他工具不读 `.claude/`] → 只能靠 `AGENTS.md` 规则和它们自己的沙箱。多数工具默认只能写工作空间，越界时会弹授权，用户拒绝即可。
- [看板仓库以后新增顶层条目，已生成的 deny 不会覆盖它] → 补规则开关可以重复运行；在看板 `AGENTS.md` 里提一句，新增顶层目录后提醒用户重跑。
- [已有工作空间不会自动拿到新规则] → 在看板 `AGENTS.md` 和模板 README 里写明手动补的两步：复制 `AGENTS.md` 的对应小节，运行补规则开关。
- [看板从 npm 包运行时，根目录是包安装目录] → 同样适用，deny 覆盖的是包目录；升级后路径变了就重跑补规则开关。

## Migration Plan

1. 合并后，新建的工作空间自动带上规则和 deny。
2. 已有工作空间：用户手动同步 `AGENTS.md` 的对应小节，并运行 `init_workspace.py` 的补规则开关。
3. 回滚：删掉 `settings.local.json` 里的 deny 条目，模板规则回退一个提交即可。看板服务端没有改动，不需要重启。
