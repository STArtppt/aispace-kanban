# 模板更新

这个工作空间是从看板仓库的模板 `templates/pm-aispace` 铺出来的。模板之后修了脚本、加了技能，
不会自己到这里来 —— 要靠这个技能拉进来。

脚本 `scripts/template_update.py` 负责判定和落盘，你负责：讲清楚、等确认、合并冲突、汇报。
判定口径写在脚本文件头，这里不抄第二遍，只写够干活的摘要：

| 计划里的组 | 意思 | 执行时怎么办 |
| --- | --- | --- |
| 新增 | 模板有、这边没有 | `apply` 写入 |
| 覆盖 | 这边没改过，模板有新版 | `apply` 替换成新版 |
| 保留 | 这边改过，模板没变 | 不动 |
| 冲突 | 两边都改过；或首次接入时和新版对不上 | **不动**，由你逐个合并 |
| 模板已删除 | 新版模板不再有这个文件 | 不删，告诉用户 |
| seedOnly 有新版 | `project.yaml`、`.gitignore`、`input/.ingestignore`、去 AI 味规则库这类「铺完归工作空间」的文件，模板那边变了 | 不动，按下文逐个处理 |

基线记在 `.aispace/template.lock.json`（入库，别手改）。本项目专有的约定在工作空间根的 `AGENTS.local.md`，
它不属于模板，更新不碰它。

## 步骤

### 1. 出计划

```bash
python3 scripts/template_update.py plan                        # 从 GitHub 公开仓库取 main
python3 scripts/template_update.py plan --ref <标签或提交号>    # 用户指定版本时
```

- 网络不通时脚本会退出并给两条出路：设代理，或 `--from <本地模板目录>`（用户手里有看板仓库或 npm 包时）。
  **不要自己去翻本机的看板仓库**，本地目录只在用户给出时用。
- 输出里有 `注意：` 的（比如没查到提交号），原样告诉用户。
- 记下计划文件路径（`plan_file`），后面几步都要用。

### 2. 讲给用户，等确认

用户是 PM，不是工程师。按下面的口径讲，**不要贴文件清单了事**：

- 新增了哪些能力（新技能、新脚本能做什么），更新了哪些工具（修了什么、对他有什么影响）；
  看不出改了什么就读一下新旧差异，别猜；
- 哪些没覆盖、为什么（这边改过的、项目专有的）；
- 有几个文件要你来合并，大概要多久；
- 模板删掉了什么，要不要这边也删（默认不删）。

然后**停下来等用户确认**。用户没明确说「可以 / 执行」之前，不跑 `apply`。

### 3. 执行

```bash
python3 scripts/template_update.py apply --plan <计划文件>
```

- 报「计划已经过期」：说明出计划之后有文件变了，回到第 1 步重新出计划、重新确认。
- 执行完，新增和覆盖的文件已落盘，lock 已更新；冲突文件一个字节没动。

### 4. 逐个合并冲突

先取三方对照：

```bash
python3 scripts/template_update.py compare --plan <计划文件>
```

它按 lock 记的来源再取一次上一版模板（基线），给两份 diff：「基线 → 工作空间」是这边改了什么，「基线 → 模板新版」是模板改了什么。
lock 来源是本地目录、取不回基线时，它只给「工作空间 → 模板新版」两方对照，并提示可以用 `--base-from` / `--base-ref`。

每个文件：

1. 以**模板新版**为底，把「基线 → 工作空间」里这边独有的改动搬回去。
2. 这边独有的内容**优先保留**；拿不准是不是有意改的，列给用户问，不要替用户丢掉。
3. 这边的改动如果是**项目专有**的（本项目的目录、客户术语、原型工程在哪），不要合回模板管理的文件，
   挪进 `AGENTS.local.md`（没有就建）。模板管理的文件越接近模板原样，下次更新越省事。
4. 这边的改动如果是**换一个项目也成立**的改进，合并时保留，另外写一份贡献单交回模板源（见模板 `AGENTS.md`「贡献改进」）。
5. **不要写带 `<<<<<<<` 冲突标记的文件。** 技能和 AGENTS.md 带着冲突标记会被智能体当成指令读进去。
6. 合并前后各给用户一句差异摘要：「保留了这边加的 X；采用了模板新加的 Y」。
7. 合并完登记：

   ```bash
   python3 scripts/template_update.py apply --plan <计划文件> --resolved <文件> [<文件> …]
   ```

   不登记，下次更新还会把它报成冲突。

### 5. seedOnly 有新版的文件

这些文件归工作空间所有，脚本永远不覆盖。计划里给了 diff，逐个处理：

- **去 AI 味规则库**（`.claude/skills/pm-deai-writing/rules/**`）：按 `pm-deai-writing` 的「用法四 · 并入模板新规则」并入，
  本地编号不改。
- **`.gitignore`、`input/.ingestignore`**：模板新加的忽略项多半该要，列给用户，确认后追加到末尾；这边原有的行不动。
- **`project.yaml`**：模板加了新字段时，把新字段按 `null` 补进来；已有的值一个不改。
- 其它：列出差异，问用户。

### 6. 汇报

- 用了哪一版模板（`source`）；
- 新增 / 覆盖 / 合并了哪些，各一句话说影响；
- 还剩哪些没处理、为什么；
- 写了几份贡献单（路径）；
- 提醒用户把 `.aispace/template.lock.json` 和这次改动一起提交（工作空间是 Git 仓库时）。

## 首次接入

几个月前铺出来、从没更新过的工作空间没有 `.aispace/template.lock.json`。这时 `plan` 标「首次接入」：
和新版逐字节相同的记为一致，其余模板管理的文件**全部列为冲突** —— 没有基线，分不清是这边改过、还是旧模板本来就那样。

所以首次接入的冲突大多**不是真的冲突**，而是旧模板原文。逐个判断：

1. 读「工作空间 → 模板新版」的 diff，只看**工作空间里有、模板新版里没有**的内容。
2. 这些内容里，确认是项目专有、或用户有意改的，才保留（项目专有的挪进 `AGENTS.local.md`）；
   看起来像旧模板的说法、旧命令、旧目录名的，按模板新版。
3. 拿不准的列给用户，一次问完，别一个文件问一次。
4. 每处理完一个就 `--resolved` 登记。全部登记完，lock 才完整；下一次更新就是正常的三方判定了。

## 不要做的事

- 不跳过第 2 步的确认直接 `apply`。
- 不改 `input/`、`output/` 下的资料和产出，不改 `visualization/`。各目录自带的 `README.md` 属于模板，照计划更新。
- 不删除任何文件，包括「模板已删除」组里的。
- 不手改 `.aispace/template.lock.json`；登记只用 `--resolved`。
- 不写看板仓库的任何文件（包括 `templates/`）。模板有问题写缺陷单，有改进写贡献单。
