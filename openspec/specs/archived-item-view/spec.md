# archived-item-view

## Purpose

产出视图怎么呈现已归档项:列表行的「归档」入口与置灰理由、归档项从三组主列表分出去到已归档分区、主列表与已归档分开报计数、堆 `INDEX.md` 排在那一堆最前面、产出物记录里由 `target` 派生的「目标已归档」标记(不进状态机),以及新前端配旧服务进程时的降级。「是否已归档」的判据由服务端下发,前端不自己解析路径。本能力由 `output-archive` 变更落地。

## Requirements


### Requirement: 列表行的「更多」菜单里有归档入口

产出文档列表的每一行 SHALL 在「更多」菜单里提供「归档」。
它 MUST 需要一次确认,确认文案 MUST 写明**文件不会被删除,仍然可以搜到和预览** ——
界面文案一律说「归档」,MUST NOT 说「移除」「删除」「清理」。

不可归档的情况(组内子目录下的文件、已经在 `一次归档/` 下的文件、
工作空间没有归档脚本)MUST 把这一项置灰并说清理由,MUST NOT 点了没反应。

#### Scenario: 归档一份

- **WHEN** 用户在某一行的「更多」里点「归档」并确认
- **THEN** 这一行从主列表消失,出现在同一组的已归档分区里
- **AND** 列表不需要手动刷新(写盘被工作空间监听捕获)

#### Scenario: 确认提示说清不是删除

- **WHEN** 确认框弹出
- **THEN** 它写明文件不会被删除,归档后仍然可以搜到和预览

#### Scenario: 没有归档脚本

- **WHEN** 工作空间里没有 `scripts/archive_output.py`
- **THEN** 「归档」置灰,并说明用模板新建的工作空间自带脚本、自己建的目录需要自己装

#### Scenario: 归档失败

- **WHEN** 脚本执行失败或接口返回 400 / 403
- **THEN** 界面照原文说明失败原因,这一行留在主列表里

### Requirement: 归档项从主列表分出去但仍可预览

归档项 MUST 从三组主列表里分出去(单独的已归档分区或筛选开关),不再占主列表的位置。
但它们 MUST 仍然可点开预览、可被搜索命中 —— 分出去不等于藏起来。

「是否已归档」MUST 由服务端判定并随产出项下发,前端 MUST NOT 自己解析路径判断 ——
同一个判据实现两遍,目录名一改就是两处要同步。

#### Scenario: 主列表不含归档项

- **WHEN** 某一组下有 3 份在用的、12 份已归档的产出物
- **THEN** 主列表只显示 3 份,已归档的 12 份在另一个分区或筛选开关后面

#### Scenario: 点开一份归档项

- **WHEN** 用户在已归档分区里点一份文档
- **THEN** 它照常在预览里打开,行为与归档前一致

#### Scenario: 搜索横跨两侧

- **WHEN** 用户搜一个只在归档项标题里出现的词
- **THEN** 结果里有它,并看得出来它是已归档的

### Requirement: 计数把主列表与已归档分开报

三组的计数 MUST 只数主列表,已归档的另报一个数,两者 MUST 同时出现。
只报主列表数会让「产出总数」突然变小,看起来像文件没了。

#### Scenario: 归档一份之后看计数

- **WHEN** 用户归档了一份 `docs`
- **THEN** `docs` 的主列表计数减一,已归档计数加一,两个数都在界面上看得到

### Requirement: 堆索引排在那一堆的最前面

已归档分区里,某个堆目录下有 `INDEX.md` 时,它 MUST 排在那一堆的最前面并标成「堆索引」。
它就是一份 Markdown,点开走现成的预览,MUST NOT 为它做专门的渲染组件。

#### Scenario: 二次归档之后看归档区

- **WHEN** 工作空间 AI 完成了二次归档,某组的归档区下有三个堆目录
- **THEN** 每堆的 `INDEX.md` 排在那一堆最前面并标成「堆索引」
- **AND** 点开它走普通的 markdown 预览

#### Scenario: 还没有二次归档

- **WHEN** 归档区下是平铺的文件,没有任何堆目录
- **THEN** 照常平铺显示,不提示、不催促

### Requirement: 产出物记录里标出「目标已归档」

产出物记录的索引项 SHALL 带一个**派生**的「目标已归档」标记,
由 `target` 路径里有没有 `一次归档/` 算出来。

它 MUST NOT 是状态:MUST NOT 写进 front-matter、MUST NOT 进三套状态机、
MUST NOT 因此修改任何记录文件。归档改变的是位置,不是产出物的状态。

`target` 在归档后会指向旧路径,由 agent 跟进(`target` 属于 AI 写区)。
跟进之前记录显示「指向丢失」MUST 保留为现有行为 —— 文件确实不在那里了,那是准确的提示,
不是 bug。归档脚本在 README 清单行里记了原路径与新路径,agent 据此跟进。

#### Scenario: 记录的 target 跟进之后

- **WHEN** agent 把某份记录的 `target` 改成归档后的新路径
- **THEN** 工作台的产出物页把这条标成「目标已归档」,状态值一个字没变

#### Scenario: 记录的 target 还没跟进

- **WHEN** 产出物已经归档,记录的 `target` 还指着旧路径
- **THEN** 这条照现有行为标成「指向丢失」(orange),MUST NOT 隐藏它、MUST NOT 自动改它

#### Scenario: 归档不动状态机

- **WHEN** 一份 `final` 的交付文档被归档
- **THEN** 它的记录 `status` 仍然是 `final`,状态流水里没有多出任何条目

### Requirement: 旧服务进程时退回改动前的行为

前端是新的而服务进程是旧的(产出项里没有「是否已归档」字段)时,归档项 MUST 照旧留在主列表里。
这种情况下界面 MUST NOT 报错、MUST NOT 白屏 ——
那等于「功能没启用,行为与改动前一致」。
触发归档时接口 404,界面 MUST 提示重启看板服务。

#### Scenario: 新前端配旧服务

- **WHEN** 用户没重启服务就刷新了页面
- **THEN** 产出视图照常显示(归档项混在主列表里),没有已归档分区,不报错

#### Scenario: 旧服务上触发归档

- **WHEN** 用户点「归档」而服务进程还是旧的
- **THEN** 接口 404,界面提示重启看板服务,工作空间里没有任何变化
