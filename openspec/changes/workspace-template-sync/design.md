## Context

工作空间由 `templates/init_workspace.py` 从 `templates/pm-aispace` 复制铺出：
`AGENTS.md`、`CLAUDE.md`、`README.md`、`.gitignore`、`.env.example`、`scripts/`、`.claude/`，外加 `output/` 下各目录的 README 和 `input/` 的约定文件。
铺完以后，实例与模板再没有联系。

上一次手工把模板同步到维护者本机的四个实例时，逐文件判定用的是看板仓库的 git 历史：实例文件等于模板某个历史版本就覆盖，否则当作本地改动。
这次暴露出三个问题：

1. **没有基线。** 有的实例是从未提交的模板工作副本铺出来的，文件和任何历史版本都对不上。
   拿「最接近的历史版」做三方合并，会把旧模板原文当成本地改动，再合回新版 —— 一份 AGENTS.md 因此看起来有 45 行「本地改动」，实际一行都没有。
   最后靠「实例里有、模板所有历史版本里都没有的行」才分清楚，而这个判法依赖看板仓库的完整 git 历史，普通用户手里没有。
2. **项目专有内容混在模板文件里。** 有个实例在 AGENTS.md 里加了一节「本项目的原型工程在哪」，
   有的在 `.gitignore`、`input/.ingestignore` 里追加了项目规则，去 AI 味规则库也会随批注沉淀而演进。
   这些混在模板管理的文件里，更新时只能人工挑出来。
3. **反向回流靠直接写本机看板仓库。** 模板 AGENTS.md 的「模板改动回同步源」一节允许智能体写看板仓库 `templates/pm-aispace/` 下的同名文件。
   这只在维护者本机成立：通过 npm 安装看板的用户没有可写的仓库；公开仓库也不该被各个工作空间直接写。

已有的交接通道是反馈单（`output/feedback/F<编号>.md`）：智能体写单，用户在看板上预览后用本机邮件客户端发出，维护者在看板仓库会话里处理，回执再转回来。
服务端只在用户点「我已发出」后写 `sent_at` 和发送记录（不变量 1 第八条）。

## Goals / Non-Goals

**Goals:**

- 已有工作空间的智能体能从公开仓库把模板的新版本拉进来：先出计划，再落盘；实例的本地改动和项目资料不丢。
- 每次铺设、更新都留下基线，下一次更新是确定的三方判定，不再靠猜。
- 项目专有内容与模板管理的文件物理分开。
- 实例里沉淀出的通用改进有一条对所有用户都成立的回流路径：贡献单 → 邮件 → 维护者合并 → 回执。
- 工作空间智能体不再写看板仓库的任何文件。

**Non-Goals:**

- 看板界面上的「模板有新版本」提示和一键更新。看板服务端不发网络请求、不写工作空间，更新由工作空间智能体执行；看板侧入口另立 change。
- 自动合并冲突。冲突交给智能体按技能说明逐个处理，脚本只负责判定和报告。
- 多模板之间的同步（用户自建模板）。本期只覆盖 `pm-aispace`，其他模板要用同一套机制，需自带 `sync` 段。
- 贡献单的自动提交（开 PR、调 GitHub API）。仍走邮件，维护者手工合并。

## Decisions

### D1 · 基线：lock 文件记来源版本和逐文件哈希，基线内容按版本现取

`.aispace/template.lock.json` 记录：模板 id、来源（`github:<仓库>@<提交号>` 或 `local:<目录>`）、铺设时间、每个已铺文件的相对路径与 SHA-256。
更新时：

- 实例文件哈希 = lock 里的哈希 → 实例没改过：模板有新版就覆盖，模板删了就列出（不删）；
- 实例文件哈希 ≠ lock → 实例改过：模板没变就保留实例版，模板也变了就是冲突；
- lock 里没有、实例里也没有 → 新增；
- 冲突时需要基线原文做三方对照，按 lock 里的提交号再取一次那个版本的源码包，只解出冲突文件。

**备选**：把铺设时的全部文件复制一份存进 `.aispace/template-base/`。离线也能三方合并，但每个实例多存几 MB（docxkit 带图片和示例），
还是一份会被搜索、被误改的影子副本。冲突本来就少，按需现取就够了。

**备选**：不记 lock，继续用「等于某个历史版本」判定。普通用户没有看板仓库的 git 历史，这个判法用不了；而且已经证实会误判。

`.aispace/` 以点开头，看板扫描本来就跳过点目录（`src/server/scan.mjs` 的点目录过滤）。lock 要入库：它是这个工作空间「当前是哪一版模板」的事实，换机器、换人接手都要用到，里面没有本机路径。
`local:` 来源只记目录名，不记绝对路径。

### D2 · 拉取：GitHub 源码包 + 标准库，版本号用提交号

`template_update.py fetch --ref <分支|标签|提交号>`（缺省 `main`）从 `https://codeload.github.com/STArtppt/aispace-kanban/tar.gz/<ref>` 下载，
用 `tarfile` 只解出 `templates/pm-aispace/` 到系统临时目录。解析出的提交号由 GitHub 接口 `api.github.com/repos/.../commits/<ref>` 取得（匿名，失败时退回记 ref 原文并给 warning）。
维护者或离线环境可以 `--from <本地模板目录>`；这是显式参数，默认路径不读本机看板仓库。

**备选**：`git clone --depth 1`。要求装 git，Windows 用户常没有；只要一个子目录，也不值得拉整库。
**备选**：从 npm 包里取（看板装在本机时 `templates/` 就在包里）。这把「更新模板」绑在「升级看板」上，而且又回到了依赖本机路径的老问题。

脚本遵守工作空间「默认路径零依赖」的约定：只 import 标准库。网络失败给中文出路（检查代理、改用 `--from`）。

### D3 · 文件分三类，写在模板的 `template.yaml`

```yaml
sync:
  seedOnly:        # 只在新建时铺；之后归实例所有，更新只报告「模板这边有新版」
    - project.yaml
    - .gitignore
    - input/.ingestignore
    - .claude/skills/pm-deai-writing/rules/**
  exclude:         # 不分发
    - template.yaml
    - visualization/**
```

其余文件都是「模板管理」，按 D1 判定。`template.yaml` 本身不分发，但 `fetch` 时一起读出来，所以分类跟着模板版本走，不写死在脚本里。
seedOnly 文件模板那边有变化时，计划里单列一组「模板有新版，未覆盖」，并给出 diff，由智能体决定要不要把新增的几行并进去（例如 `.gitignore` 新加的忽略项）。

**备选**：在每个文件头上写标记。json、png、lua 各有各的注释语法，也没法标记整个目录。

### D4 · 项目专有约定挪到 `AGENTS.local.md`

模板 AGENTS.md 开头加一句：本项目专有的约定写在 `AGENTS.local.md`（不随模板分发，更新不覆盖），和本文件冲突时以本文件为准，项目专有的补充除外。
CLAUDE.md 加一行 `@AGENTS.local.md`；Claude Code 引入不存在的文件会静默跳过，所以没有这个文件的实例不受影响。
别的 Agent 没有 `@` 引入，靠 AGENTS.md 里那句话去读。`AGENTS.local.md` 不在模板里，天然不属于任何一类。

**备选**：在 AGENTS.md 里用 `<!-- 项目专有 -->` 标记包住，更新时原位保留。标记一旦被误删或嵌套错，整段就会被覆盖掉；
而且模板改了标记附近的章节时，插回位置本身就要人判断。独立文件没有这些问题。

### D5 · 更新分 plan / apply 两步，冲突不落盘

- `template_update.py plan [--ref|--from]`：输出 JSON 计划，分组：新增、覆盖、保留（实例改过、模板没变）、冲突、模板已删除、seedOnly 有新版。只读。
- `template_update.py apply --plan <计划文件>`：只执行计划里的新增和覆盖，逐个原子替换；全部成功后重写 lock。
  冲突文件保持实例版不动，lock 里它的哈希也不更新，下次仍会报冲突，直到智能体合并完、用 `apply --plan <计划> --resolved <文件>` 把它登记为「已合并到该版本」。
  登记写进 lock 的是**这一版模板**的哈希，不是合并结果的哈希：lock 始终是三方合并的基线，
  合并结果与基线不同，下次就被认作「本地改过」—— 模板不变则保留，模板再变才冲突。
  - 计划里带来源提交号；`apply` 发现计划生成后实例文件又变了，就拒绝执行，要求重出计划。
- 技能 `pm-template-update` 规定顺序：plan → 把计划用 PM 能读懂的话列给用户（改了哪些工具、新增哪些技能）→ 用户确认 → apply → 逐个合并冲突 → 汇报。
  合并冲突时，实例独有的内容优先保留；拿不准的留给用户。

**备选**：一步到位，冲突文件写成带 `<<<<<<<` 标记的版本。技能文件、AGENTS.md 带着冲突标记被 Agent 当作指令读进去，后果比不更新更糟。

### D6 · 规则库并入上游规则：本地编号不动，上游规则取下一个空号

去 AI 味规则库是 seedOnly，但模板会随版本增补规则。`pm-deai-writing` 技能新增「用法四 · 并入模板新规则」：
`plan` 报出模板规则库有新版时，智能体按规则的「短名 + 判据」逐条比对：

- 实例里已有同一条（包括由本实例贡献、已被模板收下的）→ 跳过，只在实例规则里补记 `上游：模板 R0xx`；
- 实例里没有 → 按实例的下一个空号新增，`来源：模板 v<N> R0xx`；
- 实例已停用的，保持停用。

整批只升一个版本，CHANGELOG 来源写「模板 v<N> 同步」。

编号不统一是有意的：批注回执里的「沉淀为 R012（规则库 v2）」、交付稿的 `hits` 都引用本地编号，改号会让这些引用全部失效。
模板编号与本地编号的对应靠 `上游：` 一行，贡献回执也写这一行（D8）。

**备选**：划号段，例如模板用 R001–R499、本地从 R500 起。已有实例的本地规则已经用了 R012、R013，要么改号，要么留一个例外；而且号段只能防冲突，解决不了「同一条规则两边各有一个号」。

### D7 · 反馈单加 `kind`，贡献单另有一套内容节

front-matter 加 `kind: bug | contribution`，缺省为 `bug`，旧单不用改。贡献单的内容节：

| 节 | 写什么 |
| --- | --- |
| 贡献了什么 | 一句话 + 类型（技能文案 / 去味规则 / 脚本修复 / 目录说明） |
| 为什么能推广 | 换一个项目这条还成立的理由；只对本项目成立的不要写成贡献 |
| 合成示例 | 反例、正例或复现片段，全部自己编 |
| 涉及的模板文件 | `templates/pm-aispace/` 下的相对路径 |
| 改动内容 | diff 或新增部分全文，已脱敏 |
| 实例里的对应 | 本地编号（如规则 R012）、本地版本，方便回执对应 |

另加「## 发送记录」，与缺陷单相同。服务端 `feedback.mjs` 按 `kind` 选节的顺序表（未知节照旧排在后面）；
索引与详情带出 `kind`，写歪的值归「未识别」组，与 `status` 写歪同样处理。邮件标题前缀：缺陷单 `[aispace-kanban 反馈]`，贡献单 `[aispace-kanban 贡献]`。
第八条窄例外不变：看板只写 `sent_at` 与发送记录。

**备选**：另开 `output/contrib/` 目录和一套新接口。编号、分组、邮件、「我已发出」都要再做一遍，还要再开一条窄例外，收益只是目录名更贴切。
**备选**：沿用缺陷单的六节硬塞。「现象 / 最小复现 / 临时绕法」对贡献是错位的，智能体会写出言不及义的内容。

### D8 · 看板仓库这边：贡献单当需求处理，回执带模板里的位置

看板仓库 AGENTS.md「反馈单在看板仓库这边闭环」加贡献单的步骤：

1. 按公开仓库脱敏红线复查改动内容；
2. 判断收不收，收下就合进 `templates/pm-aispace/`，涉及规则库的写进模板规则库的下一版，并按 D6 判重；
3. 过验证闸、提交；
4. 回执写结论、模板里的位置（如「收为模板 R012（模板规则库 v2）」）和提交号；不收写理由。

实例侧收到回执后，贡献单只改 `status` 和 `receipt`；规则类的，在本地规则里补 `上游：模板 R0xx`，按规则库怎么改升一个版本（「每次变更都升版本」的约定不开例外，快照才不会互相覆盖）。
下一次模板更新时，D6 的判重会识别出这条，不会重复并入。

### D9 · 禁写规则扩到整个看板根目录

`init_workspace.py` 的 `guard_rules` 不再放行本模板目录：看板根目录下每个顶层条目都 deny，包括 `templates/`。
「模板改动回同步源」一节从模板 AGENTS.md 删掉，替换为「沉淀出通用改进时写贡献单」。
补规则开关照旧只做合并，已有实例重跑一次，就会补上 `templates/` 的 deny。

**备选**：保留本模板目录可写，给维护者留后门。维护者在工作空间里写模板，正是这次要取消的路径；维护者要改模板，就在看板仓库会话里改。

## Risks / Trade-offs

- [GitHub 在部分网络环境访问不稳定] → 失败时给出代理设置和 `--from` 两条出路。计划与 lock 都支持本地来源，离线维护者用本地目录更新，不影响判定逻辑。
- [取提交号的匿名接口有频率限制] → 取不到时记 ref 原文、给 warning；这时 lock 的基线是「某天的 main」，下次冲突取基线可能取到别的版本。判定仍然正确，只是三方对照的基线可能不准，技能要求此时以实例版为准。
- [seedOnly 文件永远不自动更新，模板对它们的修复到不了实例] → 计划里单列「模板有新版，未覆盖」并给 diff，技能要求智能体逐个向用户说明。
- [首次接入：已有实例没有 lock] → 首次 `plan` 没有基线：与新版相同的直接记入 lock，不同的一律按冲突报出，由智能体按技能里的「首次接入」一节判断。
  这就是本次手工同步的做法，只是把判据写成步骤。维护者本机的四个实例刚手工同步过，实施时直接为它们写首个 lock。
- [贡献单里带出客户资料] → 模板 README 与技能都要求合成示例；邮件预览已有「发之前确认没有真实资料」提示；维护者合并前按脱敏红线再过一遍。三道都是人为检查，没有自动拦截。
- [智能体在冲突合并时丢掉本地内容] → 冲突文件不落盘、lock 不前移，合并完要显式 `--resolved` 登记；技能要求合并前后给出 diff 摘要。
- [AGENTS.local.md 与 AGENTS.md 冲突] → AGENTS.md 写明以模板约定为准，local 只做补充；这是约定，没有校验。

## Migration Plan

1. 看板仓库：模板加 `sync` 段、脚本、技能、README 与 AGENTS.md 改动；`init_workspace.py` 写 lock、扩禁写；服务端与前端认 `kind`。过验证闸、提交。
2. 维护者本机的四个实例（用户确认后执行）：
   - 为每个实例按提交后的模板版本写首个 lock；
   - 把那一个实例 AGENTS.md 里的项目专有章节挪进 `AGENTS.local.md`，AGENTS.md 恢复为模板原样；
   - 重跑补规则开关。
3. 已铺出去的其他工作空间：用户把「更新模板」的提示词给智能体，首次按「首次接入」处理。
4. 回滚：lock 与 `AGENTS.local.md` 都是附加文件，旧版看板和旧版模板都不读它们；服务端不认 `kind` 时，贡献单按缺陷单的节显示，不白屏。

## Open Questions

- 是否要给模板打版本标签（`template-v1`、`template-v2`），让 `--ref` 默认取最新标签而不是 `main`？标签能挡住 `main` 上的半成品，但要在发布流程里多一步。倾向先用 `main`，等出现半成品被拉走的情况再改。
- 贡献单的「改动内容」很长时（整份技能文件），邮件会走「正文已复制到剪贴板」。是否要支持附件形式？现在的 `mailto:` 做不到附件，先不做。
