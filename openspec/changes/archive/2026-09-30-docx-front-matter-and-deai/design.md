## Context

- **现状**：`md-to-docx`（已实现并归档；它的「真实客户文档复验」就是这一轮）把客户旧 Word 提炼成 `reference.docx`，
  `md2docx.py` 用它作为 pandoc 的 `--reference-doc`，再做四项确定性后处理（生成标记、表头重复、题注 SEQ、Title）。
  这一步的定位写在它的 design D9 里；封面整节搬运列在 Non-Goals 与 Open Questions。
- **实测**（真实客户资料只留在本地，这里只描述结构）：一份现状调查报告作模板，把一份约 500 行、含 3 个批注块、46 处加粗、
  11 处「（依据：…）」的实施方案转成 Word。模板原件有 6 个分节：封面（浮动文本框加图片，文本框有兼容回退副本，同一段文字在 XML 里出现两次）、
  签署页（9 行表格）、版本跟踪表（15 行表格）、目录（TOC 域）、正文。
  - 我们的成品只有 1 个分节；`#` 被映射成一级标题；`## 1.` 这类手写编号和标题样式自带的多级编号叠在一起；3 处 `[!note]` 标记原样漏进正文。
  - 外部技能 docx-template-translator（Apache-2.0）转出的成品有 6 个分节：封面、签署页、目录原样保留，封面文字换成了本文的；
    `##` 是一级标题，手写编号已剥掉，批注标记已去掉。但 13 处依据引用仍在，说明**文字层面的 AI 味不是转换脚本能解决的**。
  - 它的做法：模板既当样式源，也当骨架源；封面、声明、签署页划为「受保护区域」，只在原有 run 里替换文字，不删了重建；
    正文插到真正的正文起点；目录保留 TOC 域。本 change 采用这个思路，但不照搬它的实现：它依赖 python-docx，并且要求每个项目各自改一份流水线。
- **约束**：工作空间脚本只用 Python 标准库（`md-to-docx` D3）；看板只 spawn、不写（第九条）；采集报告不含正文；本仓公开，规划产物脱敏。

## Goals / Non-Goals

**Goals:**

- 带封面、签署页、目录的客户模板，转出来的成品结构与模板一致，封面填的是本文的信息，签署页只留空格子。
- md 的写作习惯（`#` 作标题、手写编号、批注块、加粗强调）不再原样漏进 Word。
- 「AI 味」的纠正能沉淀：有一套带版本的规则库，一份原稿可以有多版交付稿，每一版改了什么、用的哪版规则、由哪些批注修订而来都看得见。
- 对交付稿的每一条批注，都能追到它改出了哪一版、沉淀成了哪条规则。
- 看板在这条线上不新增写入：只展示、比对、复制提示词，批注落盘沿用现有写口。

**Non-Goals:**

- 不做「刷新域」：目录页码、SEQ 编号仍由 Word 在打开时更新（成品会提示）。
- 不在看板里编辑交付稿或规则库，也不在看板里直接调用 AI。
- 不从人对文件的直接改动里归纳规则（沉淀只来自批注）。
- 不做规则库跨工作空间的自动同步（见 Open Questions）。
- 不做用脚本判断 AI 味的自动打分；命中统计由去味的 AI 自己记录。
- 不支持前置区在正文之后的模板（例如封底）；封底留给后续。

## Decisions

### D1 · 前置区作为「骨架源」：提炼时存 `front.docx`，转换时与正文拼装

`collect` 识别前置区，`build` 把它连同依赖的部件（图片、页眉页脚、样式、编号）切出来存成 `front.docx`；
`md2docx.py` 以 pandoc 输出为底包，把 `front.docx` 的前置区块插到正文前，并重新编排被引用部件的 `r:id`、部件名与样式 ID。

- 备选 A：转换时直接拿客户原件当底包，删掉样例正文再插入本文。**不选**：每次转换都要重新判断正文起点、再清洗一次，
  而且客户原件里的样例正文、批注、修订记录会被带进每一份成品。切一次存成 `front.docx`，清洗只做一次，也能单独预览。
- 备选 B：以 `front.docx` 为底包，把 pandoc 正文插进去。**不选**：正文这一侧的部件多而杂（列表编号、脚注、图片、超链接、代码高亮样式），
  前置区只有几张图和几个页眉页脚。把少的搬进多的，要重排的关系更少。
- 备选 C：沿用外部技能的 python-docx 做法。**不选**：D3 已经排除第三方包；而且外部技能自己也说明，它的脚本只是给每个项目改的起点，不能拿来直接用。

装配规则：前置区最后一个分节符保留（它的页眉页脚属于前置区）；正文沿用 pandoc 输出里最后的 `sectPr`，也就是 `reference.docx` 带过来的正文页眉页脚。
正文页眉页脚里与封面字段同文的部分在提炼时写成占位符，转换时一起填值（见 D14）。
样式按「显示名」对齐：`front.docx` 用到、成品里没有的样式，连同它的 basedOn 链一起补进去；显示名相同、ID 不同的，改写前置区里的引用。

### D2 · 格式处理放在 pandoc 之前，用 Lua 过滤器

标题平移、手写编号剥离、批注块、加粗这四项在 pandoc 的 AST 上做（`docxkit/filters/deai-format.lua`，由 pandoc 内置解释器执行）。
模板标题是否带编号，由 `md2docx.py` 检查 `reference.docx` 的 `heading 1` 样式有没有 `numPr`，再以 `-M` 元数据告诉过滤器。

- 备选 A：先用 Python 正则改 md 再交给 pandoc。**不选**：代码块、表格里的 `**`、`> [!` 会被误伤；
  而且「只保留段首标签加粗」需要知道节点结构，正则做不准。
- 备选 B：在 docx 的 XML 上后处理。**不选**：标题层级在 pandoc 那一步就定下来了，事后只能改样式 ID，编号和目录层级容易错位；
  批注块到了 XML 里只剩一个引用段样式，已经分不出 `[!note]` 和普通引用。
- 过滤器只改格式节点，不改 `Str` 节点的文字。例外只有两处，都写进 `log`：剥掉标题开头的编号、删掉 `[!类型]` 标记。

### D3 · 封面字段在 `front.docx` 里存成占位符，报告里只给结构和角色猜测

`build` 把映射成字段的段落文字替换成 `{{title}}`、`{{client}}` 这类占位符，转换时再填值。采集报告只给序号、字数、是否在文本框、字号等结构信息，
加上脚本内部判出的角色标签；用户对照第 ④ 步左侧的原件预览完成映射。

- 备选 A：`front.docx` 保留原文，转换时按原文匹配替换。**不选**：原文会跟着模板包流转；取不到值时还可能把模板原件的单位名称
  写进一份给别的客户的文档里。改用占位符之后，取不到值只会显示「【待填：…】」。
- 备选 B：报告直接带出封面文字，方便映射。**不选**：「报告不含正文」是 `md-to-docx` 立的承诺，反馈单和问题排查都依赖它。
  原件本来就在 `input/raw/`，看板能直接预览，对照着看就够了。
- 同一段文字在文本框和兼容回退副本里各出现一次：采集时按「规范化后的文字摘要」归并成一个字段，摘要只在脚本内部使用，不写进报告。

### D4 · 字段取值顺序：md front-matter → 文档标题 → `project.yaml` → 当天日期 → 醒目占位

- 备选：只从 md front-matter 取。**不选**：`output/docs/` 的约定是 front-matter 不强制（YAML 头对收件人是噪音），
  要求每份文档都写 `client`、`vendor` 太重；甲方、承建方本来就记在 `project.yaml` 的 `identity` 里，脚本只读它。
- `doctype` 没有兜底来源：它随文档而变，猜错了比留空更糟，所以直接显示占位，并给 warning。
  例外是文档自己写明的：`# 项目名 · 文档类型` 这类标题按分隔符拆开，后半段就是本文的文档类型（见 D14）。这不是猜，是读。

### D5 · 签署页、版本表在提炼时就清空样例数据

清空规则在第 ④ 步按表确认，`build` 执行后写进 `front.docx`，转换时不再处理。

- 备选：转换时再清空。**不选**：样例里的人名、日期、版本记录会一直留在模板包里；每次转换重复同一件事也没有必要。
- 默认规则只看结构（首列是否像标签列、首行是否像表头），不看文字内容，所以同样不需要把正文写进报告。
  「结构」要先剥掉顶部横跨整行的合并标题行，标签也不只认首列（见 D14）。

### D6 · 目录保留 TOC 域，清空缓存项，打开时提示更新

- 备选 A：脚本自己生成目录项。**不选**：页码只有排版引擎才知道，自己算一定会错。
- 备选 B：调 LibreOffice 刷新域。**不选**：`md-to-docx` 已经决定不依赖 LibreOffice。
- 代价是 Word 打开时会弹「是否更新域」的提示，WPS 的表现不一样；弹窗和 toast 里都要写明「打开后更新目录」。

### D7 · 去 AI 味两层分工：脚本只动格式，文字交给技能

用户已拍板。脚本这一层就是 D2 的四项。依据引用、套话、句式、强调过度这些，由工作空间 AI 按规则库改写成交付稿。

- 备选：脚本按规则删掉「（依据：…）」。**不选**：一旦误删就追溯不了；而且「依据该留在哪儿」要看上下文，比如移到文末还是放进表格。
- 加粗算格式，所以脚本处理（段首标签式以外的加粗一律解除），规则库里也有同一条，交付稿会在源头少写。两边做同一件事不冲突：脚本兜底，技能治本。

### D8 · 规则库放在技能目录里，每一版存全文快照

`rules.md` 是当前版，`history/v<N>.md` 是全文快照，`CHANGELOG.md` 写人读的变更。看板按快照做两版对比。

- 备选 A：靠 git 历史取版本。**不选**：工作空间不一定是 git 仓库，看板也不该依赖 git；AI 改完规则也不一定会提交。
- 备选 B：只存增量。**不选**：要看某一版的全文就得逐版回放，看板还得实现一遍这套回放。规则库只有几十 KB，存全文更简单。
- 备选 C：放在 `output/` 下。**不选**：规则库是技能的知识，不是项目的产出，跟着技能走，补齐技能时一起带过去。

### D9 · 交付稿放 `output/delivery/`，镜像原稿路径，按序号存版本

- 备选 A：放在原稿旁边（`a.交付.md`）。**不选**：产出列表会被多版交付稿挤满；多版命名也会越来越乱。
- 备选 B：并入 `output/records/`。**不选**：records 是旁挂的元数据，看板对它有第六条直写；交付稿是完整文档，由 AI 写，两者性质不同。
- 与 `records/`、`feedback/` 一样，`delivery/` 不加进 `OUTPUT_GROUPS`，不进产出列表和搜索；只从原稿的阅读器版本条进入。
  它的 `.md` 仍然下发 `docKey`，所以可以直接转成 Word，成品落在交付稿旁边（第九条第 ④ 款要扩到这里，proposal 已标出）。

### D10 · 改交付稿走「批注 → AI 修改 → 同步沉淀」，每一版写出后不再改动

用户已拍板。人不直接改交付稿：在看板里对某一版写批注，复制提示词交给 AI；AI 以那一版为底改出下一版，
同一轮把可推广的批注沉淀进规则库，再逐条回写批注状态，回执里注明沉淀到了哪条规则。
所以版本链是 `v001 →(批注 N0001–N0003)→ v002 → …`，「与上一版对比」看到的正是这一轮批注带来的改动。

- 备选 A：人直接改 md，AI 比对「AI 原样副本」与改后文件来归纳规则。**不选**（上一稿的方案）：比对出来的差异分不清哪些是偏好、哪些是顺手改的内容，
  归纳噪声大；每一版还要多存一份隐藏副本。批注本身就是人用一句话说明的意图，比从 diff 里反推可靠得多。
- 备选 B：先列出候选规则，人确认后再写规则库。**不选**：用户要的是「同步沉淀」；批注已经是人的明确意见，
  回执和 CHANGELOG 都会写明「沉淀为 R0xx」，看得见、查得到。推广错了就停用，代价小于每轮多一次确认。
- 备选 C：批注改在原稿上，再重新去味。**不选**：原稿要保持「AI 起草的底稿」这一身份，交付稿上的措辞修改回流原稿，会把两者搅在一起。
- `body_sha` 只留一个用途：发现有人绕过批注直接改了文件。看板标「被直接改过」，技能以它为底继续，但不从中归纳规则。
  摘要只算正文（front-matter 之后）、先规范化换行、SHA-256 前 16 位，技能说明与 `deai.mjs` 写成同一种。

### D11 · 交付稿的批注挂到原稿的记录上，按镜像路径解析

`findRecordByTarget` 遇到 `output/delivery/<组>/<子路径>/v<序号>.md`，先还原成 `output/<组>/<子路径>.md`，再按原规则找记录。
批注文件里每一批多一行 `- 对象：<路径>`，区分这一批针对原稿还是哪一版交付稿。

- 备选 A：给每一版交付稿建一份记录。**不选**：记录是「一份产出物一个」，交付稿是同一份产出物的不同版本；每版一份记录会把记录索引挤满，
  状态机也对不上（交付稿没有自己的 `drafting → final`）。
- 备选 B：读交付稿 front-matter 的 `source` 找原稿。**不选**：front-matter 可以被手改，批注的落点不该由一个可编辑字段决定；
  镜像路径是结构本身，改不了也骗不了。
- 这样看板的写入面一字不改：仍是第六条第二种写入，仍只写 `notes/I<编号>.md`、仍要求记录已存在、请求仍不带路径。

### D12 · 看板在去 AI 味这条线上不新增写入

看板只读规则库和交付稿；唯一的写入是批注落盘，走已有的第六条第二种写入。不新开窄例外，也不提供在线编辑。

- 备选：看板在界面里直接改规则或编辑交付稿。**不选**：这等于开第十条服务端直写；而改写和沉淀本来就是和 AI 的一轮对话，交回对话里做更自然。

### D13 · 差异对比用 jsdiff（npm `diff`），动态加载

- 备选 A：diff-match-patch。**不选**：长期没有维护，也没有按行、按词切分的现成接口。
- 备选 B：自己写 LCS。**不选**：长文档性能差，边界情况多。
- 先按段对比，再对改动过的段按字对比；超过 2000 行只按段对比。只在打开对比视图时加载。

### D14 · 真实资料复验（11.8）暴露的六处，在本 change 内修

11.8 用一份真实客户模板复验（结论只在本地）：结构与外部成品一致，但前置区有六处不对。它们都是本 change 目标
（「封面填本文信息、签署页只留空格子」）没有达成，不是新需求，所以在本 change 内修完再归档，不另开 change。

1. **正文页眉页脚里的模板原文**。客户模板的正文页眉常写着文档类型或项目名，`reference.docx` 原样带进每一份成品。
   `build` 在脚本内部拿封面字段的原文（映射成 `keep` / `clear` 的除外），到 `reference.docx` 和 `front.docx` 的页眉页脚里找：
   按段拼起全部 run 的文字（页眉文字常被拆成多个 run）规范化后比对，**包含**某个字段原文（至少 4 个字）就把这一段写成
   「前缀 + `{{角色}}` + 后缀」，保住首个 run 的格式。转换时和封面字段同一套取值、同一套「待填」。
   报告只在字段上多一个 `headerHits`（页眉页脚里同文出现几处），第 ④ 步显示「页眉页脚另有 N 处随它替换」。
   - 备选 A：把页眉页脚的全部文字开放成字段让人映射。**不选**：页眉里常有公司名、密级、Logo 旁的口号，大多该原样保留；
     只替换与封面字段同文的部分，误伤面最小，也不用把页眉文字写进报告。
   - 备选 B：页眉页脚全部清空。**不选**：客户模板的页眉格式（下划线、Logo、左右分栏）正是要保住的东西。
   - 代价：`reference.docx` 的页眉里出现 `{{doctype}}`，绕开 `md2docx.py` 直接拿它当 pandoc 参照模板会看到占位符。
     README 写明「只经 `md2docx.py` 使用」；`@base` 与没有前置区的模板不受影响。
2. **字段角色加「清空」（`clear`）**。模板的标题常拆成两段（项目名一段、子名称一段），本文标题只有一个，第二段选「保持原样」
   就把模板原文带进每一份成品。`clear` 保留段落与格式、删掉文字（文本框回退副本一起删），`front.docx` 里不留原文。
3. **文档标题的类型后缀**。标题平移得到的文档标题含分隔符（`·`、`|`、`｜`，两侧空白可有可无）、模板又映射了 `doctype` 字段时，
   在**最后一个**分隔符处拆开：前半段给 `title`，后半段在 front-matter 没写 `doctype` 时给 `doctype`（来源记「文档标题后缀」）。
   front-matter 写了 `title` 时不拆。模板没有 `doctype` 字段时不拆，标题整句照用。
4. **角色猜测的顺序**。封面上字号最大的一段常是文档类型（「××报告」），项目名反而小一号。改为先在大字号字段里认 `doctype`
   （字数 ≤ 15、以常见文档类型词结尾），再在剩下的大字号字段里取字号最大、靠前的作 `title`；
   紧跟在 `title` 后面、同一文本框（或同一节相邻段）、字号与加粗都相同的段落猜作 `clear`（标题续行）。仍然只看结构与形态，报告不加文字。
5. **标签不只在首列**。签署页常是「编写(签字)：｜签名｜审核(签字)：｜签名｜批准(签字)：｜签名」这种一行三组。
   `keepLabels` 的含义从「保留首列」改为「保留标签」：首列照旧保留；其余单元格里，**标签段落**（字数 ≤ 10、以 `：` / `:` 结尾）保留，
   「标签：值」形式的段落只清冒号后面（与封面带标签字段同一规则）；其余清空。判「像标签表」时也按标签段落所在的列数算，不只看首列。
6. **顶部合并标题行**。版本跟踪表、签署页常在第一行放一个横跨整行的标题（「文件版本记录」）。采集时先数出顶部这样的行
   （`captionRows`，任何规则下都原样保留），表头判断改看其后第一行。默认规则的优先级改为：像表头 → `keepHeader`；否则像标签表 → `keepLabels`；
   否则 `keepAll`。像版本表这种「首列是短编号、首行是表头」的，按表头清空，样例版本号不再留下。
   - 不做：往版本表里自动追加一行本文的版本记录（外部技能这样做了）。版本号、修订说明该由人填，自动写一行猜出来的记录比留空更糟。

顺带：日期字段按模板原文的形态写（月份补不补零、「年月」还是「.」分隔），形态在脚本内部判出，报告与 profile 只记形态标记（如 `YYYY年MM月`）；
回归里「报告 / `front.docx` 不含原文」的断言改为按段拼接 run 之后再搜，11.8 自查时就是这样漏掉了页眉里被拆成多个 run 的原文。

### D15 · 第二轮复验与人工审阅发现的正文版式问题，在本 change 内修

- **正文表格跟模板走**：pandoc 给单元格套 `Compact`，客户 profile 把 `Compact` 采成了正文格式（14pt、首行缩进 2 字、两端对齐），
  段落样式压过表格样式，37 张表全被放大（页数 84 对外部成品 47）。新增 `Table Text` 样式（字号、行距取 `table` 段，居中、无缩进），
  `postprocess` 把表格里的 `Compact` / 正文段落换过去；md 分隔行写了对齐的，pandoc 在段落上直接写 `jc`，照样生效。
  保底是「五号、居中、无缩进」，不再单独做可映射角色。
- **整篇不用悬挂缩进**：pandoc 自带的列表编号是「左缩进 + 悬挂」，改成左 0、首行缩进 2 字符 ×（级别 + 1）、编号后接空格。
  `firstLine` 同时写按 docDefaults 字号折算的缇值（LibreOffice 在编号定义里不认字符单位）。标题多级编号不动；需要悬挂的特殊情况由用户在 Word 里改。
- **提示框不缩进**：`Note` 的左缩进由 1 字符改为 0，只留灰底和左边线。
- **不修**：`paragraphs.jsonl` 的 mask 漏出两个样例年月，量很小，转出后人工改很快（用户 2026-09-30 定）。

## Risks / Trade-offs

- [封面字段跨 run、跨文本框的写法千奇百怪（WPS 导出、艺术字、表格排版的封面）] → 按字段收集该段所有 run，只在第一个 run 里写值、其余清空，保住首个 run 的格式；
  认不出的段落默认「保持原样」并提醒；合成语料里加「文本框 + 回退副本」「表格排版封面」两种封面。
- [样式 ID 冲突导致前置区格式漂移（外部技能重点提示过这一条）] → 按显示名对齐、改写引用；`test:docx` 反查前置区段落的格式与 `front.docx` 一致。
- [页眉页脚同文替换误伤（封面字段原文恰好是页眉里公司名的一部分）] → 只对映射成 `title` / `doctype` / `client` / `vendor` / `date` 的字段、至少 4 个字才替换；
  `log` 逐处写明「页眉 N 处 ← 某角色」；第 ④ 步提前显示 `headerHits`，不想替换的把字段改成「保持原样」。
- [「【待填：…】」没被注意就发给了客户] → 结果 `warnings` 里列出每个待填字段，toast 用 orange 标「有 N 处待填」。
- [打开时更新域的提示，有人会点「否」] → 弹窗与 `spec.md` 写明「打开后请更新目录」；目录缓存项清空后显示一行「右键 → 更新域」的占位文字。
- [AI 去味时改了事实] → 技能自检清单要求逐项核对数字、专有名词、表格；看板的「与原稿对比」让改动一眼可见。这只能降低风险，不能消除，所以原稿永远不动。
- [规则越积越多，互相冲突] → 「体检」用法与「停用」状态；首版控制在十来条。
- [同步沉淀把一次性修改误当成通用偏好] → 技能说明给出判据与正反例；回执与 CHANGELOG 都写明来源批注，工作台规则详情能跳回批注；误沉淀的规则停用即可。
- [同一份批注文件里混着原稿批次和多版交付稿批次，标记错位] → 每批带「对象」行，阅读器按对象过滤；旧批次没有这一行时一律归原稿。
- [旧工作空间缺新脚本或新技能] → 看板检测后说明出路，复制提示词让 AI 从模板补齐；已有模板要带前置区，需要「重新提炼」一次。
- [第九条两处扩张] → 已确认，实现时先改 AGENTS.md；服务端 `docKey` 反查范围只增加 `output/delivery/**/v<序号>.md` 这一类。

## Migration Plan

1. `md-to-docx` 已归档（`openspec/specs/` 下已有 `md-docx-export`、`docx-toolchain`），本 change 的 MODIFIED 以归档后的版本为准。
2. 模板与看板同版本发布。已有工作空间：由用户或工作空间 AI 从模板复制 `scripts/docxkit/`、`scripts/md2docx.py`、`scripts/docx_template.py`
   与 `.claude/skills/pm-deai-writing/`；已有模板点「重新提炼」生成 `front.docx`。
3. 回滚：模板不带 `front.docx` 时转换行为与现在一致；去掉过滤器参数即恢复 pandoc 原样输出。看板侧删掉新接口和新组件即可，工作空间里的交付稿、规则库都是普通文件。
